# E2-T04 — индекс триггеров: результат спайка

Дата: 2026-11-06. [Инструмент и протокол](../../tools/trigger_spike/README.md),
[исходные результаты JSON](E2-T04-results.json), задача #5.

## Вывод

Индекс `[scope][on-action]` сокращает стоимость потребителя уведомлений, сохраняя
результат полного обхода. **Гипотеза об ускорении ≥ 10× не подтверждена на стабильных
парах.** Для 15 000 персонажей и 1% изменённых сущностей получено 9.18×; при изменении
всей области — 1.61×. Для 5 000 персонажей результаты составили 9.73× / 5.21× / 1.68×
при изменении 1% / 10% / 100%; первая пара нестабильна (RSD индекса 5.20%).
Номинальные 12.13× для 1 000 персонажей и 1% изменений также не подтверждают порог:
RSD полного обхода 10.22%. Исследование завершено с отрицательным ответом на гипотезу,
а не с подтверждением целевого коэффициента.

Рекомендация для будущего E11: отдельные списки подписок по области и on-action,
фиксированный порядок priority/EventId, устранение повторного кандидата при нескольких
действиях и полный месячный пульс со stagger `id % 28`. Выборка пульсов уменьшает
полноту: за год она обнаружила лишь 17.80–49.55% различных подходящих пар
«определение–сущность». Её время нельзя считать ускорением эквивалентного алгоритма.

## Условия и границы эксперимента

- Windows 11, Intel Core i5-12400F (6 физических / 12 логических ядер), MSVC 19.44,
  Visual Studio Build Tools 2022, C++20, **Release**. Каждый процесс закреплён за первым
  разрешённым логическим CPU (в отчёте CPU 0); частота и глобальные настройки ПК не менялись.
- 9 сочетаний: 1 000 / 5 000 / 15 000 персонажей × 1% / 10% / 100% изменённых
  сущностей каждой области за тик. В каждом — 400 провинций, 500 определений, seed 7,
  365 дней × 3 повтора, прогрев 31 день и сброс входных данных перед измерением.
- Порядок сочетаний перемешан seed 20261106; внутри одного процесса порядок трёх
  методов чередуется по дням и повторам. Полная матрица выполнена один раз;
  нестабильные результаты сохранены, дополнительных прогонов ради коэффициента не было.
- 400 определений on-action и 100 месячного пульса; 80% определений области персонажа,
  20% — провинции. 16 видов on-action, подписка на один или два вида, 4 приоритета,
  три дешёвых предварительно декодированных целочисленных условия по 8 SoA-полям.
  Часть исходных значений проецируется из мира E1, дальнейшие изменения синтетические.
- Общий producer выдаёт одно уведомление на изменённую сущность с маской действий.
  Каждое седьмое уведомление содержит два разных бита. Это уже объединённые уведомления,
  а не модель нескольких отдельных occurrences одного действия в течение дня.
- Время включает routing, удаление повторов кандидатов, проверку условий и сортировку
  action/pulse-результатов по priority/EventId/subject. Producer, построение индекса,
  резервирование буферов, хеширование, сверка и аудит находятся вне таймера.

`naive` обходит все определения и сущности их области, но сразу отсекает неподходящие
on-action-маски и месячные слоты. Календарный день вычисляется один раз за тик;
29–31-го месячные определения пропускаются. **Количество выполненных предикатов
у `naive` и `indexed` одинаковое**: индекс экономит внешний перебор, а не проверки
заведомо допустимых кандидатов. Это сравнение с baseline, в котором уже есть ранний gate.

`indexed` идёт по уведомлениям и спискам `[scope][on-action]`, stamp-массив устраняет
повтор одного кандидата от двух битов. Месячные слоты перебираются напрямую.
`sampled` оставляет action-путь полным, а для месячного пульса выбирает сущность хешем
`(seed, month, scope, subject)` с вероятностью 10%; выбор общий для всех её pulse-определений.
Это воспроизводимая выборка, без MTTH, cooldown и компенсации вероятностей.

## Выборка пульсов и потеря полноты

Аудит первого повтора учитывает каждую пару (определение, сущность), которая хотя бы раз
прошла полный месячный пульс. Recall — доля этих различных пар, найденная выборкой
хотя бы раз за 365 дней. Количество pulse-hit в JSON — другая метрика: одна пара может
срабатывать много месяцев. Action-результат всех трёх методов остаётся одинаковым.

Задержка считается от первой полной квалификации до первого обнаружения выборкой,
только для найденных пар. Не найденные пары исключены из распределения задержки,
но показаны отдельным числом. Максимальная задержка найденных пар — 334 дня.
Условие может исчезать и появляться вновь; выборка не гарантирует доставку пропущенного
события. Нулевая медиана в плотных вариантах также не означает полной доставки.
Для 5 000 персонажей выборка сохраняет около 10% общего числа pulse-hit, но обнаруживает
лишь 18.15–48.63% различных подходящих пар за год.

Для важных событий нужен полный путь. Выборку можно рассматривать только для явно
допускающих её случайных пульсов, после отдельного определения игровой семантики,
калибровки MTTH и допустимой задержки; этот спайк такого решения не принимает.

## Проверка корректности и дальнейшая работа

На каждом тике всех девяти вариантов сравнивались точные action/pulse-векторы
`naive/indexed`; для `sampled` — точное равенство action и включение pulse в полный
результат. Потоки срабатываний совпали между повторами; хеши `naive/indexed` равны
в каждом варианте. Любое расхождение останавливает запуск. SHA-256 трёх измеренных
C++-исходников записаны в JSON вместе с параметрами и средними каждого повтора.

Целевые CTest-проверки `trigger_spike_unit` и `trigger_spike_cli` прошли на Windows
в Debug, Release и ASan: эквивалентность, области, несколько действий без дублей,
перестановка уведомлений, граница 28/29–31-го, воспроизводимая выборка и структура
реального CLI-отчёта. Порогов времени в CI нет.

Цена producer, полнота уведомлений и fan-out зависимостей ещё требуют замера в E11.
Здесь нет DSL/интерпретатора, эффектов, MTTH, cooldown, таймеров и общей очереди команд.
Параллельное исполнение и минимальный ПК не исследованы.
При 5 000 персонажей и 100% изменений даже индекс даёт mean 3.26 мс / p99 5.20 мс:
предложенный бюджет событий 1 мс в среднем / 3 мс в пике этим макетом не подтверждён.
Политика шторма событий и бюджетирование остаются задачей реального движка правил.

Схема подписок согласуется с ADR-0002 P5 и GDD событий; инструмент не меняет `World`,
PSV1/PSL1, golden-хеши или production-код симуляции. ADR остаётся предложенным до
остальных спайков и итогового E2-T09.
