# E2-T05 — способы публикации снапшотов для UI

Дата: 2026-11-07 (запуск 2026-11-06 17:12 UTC).
[Инструмент и воспроизведение](../../tools/snapshot_spike/README.md),
[исходные результаты JSON](E2-T05-results.json), задача #6.

## Решение

Для компактного числового представления карты/родов **начать с полной неизменяемой
копии UI-данных и atomic-публикации `shared_ptr`**. Прототипы диффов и двух банков
страниц остаются инструментами для будущего повторного сравнения при росте payload.
Это выбор простоты и достаточной абсолютной стоимости, **не доказательство, что
full — самый быстрый алгоритм**. Устойчивое ранжирование по этой матрице невозможно:
RSD ≤ 5% только у 6/42 micro-строк и 2/42 paced-строк; ни одна paced-пара методов
не имеет двух стабильных участников. Шумные результаты сохранены, повторных прогонов
ради ранжирования не было.

Полная копия UI-payload 16/48 КБ в paced-режиме заняла в среднем 3.83–14.34 мкс,
получение ссылки — 0.27–0.58 мкс. Самое большое одиночное publish full — 7.14 мс:
средние и p99 не являются гарантией верхней границы. Все методы сохранили точные
данные; фактическое чтение достигло 59.83–60.00 Гц. Это чтение числовых полей,
а не измерение готового кадра RmlUi/рендера.

**Полная копия UI-представления и `World::snapshot()` — разные объёмы.** Нынешний
`SimulationRunner` по-прежнему публикует `shared_ptr<const World>`; этот PR не меняет
его API или реализацию. Отдельный reference показывает стоимость полной копии мира:
mean 243–437 мкс на `year60`, 1 751–2 311 мкс на `year60x3`. Это контекст для будущего
выделения UI-представления, без коэффициента ускорения между разными payload.

## Данные и протокол

- Windows 11, i5-12400F, MSVC 19.44 / Build Tools 2022, Release, C++20.
  Producer закреплён за логическим CPU 0, UI — CPU 2; физическая топология не утверждается.
  Глобальные настройки частоты и timer resolution не менялись.
- `year60`: 400 провинций + 100 родов, 500 строк × 8 `uint32` = 16 000 байт.
  `year60x3`: 1 200 + 300, 1 500 строк = 48 000 байт. Мир-источник содержит соответственно
  5 000 / 15 000 персонажей; они не передаются в UI-payload этого эксперимента.
- Читатель в обоих размерах проходит восемь полей не более **400 провинций и 100 родов**,
  равномерно распределённых по всему источнику. Начальные поля частично взяты из E1,
  остальные — числовые заполнители; последующие изменения синтетические.
- 1/10/100% — доля изменённых **строк** за публикацию, ровно одно из восьми полей
  каждой выбранной строки. Это не 100% всех полей. Строки перемешаны, seed 7,
  имена PRNG-потоков `snapshot.fixture` / `snapshot.changes`.
- 14 сочетаний: два размера × три доли × две частоты 40/400 публикаций/с плюс два
  сценария удержания двух старых кадров. Порядок перемешан seed 20261107.
  Каждый CLI-процесс измеряет все три схемы, порядок меняется между повторами.
- Micro: 64 прогрева + 1 024 измеренных публикации, 3 повтора, один поток, одинаковые
  входы для трёх методов. Publish и acquire/apply измерены раздельно; checksum после
  таймеров. Прогретые субмикросекундные интервалы чувствительны к цене таймера.
- Paced: отдельные producer/UI-потоки, по 2 секунды × 3 повтора; UI целевые 60 Гц,
  без дополнительного прогрева. Локальные high-resolution waitable timers доступны
  во всех запусках; busy-wait нет. Опоздавшие deadlines не догоняются burst-циклом;
  фактические частоты и overruns сохранены. Неизменяемые Frame могут пережить transport.

Создание изменений, ожидаемого checksum и начальных структур исключено из publish;
в paced они входят в реальную нагрузку производителя. Publish включает выделение,
копирование, синхронизацию и освобождение сменяемого состояния. Acquire включает
применение диффов, read — фактическое чтение с checksum. Atomic-счётчики памяти
включены во время всех прототипов. P95/p99 — nearest-rank, RSD по средним publish
трёх повторов. Нагрузка ОС, частоты и причины большого разброса отдельно не исследованы.

## Три схемы и их ограничения

1. `full`: новая полная Data + atomic `shared_ptr` store/load; старое состояние живёт,
   пока читатель держит ссылку. Atomic shared_ptr не объявляется lock-free.
2. `diff`: неизменяемые пакеты `(row, field, value)`, короткий mutex для передачи;
   UI применяет их вне mutex к своему cache. Удержанный старый Frame требует копии
   cache. Pending-очередь максимум 64 пакета, отдельный UI-batch тоже максимум 64;
   переполнение pending заменяет цепочку полной контрольной копией под mutex.
3. `pages`: два банка страниц по 128 строк / 4 КиБ данных + immutable directory.
   Версия каждой страницы сравнивается с источником: обновляются все устаревшие
   страницы заднего банка, включая изменения прошлых публикаций. Удержанный читателем
   блок копируется (COW), свободный используется повторно. Два банка не означают
   фиксированный расход ровно двух копий при произвольном удержании читателями.

Все методы имеют latest-state семантику. Full/pages заменяют промежуточные версии;
diff может объединять много обновлений до следующего кадра, сохраняя правильную базу.
Это не очередь событий с обязательной доставкой каждой версии. При произвольном
удержании старых Frame расход памяти всех трёх схем может расти.

служебные capacity очередей/банков, исходный мир и массивы замеров. Счётчики
копирования описывают байты полей, а не измеренный DRAM-трафик.
`serialized_world_bytes` (158 940 / 476 540) также не является оценкой heap мира:
индексы и capacity в памяти имеют другую раскладку.

## Проверки и применение решения

Целевые `snapshot_spike_unit` и `snapshot_spike_cli` прошли на Windows в Debug,
Release и ASan. Проверены все поля, пропуск >64 версий и checkpoint, отставший задний
банк, удержание старого Frame после уничтожения transport, конкурентное чтение
монотонных полных версий и структура реального CLI JSON. В каждом эксперименте
checksum кадра сверяется с его версией, финально сравниваются все поля источника;
ошибка останавливает матрицу. Все 14 вариантов завершились корректно.

Для дальнейшего UI-моста базовая схема — компактное представление под запросы UI,
полная immutable-копия при новой публикации и ограничение частоты публикаций, как
у нынешнего runner. Извлечение представления из World, именованные строки, динамическое
создание/удаление сущностей, переменный размер строк и выборки персонажного окна не
измерены. Нужен отдельный замер при их появлении, прежде чем переносить эти числа
на готовую игру. Произвольные persistent-деревья не исследовались.

Production-переход с `World` на UI-представление требует отдельной интеграции;
здесь изменены только инструмент и факты ADR-0002. Golden-хеши, формат World/сейвов
и поведение симуляции не меняются. Общий ADR остаётся предложенным до E2-T09.
