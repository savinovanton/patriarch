# ADR-0006: Хранение людей: идентичность, архив, расписание жизненных событий, схема сохранения

- Статус: **принято**
- Дата: 2026-11-07
- Связано: E7 (#40, задача E7-T01 #157; потребители — T02…T24), E9-T03, E10, E14, E17 (ссылки на `CharacterId`); FR-DYN-7, FR-SAVE-1, NFR-PERF-2/3/5/6, NFR-DET-1; ADR-0001 (команды, снапшоты), ADR-0002 (P1 лимиты и LOD, P2 тик по частотам, P4 SoA, P8 измерения); GDD 01 §2.1, §3, §12, §13.3

## Контекст

### Что есть в коде сейчас (факты на 2026-11-07)

- `CharacterTable` — пять колонок (`dynasty`, `birth_date`, `sex`, `health`, `father`, `mother` плюс `EntityTable`) и **LIFO-переиспользование слотов**: `destroy_character` кладёт индекс в свободный список, следующий `create_character` берёт его (`entity_table.hpp`). Команда `KillCharacter` (тег 3) именно уничтожает запись; демо-системы на этом построены.
- Индекс «члены рода» — по `SparseSet<CharacterId>` **на каждый род**; разреженный массив каждого набора растёт до **наибольшего id** (`sparse_set.hpp`: «память пропорциональна наибольшему ключу»).
- Месячный и годовой разнос — по `id` (`is_monthly_slot`: `id % 28`; `is_yearly_slot`: `id % 365 == day_of_year`).
- Сейв: контейнер `PSV1` (`kSaveFormatVersion = 1`) + полезная нагрузка `World::save_state` (схема `kStateSchema = 1`, плотный дамп таблиц) + отложенные внутренние команды. Миграции пока нет: `migrate_to_current` пропускает только версию 1.
- Хеш: `WorldHash` = `total` + пять частей (`calendar`, `rng`, `dynasties`, `provinces`, `characters`), `total` — FNV-1a от пяти частей. Реплей `PRP1` хранит эти шесть чисел на каждой контрольной точке.
- `CommandType` — стабильные теги 1…5, а `type_of()` вычисляет тег как `индекс альтернативы variant + 1`, то есть теги нельзя «резервировать с пропусками».
- `CommandLog` — неограниченный `std::vector`, в него попадает каждая применённая команда.
- Золотые значения демо (`tests/golden_test.cpp`): шесть значений хеша, хеш байтов реплея, хеш байтов `save_state`. Линуксовый CI-job проверки детерминизма (#31) требует, чтобы всё новое было платформенно-независимым.

### Требования

- Ссылка на человека должна оставаться верной **всю партию**: на умершего ссылаются родство, летопись, должности, схемы (E10/E14) и древо рода (FR-DYN-7, US-7.3).
- ≤ 5 000 живых персонажей (NFR-PERF-5) и порядка 20 000 умерших за партию (≈ 125 смертей в год × 70–80 лет + стартовое население; считаем с запасом ×1.5); память людей ≤ 10 МБ [предл.] (бюджет эпика E7 §6), общий потолок партии 1.5 ГБ.
- Нагрузка на тик не должна расти с размером архива (NFR-PERF-3, «год 1 → год 60» ≤ 2×).
- Демография считается по расписанию (ADR-0002 P2), а не «всё каждый день».
- Детерминизм: порядок обработки не зависит от истории вставок, адресов, платформы (`code-style.md` §4).
- Сейвы версионированы, миграции проверяются, счётчики и id из файла не доверенные (FR-SAVE-1).
- Демо-сценарий заморожен: пять частей хеша и `total` не меняются (эпик E7 §3 строка 2).

### Что показал разбор основы

1. **Переиспользование id ломает ссылки.** После `destroy_character` тот же `CharacterId` обозначает другого человека; `father`/`mother` родившихся ранее детей начинают указывать на чужого. Для архива и летописи это недопустимо.
2. **Отказ от переиспользования ломает память индекса родов.** Если id растут монотонно до числа «когда-либо рождённых», то `SparseSet` на каждый род занимает `4 Б × max_id`: 100 родов × 25 000 id = **10 МБ**, для профиля `year60x3` (300 родов × 75 000 id) — **90 МБ**. Один только индекс съел бы весь бюджет людей. Это следствие решения D1, и оно решается в D2.
3. **Штаффель `id % 365` привязывает бросок к id, а не к человеку.** Бросок попадает в произвольный день относительно дня рождения: (а) возрастная корзина берётся с размытием до года (кому 60 исполнится в декабре, в январе бросает как 59-летний); (б) первый бросок новорождённого приходится на случайный день его первого года (0…364), то есть вся корзина «0 лет» (220 ‰) применяется одним броском в этот момент; (в) нет момента «исполнилось N лет», который всё равно нужен для совершеннолетия (16 лет), UI и событий. Эпик (§3 строка 4) называл это «пропуском корзины»; точнее — корзина не теряется, а привязывается к случайному моменту и смещает годовую функцию выживания, при этом (в) заставляет иметь расписание по датам в любом случае.
4. **Хеш растёт вместе с архивом.** FNV-1a побайтово стоит ≈ 1 нс/Б (измерено, ниже): честный пересчёт хеша 20 000 архивных строк ≈ 2 мс — это весь бюджет `compute_hash` (≤ 2 мс на 25 000 строк).
5. **Любая новая часть хеша или раздел сейва, добавленные безусловно, меняют золотые значения демо и конфликтуют между параллельными PR.** E9-T03 уже запланировал для `economy` правило «часть = 0 и вне `total`, если данных нет»; это правило нужно сделать общим.
6. **`CommandType` нельзя резервировать блоками**, пока тег = индекс `variant` + 1; E7 и E9 в своих документах оба берут «следующие теги 6, 7, …».

## D1. Идентичность и id

### Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Одна таблица, id = индекс строки навсегда; умершие остаются строками; список живых** | Ссылки верны навсегда; прямой доступ `колонка[id]` везде, как сейчас; нет косвенности; минимальная правка кода и соседних эпиков; архивная запись ищется за O(1) без поиска | Память растёт с числом когда-либо рождённых (≈ 150 Б/id); нужен список живых и новый индекс родов (D2) |
| B. Две таблицы: живые (плотная, свой слот) + `ArchiveTable`, `id → слот` через массив | Живая часть компактна (0.7 МБ), архив 68 Б/запись; суммарно −40% памяти | Каждое обращение идёт через `slot_of(id)` (все `characters().x[id.index()]` в коде, тестах, UI-мосте, команд-валидаторах переписываются); при переводе в архив строки двигаются (swap-remove меняет порядок → порядок сейва/хеша надо канонизировать отдельно); два хранилища и два набора инвариантов |
| C. Переиспользование слотов + поколенческие хэндлы (`id` 64 бита) | Устаревшая ссылка обнаруживается | Умершему всё равно нужна запись (родство/летопись) с ключом `(индекс, поколение)` — то есть тот же архив; id удваиваются во всех таблицах E10/E14/E17 и в командах; хеш и сейв меняются |
| D. Умершие остаются полными строками без сброса группы S | Проще всего | Мёртвые навыки/черты в хеше и сейве; риск, что система обработает умершего; расходы на сохранение |

### Решение

**Вариант A.** Расчёт (подробности — раздел «Расчёты»): при 5 000 живых и 20 000 умерших A занимает ≈ 3.7 МБ против ≈ 2.2 МБ у B (разница 1.5 МБ ≈ 0.1% потолка партии 1.5 ГБ, 15% бюджета людей); при профиле ×3 (15 000 + 60 000) — 11.2 против 6.6 МБ. Стоимость обхода живых от архива не зависит (список живых), поиск архивной записи — O(1) по прямому индексу, косвенность B стоит на порядок меньше, чем имеет значение (0.64 против 0.33 нс на обращение, измерено). Выигрыш B — 1.5 МБ, цена — переписывание всех обращений и новый класс ошибок «индекс слота устарел». Условия пересмотра — в «Последствиях».

Правила режима династии:

1. `CharacterId` — `u32`, выдаётся строго по возрастанию (`id = capacity`), **никогда не переиспользуется и не перенумеровывается** (ни при сохранении, ни при «сборке мусора»). Жёсткий предел `kMaxCharacterIds = 1 048 576` (≈ 150 МБ худший случай); `CreatePerson`/`Birth` сверх предела отклоняются, загрузчик проверяет `capacity ≤ kMaxCharacterIds`.
2. Состояние строки — три значения в байте `alive_flags` таблицы слотов: `0` — свободен (только режим E1), `1` — жив, `2` — архивный (retired). `World::is_alive(id)` истинно только для `1`; новый `World::exists(id)` — строка существует (жив или архивный).
3. В режиме династии `destroy_character` запрещён (`PAT_ASSERT` + `false`), свободный список всегда пуст (загрузчик отвергает иное).
4. Режим включается одним вызовом `World::enable_dynasty_mode()` сценарием (предусловие: свободный список пуст). Флаг пишется в сейв (`world_flags`, D6) и хешируется (часть `mode`, D7). Мир, в котором режим не включён, ведёт себя **бит-в-бит как в E1** (демо, тесты E1): переиспользование слотов, `KillCharacter`, пять частей хеша, прежние байты.
5. «Режим E1» — наследие ради замороженных golden; его удаление — отдельное решение после M1 (когда демо заменит сценарий E4-T10).

### Ссылки на умерших (кто что может хранить)

| Тип ссылки | На умершего допустимо? | Кто чистит |
|---|---|---|
| `father`, `mother`, дети (производный список), `spouse` (последний), `ex_spouses`, `godparent` | да, навсегда | не чистится: это факты для древа |
| Участники записей летописи | да | не чистится |
| Члены рода (`members_`), глава рода | **нет** | `Die.apply` сразу |
| Собственные разреженные данные умершего (мнения, беременность, претензии, образование, `planned_death`) | освобождаются | `Die.apply` сразу |
| Ссылки живых **на** умершего в чужих разреженных данных (мнения о нём, наставник) | допустимы временно | лениво: месячный проход затухания/проверок удаляет; `check_invariants` разрешает именно эту группу |
| Должности, регентство, армии, схемы, договоры (E8/E10/E14/E17), администраторы провинций (E9) | **нет** | эти эпики реагируют на применённую `Die` из журнала тика и добавляют проверки в свой `check_invariants` (контракт — «Реализация S3» ниже) |
| Записи очереди расписания | допустимы (устаревшие) | отбрасываются при извлечении |

Поскольку id не переиспользуются, устаревшая запись очереди или лениво хранимая ссылка всегда однозначно указывает на **того же** умершего: никаких «чужих» срабатываний.

## D2. Раскладка живой таблицы (SoA)

Колонки хранятся отдельными `std::vector` «по id» (длина = `capacity`). Каждой колонке назначена группа:

- **K** — «переживает смерть»: идентичность и факты для древа/летописи; в архивной строке остаётся как есть;
- **S** — «состояние живого»: при `Die` сбрасывается в значение по умолчанию (сброс — часть `Die.apply`; инвариант: у архивной строки вся группа S равна умолчанию).

| Колонка | Тип | Б | Гр. | Задача |
|---|---|---:|:-:|---|
| `alive`, `generation` (из `EntityTable`) | `u8`, `u32` | 5 | K | E1 (поколение в режиме династии не растёт) |
| `dynasty`, `birth_date`, `sex`, `father`, `mother` | `u32`, `i32`, `u8`, `u32`, `u32` | 17 | K | E1 |
| `health` | `Fixed32` | 4 | S | E1 |
| `name`, `branch`, `portrait` | `StringId`, `u32`, `u16` | 10 | K | T02 |
| `legitimacy`, `cause_of_death` | `u8`, `u8` | 2 | K | T02 (причина — T04) |
| `death_date` | `Date`; «нет» = `INT32_MIN` | 4 | K | T02 (заполняет T04) |
| `skills[5]` | `Fixed32` 0…20 | 20 | S | T02 |
| `fertility`, `stress`, `piety` | `Fixed32` 0…100 | 12 | S | T02 |
| `ambition`, `loyalty_head`, `loyalty_emperor` | `Fixed32` −100…100 | 12 | S | T02 |
| `traits[8]` | `u16`, отсортированы, 0 = пусто | 16 | S | T02 (решение эпика §3 стр. 10) |
| `education {focus, tutor, level}` | `u8`, `u32`, `u8` (отдельные колонки) | 6 | S | T02 |
| `planned_death` | `Date`; «нет» = `INT32_MIN` | 4 | S | T02 (использует T10, D4) |
| `spouse`, `marriages`, `ex_spouses[3]`, `godparent[2]` | `u32`, `u8`, `u32×3`, `u32×2` | 25 | K | T03 (`godparent` зарезервирован по умолчанию варианта A вопроса ❓3 / #135) |
| `first_child`, `next_sibling` | `u32` | 8 | K | T03, **производные** (не сохраняются) |
| `member_pos` (позиция в списке рода) | `u32` | 4 | K | T04, производный |
| **Итого на id** |  | **149** |  | K = 75 Б, S = 74 Б |

Разреженные данные вне таблицы (по ключу `CharacterId`, в порядке возрастания ключа): беременности (T12), мнения ≤ 30 на персонажа (T17), летопись по родам (T16), претензии (E12). Они освобождаются при `Die`.

**Что «горячее».** Строго горячих колонок нет: на 5 000 живых за день трогается ≈ 16 человек (дни рождения) и ≈ 180 (месячный слот `id % 28`). Раскладка выбирается не по плотности кэша, а по трём практическим причинам: (1) группа S сбрасывается целиком и сравнивается с умолчанием одной операцией; (2) группы сохраняются разными разделами сейва (D6); (3) hot-путь «обойти живых» вообще не читает колонки мёртвых. Внутри колонки данные, читаемые вместе, лежат рядом (`skills` — массив из 5 `Fixed32` как один элемент колонки; `traits` — массив из 8 `u16`).

**Производные индексы** (строятся при загрузке функцией `rebuild_derived_indexes()`, **не сохраняются и не хешируются**, сверяются в `check_invariants`):

| Индекс | Что это | Порядок |
|---|---|---|
| `living_` | вектор живых id | **строго по возрастанию id**: новый id всегда больше → `push_back`; смерть → `erase(lower_bound)` (≈ 0.5 мкс на 5 000) |
| `first_child`/`next_sibling` | связные списки детей | по `(birth_date, id)` — канонический порядок, не зависящий от истории вставок |
| `member_pos` | позиция персонажа в списке своего рода | см. ниже |
| `life_queue_` | очередь расписания (D4) | см. D4 |
| накопитель хеша архива | см. D7 | — |

**Индекс членов рода.** `members_` (списки по родам) сохраняется и хешируется в части `dynasties` в порядке «вставка — в конец, удаление — swap с последним» — этот порядок заморожен. Меняется только реализация (T04): вместо `SparseSet` на род — `std::vector<CharacterId>` на род + **один** массив `member_pos` по id. Семантика и байты порядка те же (тест: хеш `dynasties` демо не меняется), память `4 Б × (id + члены)` вместо `4 Б × max_id × число родов` (устраняет проблему 2). Ограничение в `stressgen` («`dynasties × (characters + provinces) ≤ 64 млн`») после этого снимается.

## D3. Архив

`Die{character, cause}` в режиме династии делает атомарно (всё в `apply`, окна несогласованности нет):

1. `death_date = today`, `cause_of_death = cause`; факт «смерть» пишется в летопись рода (фактические события — рождение, смерть, смена главы, вымирание — записывают сами применяющие функции, чтобы они не расходились; редакционные записи — команда `RecordChronicle`);
2. удаление из `members_` и `living_`, сброс `head` рода (преемника выбирает система T15 на следующем тике — как демо-`SuccessionSystem`);
3. супруг(а): `spouse` живого партнёра очищается, умерший заносится в его `ex_spouses`, счётчик браков не меняется (овдовение — эффект `Die`, а не отдельная команда);
4. сброс группы S в умолчание; освобождение собственных разреженных данных (мнения, беременность — ребёнок теряется, `planned_death`, образование);
5. `ids.retire(id)`: флаг `1 → 2`, id в свободный список **не попадает**; `alive_count` уменьшается.

Остальное — лениво (см. таблицу ссылок в D1). После `Die` строка **неизменяема**: у `World` нет мутаторов для архивных строк (`PAT_ASSERT`), поэтому накопитель хеша архива (D7) корректен.

**Доступ к умершим — только значением:** `World::archived(id) → ArchivedPerson` (имя, род, ветвь, даты, причина, родители, дети, супруги — копия полей группы K). Ссылки на колонки для архивных строк наружу не выдаются. Это позволяет позже уплотнить хранилище (вынести группу K старых умерших в упакованные блоки) **без смены API, формата id и сейва**.

`EntityTable` получает `retire(id)`, `retired_count()`, значение флага `2` в `restore()`; `alive_count()` считает только флаг `1`; `hash_table_slots` хеширует байты флагов как раньше (для демо — те же 0/1, часть `characters` не меняется); пропуск «неживых» строк при хешировании части `characters` меняется с `== 0` на `!= 1`.

## D4. Расписание жизненных событий

### Варианты

| Вариант | Стоимость в день (измерено/оценено) | Плюсы | Минусы |
|---|---|---|---|
| A. Штаффель `id % 365` (`is_yearly_slot`) | обход 25 000 строк ≈ 57 мкс, по списку живых ≈ 6 мкс | Ничего не хранит | Проблема 3 (размытие корзин, случайный момент первого броска, нет «исполнилось N лет») |
| B. Календарное колесо: список живых на каждый день года, обрабатывается список «сегодня» | ≈ 0 + сортировка дня | Просто для периодических событий | Для разовых событий (плановая смерть, роды) всё равно нужна очередь → два механизма |
| **C. `ScheduledQueue` как производный индекс; события выводятся из колонок** | **≈ 1.5 мкс** (6 000 записей, ≈ 16 событий в день, с сортировкой и перепланированием) | Один механизм для дней рождения, плановых смертей, родов, совершеннолетия; контейнер можно заменить (например, на колесо B) без смены формата; готовый протестированный класс | Нужна пересборка при загрузке и сверка в `check_invariants` |
| D. Колонка `next_event` и скан по ней | 57 мкс/день и растёт с архивом | — | Нарушает правило ADR-0002 P8 («каждый день по всем») |

### Решение: вариант C

**Первичные данные лежат в колонках и таблицах, очередь — только индекс над ними.** Очередь не сохраняется и не хешируется (хеш покрывает колонки), после загрузки она пересобирается `rebuild_life_queue()`; в `check_invariants` проверяется, что очередь равна пересборке (с допуском на устаревшие записи неживых). Поэтому:

- формат сейва не зависит от структуры очереди (кучу можно заменить на колесо в T20 без миграции);
- «загруженный» и «непрерывный» мир не различаются ни хешем, ни поведением;
- нечего «портить» в файле: допустимого рассогласования очереди с колонками просто нет.

**Виды записей** (поле `kind`, он же приоритет внутри дня):

| kind | Что | Откуда выводится | Кто обрабатывает |
|---|---|---|---|
| 1 `Birthday` | следующая годовщина `birth_date` после последней обработанной даты | колонка `birth_date` у живого | T10: бросок смертности на предстоящий год, T13: совершеннолетие в 16 лет, возрастные пороги |
| 2 `PlannedDeath` | `planned_death` | колонка `planned_death` | T10: команда `Die` с причиной по контексту |
| 3 `Labour` | `due` беременности | таблица беременностей (T12) | T12: исход родов (`Birth`/мёртворождение, риск матери) |

**Алгоритм дня** (система `dynasty.life`, `Cadence::Daily`, T10):

1. `World::take_due_life_events(today, scratch)` вынимает из очереди все записи `due ≤ today` (через `pop_due`), **отбрасывает устаревшие** (человек не жив; `planned_death` уже изменён; беременности нет), сразу **перепланирует `Birthday`** на следующую годовщину (строго после обработанной) и возвращает остальное **отсортированным по `(due, kind, id)`**.
2. Система обходит список и принимает решения: `Birthday` → бросок смертности и, если человек «умирает в этом году», команда `PlanDeath{id, date}`; `PlannedDeath` → `Die`; `Labour` → `Birth`/`Die`. Эффекты — внутренние команды (применяются в начале следующего тика).

**Порядок внутри дня — функция состояния, а не истории.** `ScheduledQueue` упорядочивает по `(due, sequence)`, а `sequence` — это порядок вставки; чтобы результат (а значит, и порядок извлечений ГСЧ) не зависел от того, как и когда записи вставлялись, система **не использует порядок `pop_due`**: она собирает всё, что пришло в этот день, и сортирует по явному ключу `(due, kind, id)`. Номера `sequence` остаются внутренностью кучи. Класс `ScheduledQueue` менять не нужно. Правило: записи с `due < today` (например, после длинной паузы) идут раньше записей дня.

**Бросок смертности на день рождения.** Исполняется `k` лет → бросается корзина возраста `k` на предстоящий год `[k, k+1)`; новорождённый получает запись `Birthday` со `due = birth_date`, поэтому корзина «0 лет» (220 ‰) бросается сразу при рождении, а дата смерти распределена по первому году. Если «умирает в этом году», дата смерти = день рождения + равномерное смещение 0…364 (смещение < длины года 365/366, поэтому в году не бывает двух плановых смертей). Ровно **две** выборки из `demography.mortality` на каждый бросок (сравнение с вероятностью и смещение) — **всегда обе**, независимо от ветки (правило эпика §3 стр. 8). Следствия: смерть наступает в реальную дату, а не всегда в день рождения; плановая смерть хранится в колонке и **может быть изменена событиями** (E11: «лечение» отменяет её командой `PlanDeath` с пустой датой) — это не скрытое состояние, оно сохраняется, хешируется и воспроизводится.

**Тонкости календаря.**
- Юлианский високосный год — каждый четвёртый (`Date::is_leap_year`), 1700-й високосный.
- День рождения 29 февраля в невисокосные годы приходится на **28 февраля**. Возраст на дату `d` = число годовщин `≤ d`, считается той же функцией, что и расписание (`age_years`, `next_anniversary_after`, `anniversary_in_year` в `date.hpp`, T02), чтобы возраст и расписание не расходились. Тест: рождённый 29.02.1704 получает по одной обработке в каждом году, в 1705 — 28 февраля.
- Начальное население сценария (создаётся до первого тика) получает первую запись `Birthday` на ближайшую годовщину `≥ today`; экспозицию текущего возрастного года до неё учитывает помощник сценария дробным броском (промилле × оставшиеся дни / 365) — иначе стартовый состав бессмертен до своих дней рождения (T10/T18).
- Месячные расчёты (здоровье, стресс, зачатие) остаются на `is_monthly_slot(id)` по `living_` (≈ 6 мкс в день на 5 000 живых); роды — запись `Labour`; образование — помесячный прогресс; совершеннолетие — внутри обработки `Birthday` в 16 лет.

Правка GDD 01 §3 («Старение и смертность — … в день рождения»): уточнены корзина «на предстоящий год», дата смерти внутри года, 29 февраля; правка внесена этим PR.

### Что — команда, что — прямое изменение

Журнал команд неограничен (`CommandLog` — вектор), поэтому E7 разделяет изменения по критерию **значимости**:

- **Команда** — значимое, наблюдаемое другими системами/UI/летописью событие: смерть, рождение, брак, образование, совершеннолетие, черта, плановая смерть, изменение единства, запись летописи. Оценка объёма E7 ≈ 1 000 команд в год — пренебрежимо.
- **Прямое изменение через API `World` внутри владеющей системы** (с ограничением диапазонов): помесячный дрейф здоровья/стресса/плодовитости (5 000 человек в месяц), затухание мнений. `PRP1` **не меняется**: реплей хранит только внешние команды и шесть чисел хеша на контрольной точке; `total` включает непустые расширенные части (D7), поэтому расхождение любых данных E7 видно на контрольной точке, а имя расходящейся расширенной части диагностируется инструментом (`simcli`) повторным пересчётом. `play_replay` сравнивает с контрольной точкой **только записанные в файле поля** (`total` + пять частей); `operator==` для `WorldHash` с массивом `ext` для этого не годится, и T02 вводит отдельное сравнение. Внутренние команды (`Die`, `Birth`, …) в реплей не пишутся — системы порождают их заново. Старые реплеи демо остаются валидными, пока не изменился сценарий (`scenario_id`).

## D6. Схема сохранения

### Контейнер и место миграции

- Контейнер `PSV1` и `kSaveFormatVersion = 1` **не меняются**: заголовок, zstd, хеш полезной нагрузки, отложенные внутренние команды — как сейчас. `migrate_to_current` на уровне контейнера остаётся для преобразований байтов целиком и в этой работе не используется.
- **Миграция схемы мира живёт в `World::load_state`**, который читает любую схему из диапазона `[1, kStateSchema]` и приводит мир к текущему виду типизированными шагами над уже загруженным миром (а не преобразованием байтов). Схема новее текущей — ошибка «сохранение создано более новой версией».
- Диапазон поддержки начинается с 1 и не сужается в M1.

### Раскладка полезной нагрузки (схема ≥ 2)

```
u32 schema
[ тело ядра — ровно как в схеме 1: часы, ГСЧ, роды+списки членов и владений, провинции,
  таблица слотов персонажей + запись v1 на каждый слот ]
--- блок расширения (схема ≥ 2) ---
u32 world_flags          бит 0 = режим династии; остальные биты 0, иначе ошибка
u16 section_count        ≤ 32
section_count × { u16 id (строго по возрастанию) | u16 version | u32 byte_length | байты раздела }
[ отложенные внутренние команды — как в схеме 1 ]
```

Правила читателя: каждый раздел читается отдельным `ByteReader` на `byte_length` байт, обязан быть **израсходован полностью**; неизвестный `id`, неподдерживаемая `version`, раздел, чья минимальная схема больше схемы файла, нарушение порядка — ошибки (не падения). Отсутствие раздела = состояние по умолчанию. **Пустое не пишется**: раздел опускается, если его содержимое равно умолчанию; плотные колонки пишутся **разреженно** — только строки, отличные от умолчания, по возрастанию `id` (`u32 id` + поля).

Границы и недоверие (для каждого счётчика и ссылки из файла, как в `world_io.cpp`): `plausible(count, bytes_each)` до выделения памяти; `id < capacity`; ссылки на персонажей/роды/ветви в диапазоне; перечисления — известные значения; `Fixed` в диапазонах колонок; `traits` отсортированы, без повторов, нули в конце; `planned_death`/`death_date` либо «нет», либо разумная дата; для строк с флагом «жив» не допускается `death_date`, для архивных — обязателен; свободный список в режиме династии пуст; флаг `2` допустим только в режиме династии. После чтения — `rebuild_derived_indexes()` и `check_invariants()`; непустой отчёт = ошибка загрузки.

**Реализация S1 (E7-T02, схема 2) — что уточнено при реализации.** Это не меняет решений ADR, а фиксирует детали, которых в нём не было:

- Колонки — по таблице D2. Для рода: `unity` (по умолчанию 50 [предл.], 0…100) и `succession_law` (`Majorat` по умолчанию; `Minorat`, `Partition`, `FamilyCouncil`, `Appointment`). `BranchTable` в T02 — только `{name, dynasty}` (ветви не уничтожаются; поле «старший ветви» добавит T15 в разделе 2 версии 2 вместе с логикой выбора). Образование: `focus` 0 = нет, 1…5 = навык + 1; `level` 0…100 [предл.]; наставник — любая существующая строка таблицы.
- Все значения по умолчанию — нули/«нет»; `unity` — исключение (50), поэтому раздел `dynasty` не пишется только у мира, где все роды на умолчаниях и нет ветвей.
- Раздел 1 `person`: `u32 rows` и строки по 90 байт (`id`, `name`, `branch`, `portrait`, `legitimacy`, `cause_of_death`, `death_date`, 5 навыков, 6 шкал, 8 черт, образование, `planned_death`), только отличающиеся от умолчания, по возрастанию `id`. Раздел 2 `dynasty`: `u32 rows` × `{id, unity, law}` (9 байт), затем `u32 branches` × `{name, dynasty}`. Точная раскладка — комментарий в начале `src/sim/world_io.cpp`.
- Ссылки на ветви проверяются после чтения обоих разделов (`check_invariants`: ветвь существует и принадлежит роду персонажа); `set_character_dynasty` сбрасывает ветвь при смене рода.
- Очередь расписания: в T02 в ней только `Birthday` и `PlannedDeath` (`Labour` — T12). Запись `Birthday` при создании — по правилу D4 (новорождённый — `birth_date`, остальные — ближайшая годовщина ≥ сегодня); пересборка после загрузки — первая годовщина **строго после** сегодня (состояние на границе тика: всё до сегодняшнего дня обработано). Поскольку потребителя очереди ещё нет (`take_due_life_events` — T10), `check_invariants` в T02 проверяет **структуру**, а не точное равенство пересборке: ровно одна запись `Birthday` на живого в режиме династии, дата — годовщина рождения и не позже пересборочной, плановая смерть поставлена в очередь, записи неживых и устаревшие записи `PlannedDeath` допускаются, вне режима династии очередь пуста. T10 ужесточает проверку до равенства.
- `EntityTable` получила состояние слота `2` (`retire`, `retired_count`, `restore` его принимает), но `World` пока отвергает архивные строки («не поддерживается до E7-T04»): сама семантика архива (`Die`, сброс группы S, накопитель хеша `archive`) — T04, поэтому ни формат, ни `check_invariants` не обещают её раньше. `exists(CharacterId)` была добавлена уже в T02 (строка существует — жива или архивная), `ArchivedPerson` и `archived_person` пришли в T04 (см. «Реализация S3»).
- Теги команд — явная таблица в `command.cpp` (`CommandTag<…>`, `static_assert` на уникальность и ненулевое значение); в T02 добавлена `CreatePerson` (тег 9). `KillCharacter` в режиме династии отклоняется (`InvalidState`).
- `PRP1` не менялся. `play_replay` сравнивает `total` и пять частей (`WorldHash::same_recorded_parts`); при расхождении, видимом только в `total`, отчёт сообщает «extended parts (one of: …)» со списком используемых расширенных частей — назвать часть точно по файлу нельзя, это делает повторный пересчёт.
- `tools/stressgen` строит миры в режиме династии с правдоподобными значениями новых колонок (отдельный поток ГСЧ `stress.persons`, прежние потоки не сдвинуты).

**Реализация S2 (E7-T03, схема 3) — что уточнено при реализации.**

- Колонки группы K: `spouse` (`CharacterId`), `marriages` (`u8`), `ex_spouses[3]`, `godparent[2]` (зарезервировано по умолчанию варианта A вопроса ❓3 / #135: колонка есть, сохраняется и хешируется, пишет в неё только `World::set_character_godparents`, которым пока никто не пользуется). Раздел `kin` (id 3, версия 1, схема ≥ 3): `u32 rows`, затем только строки не по умолчанию, по возрастанию `id`: `u32 id | u32 spouse | u8 marriages | 3×u32 ex | 2×u32 godparent` (29 байт). Родители — прежние `father`/`mother` тела ядра, дети — производные.
- **Брак живёт на обоих партнёрах и заканчивается симметрично.** Любое окончание (расторжение, пострижение, смерть) очищает `spouse` у обоих и вносит каждого в `ex_spouses` другого в порядке окончания; у умершего запись о вдове/вдовце остаётся в его `ex_spouses`. Это уточняет строку D1 («`spouse` (последний)» остаётся на умершем): так инвариант «супруг симметричен» верен для всех живых, а дерево рода хранит все браки. `Die` (T04) вызывает `World::end_marriage(умирающий)` до перевода в архив; отдельной команды овдовения нет. Команды: `Marry{a, b}` (тег 7), `EndMarriage{a, reason}` (тег 8, причины `Annulment`, `Tonsure`) — только система, только режим династии.
- **Не более трёх браков** (GDD 01 §7.3) — жёсткий предел примитива (`kMaxMarriages`), он же ограничивает `ex_spouses`: ни один брак не теряется. Те же двое повторно не женятся. Пол, возраст, степень родства, согласие Церкви — правила E8, примитив их не проверяет.
- **Списки детей — по два звена на ребёнка, а не одно.** Ребёнок состоит в списке отца и в списке матери, поэтому колонок три (`first_child`, `next_by_father`, `next_by_mother`), 12 Б вместо 8 Б на id; `vector<vector<…>>` нет. Список ведёт тот, чей пол задаёт роль (мужчина — детей-отцовство, женщина — материнство), поэтому однозначно. Порядок — `(birth_date, id)`, старший первым; строятся инкрементально при создании и пересобираются сортировкой за O(n log n) в `rebuild_derived_indexes()`; тест сверяет оба пути.
- **Списки и родство существуют только в режиме династии.** В режиме E1 id мёртвых переиспользуются, поэтому ссылки не сохраняют смысла; там списков нет, запросы пусты, а `Marry`/`EndMarriage` отклоняются (`InvalidState`). `enable_dynasty_mode()` теперь отказывает (`false`), если у живого есть родитель, который не мог бы им быть. В режиме династии `create_character` обнуляет невозможного родителя (не существует, не тот пол, не старше ребёнка); команды `CreateCharacter`/`CreatePerson` в этом режиме отклоняют такого родителя (`InvalidArgument`). Демо (E1) не затронуто.
- Инварианты (`check_invariants`, GDD 01 §13.3): нет циклов (всегда, итеративный обход), отец — мужчина, мать — женщина, ребёнок строго младше родителей, брак симметричен и счётчик не меньше числа партнёров, бывшие супруги упакованы, без повторов, взаимны, `godparent` существуют и различны, списки детей равны ровно допустимым связям. Данные родства вне режима династии — ошибка. Загрузчик проверяет `id`/ссылки по границам таблицы, счётчик браков и порядок строк; остальное проверяет `check_invariants`.
- **Хеш:** отдельная часть `ExtPart::Kinship = 7` (а не внутри `character_ext`, как предполагал шаг S2): пуста (0) и вне `total`, пока ни у кого нет браков/крёстных. Поэтому все шесть значений демо и `kExpectedSaveBytesHash` не изменились. Легитимность остаётся колонкой человека (решение ❓1 / #133, T02); для рождений `kin::inherited_branch` даёт ветвь по умолчанию, а саму легитимность задаёт создатель (`Birth`, T12).
- Запросы `pat/sim/kinship.hpp`: `children_of`, `child_count`, `siblings_of`, `ancestors_of`, `descendants_of`, `is_ancestor_of`; порядок в заголовке: «старший первым» и по поколениям (отец раньше матери; старший ребёнок раньше), каждый человек один раз.
- Фикстура схемы 2 (`tests/data/saves/dynasty_v2.psv`, сделана `stressgen` кодом T02) читается и сохраняется в те же байты, кроме слова схемы.

**Реализация S3 (E7-T04, схема 4) — что уточнено при реализации.**

- **Команда и примитив.** `cmd::Die{character, cause}` (тег 6) — только система, только режим династии; `validate` отклоняет с причиной: актор задан (`NotAuthorized`), режим E1 (`InvalidState`, «используйте `KillCharacter`»), неизвестный id (`UnknownEntity`), уже мёртв (`InvalidState`, «already dead»), причина `None` или неизвестная (`InvalidArgument`), ещё не рождён (`InvalidState`). Работу делает `World::die(id, cause)` (публичный, как `marry`): повторный вызов и вызов в режиме E1 возвращают `false` и ничего не меняют. `KillCharacter` не менялся и в режиме династии по-прежнему отклоняется. Причины — `enum CauseOfDeath` (`None = 0`, затем старость, болезнь, роды, война, казнь, убийство, несчастный случай, раны, горе = 1…9; значения только добавляются в конец), хранятся в колонке `cause_of_death`; запись команды в журнале — `u32 id | u8 cause`, читатель отвергает значение ≥ 10.
- **Порядок в `die`:** (1) `end_marriage(умирающий)` — пока он ещё «жив» для примитива: вдова(вдовец) получает умершего в `ex_spouses`, у умершего `spouse` очищен, запись о вдове остаётся в его `ex_spouses`; (2) удаление из списка членов рода и сброс главы, если умирал глава; (3) `death_date = today`, `cause_of_death`; сброс группы S (здоровье, навыки, шкалы, черты, образование, `planned_death`); (4) записи очереди жизненных событий человека удаляются (`ScheduledQueue::remove_if`, O(размер очереди) на смерть); (5) удаление из `living_`, `ids.retire(id)`, прибавление хеша строки к накопителю. Глава рода **только сбрасывается** (преемника выбирает E7-T15 по записи `Die` в журнале: `archived_person(умерший).dynasty` называет род, пустой `head` у рода с живыми членами — сигнал); отдельного флага нет, чтобы не заводить хешируемое состояние. Запись в летопись рода (рождение, смерть, …) — задача E7-T16: она читает тот же журнал и `archived_person`, поэтому «факты для летописи» сейчас — дата, причина, род, ветвь, родители, дети и браки в архивной строке.
- **Архивная запись:** `World::archived_person(id) → std::optional<ArchivedPerson>` (копия группы K: род, ветвь, имя, портрет, пол, легитимность, даты, причина, родители, число браков, `ex_spouses`, `godparent`, список детей «старший первым», живых и мёртвых); `World::is_archived`, `archived_count`; `exists()` — по-прежнему «жив или архивный». Текущего супруга у архивной записи нет (брак закончила смерть), вдова — последний в `ex_spouses`. Ссылок на колонки архивных строк по-прежнему нет.
- **`MemberIndex`:** списки членов рода — `std::vector<CharacterId>` на род и один массив `member_pos_` по id вместо `SparseSet` на род; порядок прежний (вставка в конец, удаление swap с последним), поэтому часть `dynasties` и байты `members_` демо не изменились (golden подтверждает). Память `4 Б × (id + члены)` вместо `4 Б × max_id × число родов`; ограничение `stressgen` теперь только `роды × провинции ≤ 64 млн` (индекс провинций остаётся `SparseSet`).
- **Хеш:** `ExtPart::Archive = 2` — `nonzero(FNV(сумма хешей строк, число строк))`; строка хешируется по всем колонкам группы K (id, род, ветвь, имя, портрет, пол, легитимность, даты рождения и смерти, причина, родители, `spouse`, счётчик браков, `ex_spouses`, `godparent`). Накопитель `archive_sum_` — производное поле `World`: `die` прибавляет хеш новой строки (O(1)), `rebuild_derived_indexes()` пересчитывает сумму при загрузке и в `enable_dynasty_mode`; `check_invariants` сверяет его с полным пересчётом. Строки неизменяемы: все мутаторы `World` уже требуют `is_alive`, а группа S проверяется на умолчания. Пока мёртвых нет, часть равна 0 и вне `total`.
- **Сохранение (схема 4):** байтовая раскладка **не меняется**: байт слота `2` пишется в таблице слотов тела ядра (ядро и раздел `person` уже хранят всё нужное: запись E1 с `health = 0`, `death_date`, `cause_of_death`; раздел `kin` — браки), в списки членов архивные не попадают. Номер поднят, потому что сменилась допустимая область значений формата: читатель схемы 3 отвергает файл с флагом `2` (и должен говорить «более новая версия», а не «повреждён»). Шаг миграции «3 → 4» пуст; загрузчик отвергает файл схемы < 4 с архивными строками, флаг `2` без режима династии, архивную строку без даты и причины смерти, с непустой группой S, с текущим супругом, внутри списка членов. Накопитель и очередь в файле не хранятся. Фикстуры: `dynasty_v3.psv` (сделана кодом T03 первым коммитом PR, читается, хеш `d11a46b2f4fc2641` прежний, пересохраняется в те же байты, кроме слова схемы), `dynasty_v4_archive.psv` (`stressgen … --archived 160`, 240 живых + 160 мёртвых).
- **Очередь:** `check_invariants` теперь считает ошибкой запись очереди неживого человека (`die` их удаляет, пересборка не создаёт); устаревшие `PlannedDeath` живых по-прежнему допустимы.
- **Golden:** шесть значений хеша демо, хеш байтов реплея и хеш полезной нагрузки сейва (`kExpectedSaveBytesHash`, слово схемы не хешируется) **не менялись**. `PRP1` и `PSV1` не менялись.
- **Контракт для E8/E9/E10/E14/E17 (и E7-T15/T16/T17).** После применения `Die` в журнале тика (`CommandLog`, запись с `outcome = None`, `source` — `Internal` для смерти от системы, `External` для команды извне) уже верно: человек не в `members_of`, не в `living()`, не глава рода, его мнения/беременность/очередь не нужны (свои разреженные данные освобождает владелец данных — T12/T17 читают тот же журнал), вдова(вдовец) свободен(на). **Всё остальное, что хранит `CharacterId` живого человека, должно реагировать само**: система эпика в тот же или следующий тик просматривает записи `Die` журнала (`Simulation::command_log()`, записи с датой тика) и снимает/передаёт должность, регентство, командование армией, роль в схеме и договоре, `administrator` провинции (E9 `administrator_profile`), наставничество; после реакции эпик добавляет проверку «нет живых ссылок на архивных там, где они недопустимы» в свой `check_invariants` (мир-уровневый `check_invariants` этого не знает). Сослаться на мёртвого *безопасно* в данных, которые вечны по смыслу (родство, летопись, прежние должности в истории): id не переиспользуется и `archived_person` отвечает за любой существовавший id. Реакция на смерть не должна зависеть от порядка записей в журнале внутри тика (смертей может быть много); если нужен порядок — по возрастанию id умершего.

**Реализация E9-T03 (схема 5) — что уточнено при реализации.** Экономика (E9-T02) сохраняется разделами 32…39 блока расширения (не «хвостом» состояния с байтом `present`, как предполагал `economy-model.md` §13 до этого PR; расхождение снято, документ исправлен). Хеш — часть `ExtPart::Economy = 16`, отдельного поля `WorldHash.economy` нет. Мир без экономики не пишет ни одного из этих разделов и имеет ту же часть хеша 0: шесть значений хеша демо, хеш байтов реплея и `kExpectedSaveBytesHash` не менялись (слово схемы не хешируется), `PSV1` и `PRP1` не менялись. Ведомость хранится по кодам статей (список кодов перед счетами), поэтому будущий новый код статьи не сдвигает файл. Подробности — `economy-model.md` §13.5. Фикстуры схемы 4, сделанные кодом `main` до правок: `dynasty_v4_provinces.psv` (stressgen, 60 провинций, 60 мёртвых) и `e1_demo_v4.psv` (simcli, демо посреди года).

**Фикстуры:** каждая версия оставляет в `tests/data/saves/` файл, созданный **кодом предыдущей версии** (поэтому фикстуру нового шага создаёт автор следующего PR первым коммитом, до правок формата), плюс файлы с «нетривиальным содержимым» своей версии (беременность посреди срока, архив, летопись). Тест цепочки: каждая фикстура → текущий мир → `check_invariants()` пуст, пять старых частей хеша демо-фикстуры совпадают с эталоном, сохранение и повторная загрузка дают тот же хеш. Фаззинг E1 (порча байтов, обрезания) расширяется на каждый раздел; в каждом разделе — «пустой», «один элемент», «максимум», «счётчик больше остатка файла».

## D7. Хеш и политика golden

### Части

`WorldHash` сохраняет поля `total`, `calendar`, `rng`, `dynasties`, `provinces`, `characters` и вычисляются **как сейчас** (кроме замены условия пропуска строк в `characters`, D3 — для демо не меняет ни одного байта). Добавляется массив `ext[64]` — расширенные части по стабильным номерам:

| № | Часть | Что хеширует | Кто |
|---:|---|---|---|
| 0 | `mode` | `world_flags`, если ≠ 0 | T02 |
| 1 | `character_ext` | живые строки по возрастанию id, **только отличающиеся от умолчания**: все колонки групп K и S и `kin` | T02 |
| 2 | `archive` | архивные строки: **сумма (по модулю 2^64) хешей отдельных строк** и их число | T04 |
| 3 | `dynasty_ext` | роды по возрастанию, только отличающиеся от умолчания: единство, закон, ветви, журнал | T02/T14 |
| 4 | `pregnancy` | по матери по возрастанию | T12 |
| 5 | `chronicle` | по родам, записи в порядке хранения | T16 |
| 6 | `opinion` | держатель ↑, цель ↑ | T17 |
| 7 | резерв E7 | | |
| 8…15 | E8 | | |
| 16 | `economy` — FNV от девяти под-хешей таблиц экономики (`World::economy_hash_parts()`); 0 и вне `total` при выключенной экономике | E9-T03 |
| 17…23 | резерв E9 | |
| 24…63 | остальные эпики блоками | | |

**Правило пустоты.** Часть, у которой нет содержимого (нет отличающихся от умолчания строк, нет записей), равна `0`; если хеш случайно вышел `0`, он заменяется на `1`. Хеш строится **по содержимому**, поэтому «строка с умолчаниями» и «нет строки» неразличимы — это одно и то же состояние (само существование строки покрывает часть `characters`).

**Состав `total`.** Как сейчас: FNV-1a от пяти старых частей по порядку; затем для каждого `ext`-номера по возрастанию, у которого значение ≠ 0, в поток добавляются `u8(номер)` и `u64(значение)`. Следовательно, **мир без расширенных данных имеет тот же `total`, что и в E1**, а добавление новой части (E8, E9, E10…) не меняет `total` ни одного мира, который её не использует. Это обобщение правила E9 «часть `economy` = 0 и вне `total`, если данных нет»; E9-T03 пользуется тем же механизмом.

### Стоимость хеширования (оценка по измеренной скорости FNV-1a ≈ 1 нс/Б)

- `character_ext`: живая строка ≈ 200 Б хешируемых байт × 5 000 ≈ 1.0 МБ ≈ **1.0 мс**.
- Архив 20 000 строк × ≈ 110 Б ≈ 2.2 МБ ≈ **2.2 мс** при полном пересчёте — не укладывается в ≤ 2 мс на 25 000 строк. Поэтому хеш архива определён как **сумма хешей строк** (коммутативная, порядок смерти не важен), а `World` держит **накопитель**: при `retire` к нему прибавляется хеш новой строки (≈ 0.1 мкс), `compute_hash` для архива — O(1); при загрузке накопитель пересчитывается (≈ 2 мс один раз), `check_invariants` сверяет его с полным пересчётом. Строки архива неизменяемы (D3), поэтому накопитель корректен.
- Итого `compute_hash` ≈ 1.3 мс на 5 000 + 20 000 (оценка; T20 измеряет).

### Политика golden-значений

| Что | Когда меняется |
|---|---|
| **Демо `demo.v1`:** шесть значений хеша | не меняются **никогда** в рамках E7/E8/E9/E10…: это доказательство, что ядро не сдвинулось. Изменение — баг |
| **Демо:** хеш байтов реплея (`PRP1`) | не меняется (формат реплея не трогаем) |
| **Демо:** хеш байтов `save_state` | один раз в T02 (появляется блок расширения: `u32 flags = 0`, `u16 count = 0`). Чтобы дальнейшие подъёмы схемы не трогали это значение, тест хеширует **полезную нагрузку без первых четырёх байт** (слово схемы), а равенство слова схемы константе `kStateSchema` проверяется отдельно. После T02 значение заморожено: новые разделы пустых миров не пишутся |
| **`dynasty.v1`** (T18/T19) | собственные значения в `tests/golden_dynasty_test.cpp`; фикстура данных — копия в `tests/data/`; первое закрепление в T18 «предварительное», в T19 пересчёт один раз; далее — только с объяснением в коммите |
| Любой PR | «незапланированное» изменение (порядок обхода, платформа) — баг, а не повод править константу; два PR, меняющих golden, одновременно — повод остановиться (agents-workflow §4) |

Обоснование отказа от «`total` меняется один раз в T02», как формулировал эпик: при таком правиле golden `total` менялся бы в каждом эпике, добавляющем часть хеша (E9, E10, …), и каждый такой PR конфликтовал бы по `tests/golden_test.cpp` с остальными.

## Расчёты

### Измерения

Одноразовый микротест автора (не в репозитории; машина разработки, Windows 11, MSVC 14.44 `/O2`, данные синтетические: 25 000 id, 5 000 живых, случайно разбросанных). Это порядки величин для выбора между вариантами; воспроизводимые замеры — T20.

| Операция | Результат |
|---|---:|
| Обход 25 000 флагов «жив» + слот `id % 28` + две колонки (вариант «скан по таблице»), в день | **57 мкс** |
| Обход списка живых (5 000) + тот же слот + две колонки, в день | **5.9 мкс** |
| То же через косвенность `slot_of[id]` (вариант B) | 6.2 мкс |
| Поиск отца 1 000 случайных умерших: прямая колонка / через `archive_row[id]` | 0.33 / 0.64 мкс (≈ 0.3 / 0.6 нс на обращение) |
| Очередь дней рождения: 6 000 записей, ≈ 16 событий в день: извлечение, сортировка по `(due, kind, id)`, перепланирование | **1.5 мкс** в день |
| FNV-1a: 20 000 строк × 72 Б (1.44 МБ) / 5 000 строк × 180 Б (0.9 МБ) | 1.41 / 0.89 мс (≈ 1 нс/Б) |
| Сравнение 5 000 строк по 80 Б с умолчанием (разреженное хеширование/сохранение) | 23 мкс |

### Память таблиц людей (5 000 живых + 20 000 умерших)

| Статья | Вариант A (принят) | Вариант B (две таблицы) |
|---|---:|---:|
| Плотные колонки | 25 000 × 149 Б = **3.73 МБ** | живые 5 000 × 149 Б = 0.75 МБ; архив 20 000 × 68 Б = 1.36 МБ; карта `id → строка` 0.10 МБ → **2.21 МБ** |
| Список живых | 20 КБ | 20 КБ |
| Очередь расписания (≈ 6 000 × 24 Б, производная) | 0.14 МБ | 0.14 МБ |
| Мнения (≤ 30 × 12 Б; в среднем ≈ 12 записей на живого) | 0.7 МБ (макс. 1.8 МБ) | то же |
| Летопись (≈ 256 записей × 24 Б × 100 родов), беременности | 0.6 МБ | то же |
| **Итого** | **≈ 5.2 МБ** (макс. 6.3 МБ) | ≈ 3.7 МБ (макс. 4.8 МБ) |
| Профиль ×3 (15 000 живых + 60 000 умерших), только колонки | 11.2 МБ | 6.6 МБ |
| Бюджет эпика | ≤ 10 МБ — выполняется (при ×3 колонки сами превышают 10 МБ, но это стресс ×3, не игровой потолок; пересмотр — в «Последствиях») | |

Для сравнения с проблемой 2: индекс членов `SparseSet` на род при 100 родах и 25 000 id занимал бы 10 МБ, при ×3 — 90 МБ; `MemberIndex` — 0.1 и 0.3 МБ.

### Размер сейва (несжатый, оценка)

Тело ядра 25 000 слотов × 21 Б ≈ 0.5 МБ; раздел `person`: живые ≈ 90 Б × 5 000 ≈ 0.45 МБ, архивные ≈ 20 Б × 20 000 ≈ 0.4 МБ; `kin` ≈ 29 Б × 25 000 ≈ 0.7 МБ; остальные разделы ≈ 1 МБ. Итого ≈ **3 МБ** при бюджете ≤ 6 МБ (до сжатия zstd, которое для таких таблиц даёт кратное уменьшение). Загрузка: чтение и проверки ≈ десятки мс + `rebuild_derived_indexes()` (≈ 25 000 строк, очередь на 6 000 записей, накопитель архива ≈ 2 мс) — с запасом укладывается в 200 мс (бюджет эпика).

### Снимок мира

`World::snapshot()` копирует **все** колонки, включая архивные строки: при варианте A это ≈ 4–5 МБ `memcpy` (порядка 1 мс). Для UI это не ограничение (решение E2-T05: компактное представление под запросы окон, а не копия мира); полная копия нужна сохранению в фоне (`save_async`), редкая операция. Если T20 покажет > 2 мс, это один из триггеров пересмотра (ниже).

## Последствия

**Что становится проще.** Ссылки на людей верны всю партию; никаких косвенных обращений; архив — просто строка; расписание — один механизм (очередь как индекс), формат сейва не зависит от его реализации; демо и его golden неприкосновенны; соседние эпики добавляют свои разделы/части/теги, не трогая чужие.

**Что становится сложнее.** Появляются два режима мира (E1 и династия) с общим кодом, пока демо жив; надо поддерживать производные индексы и их сверку; ленивая очистка ссылок на умерших требует дисциплины в соседних эпиках (таблица D1); сейв хранит разреженные строки и разделы с версиями.

**Триггеры пересмотра D1/D3 (переход к уплотнению хранилища архива без смены id и API):** число id > 200 000 в реалистичной партии; память людей > 10 МБ на профиле `year60`; полная копия мира > 2 мс; `compute_hash` > 2 мс; рост тика «год 1 → год 60» > 2× из-за архива.

**Что измерить в E7-T20 (на `stressgen` с правдоподобной генеалогией, режим династии, 5 000 живых + 20 000 архивных, профили `year60`/`year60x3`):**
1. фактический `sizeof`-итог на id и память таблиц, сравнение с таблицей выше;
2. `compute_hash` целиком и по частям (особенно `character_ext` и накопитель архива), загрузка с `rebuild_derived_indexes()`;
3. `World::snapshot()` и размер/время сохранения;
4. годовая обработка дней рождения при реальных 16 событиях в день и «пик в один день» (все 5 000 в один день ≤ 5 мс);
5. `Die.apply` (удаление из `living_`/`members_`), `take_due_life_events`, месячный проход по `living_`;
6. стоимость `check_invariants` (сверка очереди и накопителя);
7. деградация «год 1 → год 60».

**Риски.** (1) Два режима мира — риск «забыть включить режим»: `check_invariants` проверяет, что в режиме династии у каждого живого есть запись `Birthday`; сценарии включают режим первой строкой. (2) Ленивые ссылки на умерших (мнения, наставник) — месячная проверка и инвариант-исключения перечислены в D1. (3) Дата смерти определяется на год вперёд — события (E11) должны менять её командой `PlanDeath`, а не обходить; это решение, а не побочный эффект. (4) Неограниченный `CommandLog` (вне этого ADR): оценка E7 ≈ 1 000 команд в год — безопасно, но политику ограничения журнала нужно принять до E10/E17 (они дадут сотни команд в день).

## Отклонённые альтернативы

- **Две таблицы с косвенностью (B)** — выигрыш 1.5 МБ не оправдывает переписывание всех обращений и канонизацию порядка; остаётся запасным путём D3 (value-API).
- **Поколенческие 64-битные идентификаторы (C)** — не избавляют от архива и раздувают все ссылки.
- **Штаффель по `id` для демографии (A в D4)** и **скан колонки `next_event` (D)** — см. проблему 3 и P8.
- **Сохранение очереди расписания в сейве** — создаёт второй источник истины; производный индекс проще и безопаснее.
- **Безусловные новые части хеша и безусловные новые разделы** (как в первоначальной формулировке эпика) — меняют golden демо в каждом эпике и порождают конфликты PR.
- **Новая версия `PRP2` для реплеев** — не нужна, пока `total` покрывает расширенные части; `PRP1` остаётся.
- **Все изменения здоровья и стресса через команды** — миллионы записей журнала за партию без пользы для наблюдателей.
