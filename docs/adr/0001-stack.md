# ADR-0001: Технологический стек

- Статус: **принято (предварительно)** — подтверждается спайком E3 (см. «Проверка решения»)
- Дата: 2026-11-06
- Заменяет: черновик с Rust и выбором Bevy/Godot (отклонён владельцем в пользу собственного движка на C++)

## Контекст

Хобби-проект, соло, долгая разработка. Одиночная стратегия с 2D-картой всей России 1703 года и очень насыщенным UI. Партия 30+ часов, поэтому поздняя стадия партии должна оставаться быстрой (ADR-0002). Владелец хочет **собственный движок на C++** и склоняется к **DirectX**.

## Решение

**Гибрид:** своё — там, где это даёт ценность игре (ядро симуляции, рендер карты, слой данных, ИИ); готовое — там, где свой код только отнимает месяцы (UI-фреймворк, шрифты, звук, формат данных).

### 1. Язык и сборка
- **C++20** (MSVC в Visual Studio 2022 на Windows; clang как второй компилятор для проверки переносимости).
- **CMake + vcpkg** (манифест), **Ninja**; CI — GitHub Actions.
- Флаги: `/W4` (или `-Wall -Wextra`), санитайзеры (ASan/UBSan) в отдельной CI-конфигурации.

### 2. Архитектура: ядро отделено от движка

```
patriarch/
├─ src/
│  ├─ core/       # утилиты: ID, фиксированная точка, PRNG, контейнеры, аллокаторы, логи
│  ├─ sim/        # СВОЁ: состояние мира, тики, команды. Без графики и платформы, детерминированное
│  ├─ data/       # схемы контента, загрузчики, валидация
│  ├─ rules/      # события, условия, эффекты (скомпилированный DSL/AST)
│  ├─ ai/         # ИИ династий и императора (читает снапшот, выдаёт команды)
│  ├─ engine/     # СВОЁ: окно/ввод, рендерер (абстракция + D3D11), камера, ресурсы, потоки задач
│  ├─ ui/         # интеграция RmlUi, модели данных (data binding), локализация
│  └─ game/       # склейка: сценарии, экраны, режимы карты
├─ tools/         # валидатор контента, генератор стресс-состояний, инспектор сейвов, сборщик карты
├─ content/       # данные игры, локализация
├─ tests/ bench/
└─ docs/
```

Правила:
- `sim` **не зависит** от `engine`/`ui`/платформы. Его можно собрать как консольную программу, гонять в тестах, бенчмарках и стресс-сценариях без GPU.
- UI и рендер **читают неизменяемый снапшот** состояния и **отправляют команды**. ИИ использует те же команды, что и игрок.
- Симуляция идёт в **отдельном потоке**; рендер/UI никогда не ждут тика.
- Рендер скрыт за интерфейсом `IRenderer`; сейчас единственный бэкенд — D3D11.

### 3. Детерминизм
- Арифметика симуляции — **целые числа / фиксированная точка** (`Fixed32`, `Fixed64`), без `float/double` в состоянии.
- Свой PRNG (PCG32/xoshiro), зерно хранится в сейве; отдельные потоки случайности по подсистемам.
- Итерация только по упорядоченным структурам (плотные индексы, `std::vector`, сортированные контейнеры); неупорядоченные хеш-таблицы не влияют на состояние.
- Золотые тесты: `seed + поток команд → хеш состояния`, сравнение на разных сборках/ОС.

### 4. Графика: Direct3D 11 (Windows-first)
Почему D3D11, а не D3D12/Vulkan:
- 2D-карта и UI не упираются в API; D3D12/Vulkan — это недели кода и риск ошибок синхронизации без выигрыша.
- D3D11 зрелый, хорошо документирован, имеет отличные инструменты (RenderDoc, PIX, Visual Studio Graphics Debugger).
- Абстракция `IRenderer` оставляет путь к другому бэкенду (Vulkan/OpenGL) при желании выйти на Linux.

Что рисуем сами:
- карту провинций: **цветовая карта ID провинций** (индексная текстура) + шейдерная выборка владельца/режима карты через палитру-текстуру (режимы карты переключаются заменой палитры, без перерисовки геометрии);
- границы — шейдером по соседним ID или предрасчитанной векторной геометрией;
- юниты/маркеры/надписи на карте — батчинг, атлас, SDF-шрифт для названий.

### 5. UI: RmlUi (HTML/CSS-подобный игровой UI)
- Окна, списки, тултипы, анимации, привязка данных (data binding) к моделям из снапшота. Разметка и стили в файлах `.rml`/`.rcss` — стили редактируются без пересборки.
- Для RmlUi нужен **свой render-интерфейс на D3D11** (небольшой, ~сотни строк: геометрия, текстуры, scissor, transform) и интерфейс системы/файлов.
- Шрифты: FreeType (+ HarfBuzz при необходимости); кириллица из коробки.
- Альтернатива, если RmlUi не подойдёт на спайке: Dear ImGui для инструментов/отладки и собственный лёгкий UI-слой для игры (дороже по времени).
- **Dear ImGui** в любом случае используем для dev-оверлеев (телеметрия, отладка симуляции).

### 6. Прочие библиотеки

| Область | Выбор | Примечание |
|---|---|---|
| Окно/ввод | **SDL3** (Windows-first, оставляет дверь для Linux) | Либо Win32 напрямую, если SDL окажется лишним |
| Аудио | **miniaudio** (+ stb_vorbis), позже, возможно, FMOD | Простой и достаточный старт |
| Изображения | stb_image, `DirectXTex` для DDS/BC-сжатия | Атласы и карта |
| Формат данных | **JSON5/TOML** или собственный человекочитаемый формат (Paradox-подобный) + свой парсер | Решается в E4; цель — читаемость и открытость для модов |
| Правила | Свой DSL → AST → байткод при загрузке | Без интерпретации текста на тике (ADR-0002 P5) |
| Локализация | Файлы строк + **ICU MessageFormat** (или свой лёгкий плюрализатор для RU/EN) | Русские склонения и числа |
| Сейвы | Собственный бинарный формат + **zstd**, версионированная схема | Миграции |
| Потоки | Свой пул задач или **enkiTS / taskflow** | Детерминированное слияние результатов |
| Тесты | **doctest** (или Catch2) + property-подход вручную/`rapidcheck` | Golden-реплеи |
| Бенчмарки | **Google Benchmark** | Гейт в CI |
| Профилирование | **Tracy**, RenderDoc, PIX, VS Profiler | Оверлей времени подсистем |
| ECS | Не обязателен для `sim`; допускается **EnTT** для презентационного слоя | Для `sim` предпочитаем плотные массивы по типам (SoA) |
| Математика | Своя минимальная / `glm` для графики | В `sim` — только фиксированная точка |

### 7. Платформы
- Релиз: **Windows 10/11 x64**.
- Linux/Proton: через Proton уже работает на D3D11 (DXVK), отдельный бэкенд — этап после релиза по желанию.

## Проверка решения (спайк E3, ~2–3 недели)

Нужно доказать три вещи, прежде чем фиксировать статус «принято» окончательно:
1. **Карта:** индексная текстура на ~300 провинций, переключение режимов карты палитрой, зум/пан, выбор провинции — стабильно 60+ FPS на целевом слабом железе.
2. **UI:** окно «персонаж» на RmlUi с кириллицей, вложенными тултипами (тултип в тултипе), списком со скроллом на 1000 строк, привязкой данных к снапшоту.
3. **Ядро:** прототип `sim` на 400 провинциях и 5 000 персонажей с замером дневного и месячного тика (ADR-0002).

Если RmlUi не проходит — переходим к альтернативе из п. 5.

## Последствия

- Большой объём «своего» кода: больше работы, но и полный контроль над производительностью и форматами — в духе проекта.
- Дисциплина границ модулей (`sim` ↔ `engine/ui`) нужна с первого дня.
- Фиксированная точка требует аккуратных типов и тестов арифметики.
- В C++ нет «бесплатной» безопасности памяти — компенсируем санитайзерами, статанализом, правилами RAII и ревью по чек-листу.

## Отклонённые альтернативы

- **Rust + Bevy / Godot + gdext / wgpu**: предлагались как основной план; владелец выбрал C++ и собственный движок. Rust остаётся хорошим вариантом, если C++ окажется непосильным по сопровождению.
- **Unity / Unreal / Godot целиком**: противоречит цели «свой движок».
- **D3D12 / Vulkan**: избыточная сложность для 2D-карты и UI.
- **Электрон/веб-UI**: лишняя среда, вес приложения, склейка рендера.
