# ADR-0002: Архитектура производительности

- Статус: **принято** — E2-T09, 2026-11-08; [итоговый отчёт и границы проверки](../dev/e2-spike-report.md)
- Дата: 2026-11-06

Приняты архитектурные решения для следующего этапа разработки. Бюджеты остаются
целями ТЗ: спайки на синтетических данных не подтверждают производительность готовой
игры или минимального ПК. E2-T08 (память/слабый профиль) и регрессия #217 остаются
открытыми; принятие ADR не закрывает E2/M0.

## Проблема

У HoI4 и Victoria 3 (а также CK3) поздняя партия тормозит. Типичные причины:

| Причина | Где проявляется |
|---|---|
| Рост числа сущностей без верхней границы (персонажи, поп-группы, юниты) | CK3: тысячи живых и «исторических» персонажей |
| Пересчёт «всего каждый тик» | Модификаторы, цены, снабжение, пути |
| Интерпретируемый скрипт: условия событий проверяются для всех сущностей постоянно | Paradox-script |
| Однопоточные участки на критическом пути | Экономика/ИИ |
| ИИ со сложными решениями каждый тик по каждой стране | HoI4 (тысячи дивизий, пути), Vic3 (ИИ и рынки) |
| UI завязан на тик симуляции | Фризы интерфейса |

## Принципы (решения)

### P1. Ограничивать рост *по дизайну*
Верхние границы (см. NFR-PERF-5): ≤ 5 000 полных персонажей, ≤ 300 армий, ≤ 400 провинций (вся Россия), ≤ 100 «крупных» династий с полными персонажами (+ ~400 «малых» родов — лёгкие записи без персонажей, GDD 02 §6.5, решение владельца 2026-11-08). Партия идёт 30+ часов, поэтому границы — обязательные, а не пожелания.
- **Агрегаты вместо людей:** население — это (провинция × сословие), а не отдельные люди. Полностью симулируются только **знать, члены династий и значимые слуги**.
- **LOD персонажей:** умерший/неактуальный → архивная запись (имя, даты, родители, дети) без активной симуляции; далёкие от игрока персонажи считаются реже.
- **Армии — единицы, а не дивизии.** Лимиты на число армий; слияние мелких отрядов.
- **Глубина партии ограничена по замыслу:** 30+ часов — это реальное время, а не годы; ориентир ≈ 70–80 игровых лет при скоростях 3–5. Дальше партия переходит в «песочницу» с усиленной архивацией и ограничением роста.
- **Вне ядра — упрощённые территории:** слабоосвоенные регионы (Сибирь, Дальний Восток) — укрупнённые провинции с минимальной симуляцией.
- **Внешние державы — не акторы-симуляции:** события и шкалы давления вместо их династий и экономик.

### P2. Многоуровневый тик
| Частота | Что считается |
|---|---|
| Ежедневно | Перемещение армий, осады, таймеры схем и событий, срочные команды |
| Еженедельно | Интриги (прогрессы), настроения двора |
| Ежемесячно | Экономика провинций, казна, торговые потоки, население (прирост/убыль) |
| Ежегодно | Демография, старение, рождения/смерти (с равномерным распределением), реформы |

**Шахматная разгрузка (staggering):** тяжёлые месячные расчёты распределяются по дням — в день *d* (1–28) месяца считаются сущности с `id % 28 == d - 1`; дни 29–31 никого не выбирают, поэтому каждая сущность обрабатывается ровно один раз в любом месяце (реализовано в `pat/sim/calendar.hpp`: `is_monthly_slot`, `is_weekly_slot`, `is_yearly_slot`, `is_due_every`). Это сглаживает пики, а не создаёт «лаг раз в месяц». Исключение: старение и смертность людей идут по **дням рождения** через очередь расписания, а не по `id % 365` (ADR-0006 §D4).

### P3. Инкрементальность вместо пересчёта
- Модификаторы и производные значения кэшируются и **пересчитываются только при изменении источников** (dirty-флаги, граф зависимостей).
- Значения для тултипов («почему это число») хранят разложение на слагаемые лениво, только когда окно открыто.

### P4. Данные, дружелюбные к кэшу процессора
- Сущности адресуются **плотными ID** (`u32` newtype), хранятся в `Vec` по схеме SoA (раздельные массивы полей) для горячих данных.
- Никаких графов из `std::shared_ptr`/указателей в горячих путях; поколения (generation) для безопасных ссылок на удаляемые сущности; арены/пулы вместо `new` на тик.
- Строки — интернированы (`u32` символы); строки не участвуют в тике.

### P5. Правила — компилируемые и событийные
- События, условия и эффекты загружаются как **скомпилированные деревья/байткод**, а не интерпретируемый текст.
- **Индекс триггеров:** событие подписывается на тип триггера («смерть персонажа», «брак», «смена владельца»), поэтому проверяются **только** подписанные события на **изменившихся** сущностях, а не «все события × все персонажи» каждый тик.
- Для E11: списки `[scope][on-action]` с фиксированным порядком priority/EventId и устранением повторного кандидата от нескольких действий. Месячный пульс полный, со stagger `id % 28`; 10%-ная выборка из E2-T04 меняет полноту и не заменяет его без отдельного решения о семантике.
- Случайные события — взвешенные пулы с таймерами, а не «бросок на каждого каждый день».

### P6. ИИ с бюджетом
- Утилити-ИИ, решения кэшируются (перепроверка по таймеру или по значимому изменению).
- **ИИ-LOD:** династии рядом с игроком/престолом думают чаще, далёкие — раз в N дней.
- Детерминированная квота ИИ в WU на тик: очередь решений с приоритетами; незавершённое продолжается на следующем тике. Миллисекунды — метрика бюджета, не условие остановки логики (NFR-DET-1).
- ИИ читает **снапшот** и выдаёт **команды** — не мутирует мир напрямую.

### P7. Потоки и разделение UI/симуляции
- Симуляция в **своём потоке**; рендер и UI в главном. UI читает последний опубликованный неизменяемый снапшот через атомарную подмену `shared_ptr`.
- Базовое исполнение внутри тика — `SerialExecutor` и месячный stagger. Универсальный dispatch мелких задач в пул не вводится: E2-T03 не показал выигрыша для stagger на 2–6 ядрах. Пул (#33) допускается для конкретной тяжёлой системы после проверки её гранулярности, с **детерминированным** слиянием результатов в фиксированном порядке.
- Базовая схема будущего UI-моста — полная неизменяемая копия **компактного UI-представления** с ограниченной частотой публикаций. Диффы и два банка страниц остаются альтернативами при росте payload; E2-T05 не доказал точного ранжирования по скорости. Текущий runner продолжает копировать весь `World`; переход требует отдельной интеграции.
- Сохранение — в фоне: копируем снапшот, сжимаем и пишем в другом потоке.

### P8. Измерять с первого дня
- Бенчмарки Google Benchmark на ключевые стадии тика, CI-гейт на регрессию > 10%.
- Гейт E2-T07 сравнивает исходные повторы двух закоммиченных версий на одном runner: медиана строго >10%, sample RSD ≤5%, минимум 5 повторов (capture — 7). Шум возвращает `inconclusive`, ошибки/несопоставимость — `invalid`; эталон обновляется только явно через ревью. [Протокол](../dev/performance-gate.md).
- **Генератор стресс-состояний** (`tools`): создаёт мир «год 60» с нагрузкой ×3 и прогоняет тики; бюджеты — NFR-PERF-2.
- Оверлей телеметрии: время каждой подсистемы, размеры коллекций, p50/p95/p99.
- Tracy-метки в каждой подсистеме.
- Правило ревью: любое новое «каждый тик по всем X» требует обоснования или перевода в событийную/периодическую модель.

## Бюджеты (цели ТЗ; проверка готовой игры ещё впереди)

| Метрика | Цель |
|---|---|
| Дневной тик (p95) | ≤ 8 мс |
| Недельный | ≤ 30 мс |
| Месячный (с staggering — пик) | ≤ 120 мс |
| Годовой | ≤ 400 мс |

| FPS UI | ≥ 60, независимо от скорости |
| Деградация «год 1 → год 60» | ≤ 2× |

## Последствия

- Дизайнерские ограничения (лимиты армий, длина партии, агрегаты населения) — часть ТЗ; геймдизайн не должен их нарушать «ради фичи».
- Дополнительная работа на инфраструктуру (бенчмарки, стресс-генератор) с первого спринта — окупается на поздней стадии.

## Факты спайка E2-T03 (2026-11-06)

[Отчёт и исходные результаты](../benchmarks/E2-T03-tick-cost.md): 48 вариантов на i5-12400F,
Windows/MSVC Release, по 10 игровых лет × 3 повтора; одинаковые хеши Serial/Pool,
burst/stagger и grain 64/256 на границах полных месяцев. На макете `year60x3` serial +
stagger дал p99 58.4 мкс против 160.2 мкс burst. Dispatch мелких batch на 4–6 ядер
не окупился; ограниченный выигрыш 2 ядер получен для `burst / grain 64` (1.65× по mean).
40/48 строк имеют RSD ≤ 5%; остальные не используются для точного ранжирования.

Рабочий вывод для нынешних макетов: сохранять SerialExecutor + месячный stagger,
не подменять все циклы универсальным пулом. Пул остаётся экспериментом инструмента;
production-backend (#33) требует замера конкретной тяжёлой игровой системы и её
гранулярности. Эти числа не подтверждают бюджеты готовой игры или минимального ПК.
Решение включено в принятую архитектуру E2-T09 с этими ограничениями.

## Факты спайка E2-T04 (2026-11-06)

[Отчёт и исходные результаты](../benchmarks/E2-T04-trigger-index.md): 500 определений,
400 провинций, 1 000/5 000/15 000 персонажей × 1/10/100% изменений за тик, 365 дней
× 3 повтора на одном логическом CPU i5-12400F, Windows/MSVC Release. Индекс и полный
обход дают одинаковые action/pulse-векторы на каждом тике и хеши между повторами.
Стабильны 4/9 пар (RSD обоих методов ≤ 5%); гипотеза ускорения ≥ 10× не подтверждена:
9.18× при 15 000 персонажей и 1% изменений, 1.61× при 100%. Для 5 000 персонажей
при 10/100% изменений — 5.21× / 1.68×. Номинальные 9.73× при 1% нестабильны.

Рекомендация для E11 в рамках P5: списки `[scope][on-action]` в порядке priority/EventId,
устранение повторного кандидата от нескольких действий, полный пульс `id % 28`.
10%-ная выборка обнаружила лишь 17.80–49.55% различных подходящих pulse-пар за год;
она меняет семантику и требует отдельной калибровки MTTH/допустимой задержки. Цена
producer и fan-out зависимостей не измерена. При плотном потоке и 5 000 персонажей
индекс даёт mean 3.26 мс / p99 5.20 мс: бюджет событий GDD 08 §5.3 не подтверждён.
Игровой движок правил не внедрён; E2-T09 принимает направление для его реализации.

## Факты и решение спайка E2-T05 (2026-11-07)

[Отчёт и исходные результаты](../benchmarks/E2-T05-snapshot-publication.md): одинаковое
UI-представление 16/48 КБ (400/1 200 провинций + 100/300 родов), 1/10/100% изменённых
строк по одному полю, producer 40/400 Гц и чтение до 400 провинций/100 родов на 60 Гц.
Три схемы — полная копия, очередь диффов с checkpoint и два банка страниц с COW.
14 сочетаний по 3 повтора, Windows/MSVC Release на i5-12400F; все данные совпали.
Фактическое чтение 59.83–60.00 Гц. Полная UI-копия: mean publish 3.83–14.34 мкс,
acquire 0.27–0.58 мкс; пик владения 31.36/93.86 КиБ без удержания старых кадров.
RSD ≤ 5% у 6/42 micro-строк и 2/42 paced-строк: точный победитель не установлен.

Базовый выбор для будущего UI-моста: компактное представление под запросы UI,
полная неизменяемая копия и atomic-публикация shared_ptr с ограниченной частотой.
Выбор основан на простоте и абсолютной стоимости, не на доказанном превосходстве
по скорости. Диффы переносят работу на UI и при плотной очереди расходуют больше
памяти; два банка требуют учёта всех устаревших страниц и COW для старых читателей.
Произвольное удержание снапшотов увеличивает память любой схемы.

Нынешний SimulationRunner / World::snapshot() не изменены. Копия полного мира —
отдельный reference (mean 243–437 мкс / 1 751–2 311 мкс), с другим payload; это не
ускорение одного алгоритма. Извлечение UI-представления, строки, персонажные окна
и RmlUi не входят в измерение. Production-интеграция — отдельная задача; общий
ADR принят в E2-T09; стоимость production-интеграции ещё не проверена.
