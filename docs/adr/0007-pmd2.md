# ADR-0007: Формат карты PMD2 — разделение слоёв, версионирование, миграция

- Статус: **предложено** (документ + замеры; кода нет, `PMD1` не меняется)
- Дата: 2026-11-08
- Связано: ADR-0003 (объёмная карта), ADR-0004 §2, §5, §6 (слои, формат, исторические корректировки), E3-T03 (`PMD1`), E21, Geo-3 (#79), Geo-5 (#81), Geo-6 (#82), Geo-7 (#83), Geo-9 (#85), Geo-8 (#84); решения владельца #200 и #201

## Контекст

### Что такое PMD1 сегодня (факты по `src/mapdata`, 2026-11-08)

Один файл, все слои вместе, порядок байт — little endian, целые фиксированной ширины, `float` в файле нет.

```
Заголовок, 36 байт:
  "PMD1" | u16 format_version (=1) | u16 flags (должен быть 0) | u32 width | u32 height |
  u16 sea_level | u16 province_count | u32 metres_per_unit_milli | u64 seed | u32 section_count (=4)
Далее ровно 4 секции подряд, каждая:
  u32 id | u64 uncompressed_size | u64 hash | u64 compressed_size | кадр zstd (28 байт заголовка секции)
```

| id | Секция | Содержимое до zstd |
|---|---|---|
| 1 | высоты | `u16` на пиксель; построчная дельта (первый пиксель строки — абсолют) с переносом по модулю 2^16, затем два байтовых плана (все младшие, все старшие) |
| 2 | провинции | `u16` на пиксель, 0 = вода, 1..N = провинция; то же преобразование, что у высот |
| 3 | материалы | `u8` на пиксель, значения `Material` (10 классов), без преобразования |
| 4 | таблица | по записи на провинцию: `id, color_rgb, area_px, centroid, bbox, mean_height, coastal, соседи (id + длина границы в пикселях)` |

`hash` — FNV-1a 64 (`core::HashStream`) от несжатых байт секции; это защита от порчи, а не криптография. Читатель проверяет: магию, версию (только `1`), `flags == 0`, `section_count == 4`, размеры (ширина/высота ≤ 65535, пикселей ≤ 2^30, таблица ≤ 64 МБ), порядок и размер каждой секции, хеш, отсутствие лишних байт в конце, согласованность (`p.id == i+1`, id провинции в растре ≤ `province_count`, материалы в диапазоне). Любое отклонение — ошибка с кодом 20…45; частичного чтения нет. Запись атомарная (`.tmp` + переименование).

Инварианты `validate_map` (не часть файла): вода = высота ≤ `sea_level` ровно там, где провинция = 0; запись таблицы совпадает с пикселями; каждая провинция — одна 4-связная область; соседство симметрично; граф провинций связен; цвета уникальны.

### Что мешает требованиям владельца (ADR-0004 §5, Geo-8 #84)

1. **Слои слиты в один файл.** Секция высот — 95% объёма. Исправление границы провинции переписывает весь файл, и наоборот: смена стилизации рельефа заставляет пересобирать провинции. Чужие секции читать не нужно, но и менять отдельно нельзя.
2. **Нет явной воды.** «Суша» = «высота > sea_level». Озеро с поверхностью на 456 м (Байкал) и Каспий на −28 м этим правилом не выразить. Рек нет вовсе.
3. **Нет привязки к Земле.** Нет проекции, шага пикселя, начала координат, широты и долготы.
4. **Нет природных регионов** и провенанса (чем и из чего собрано).
5. **Нет механизма расширения:** неизвестная секция, `flags != 0` или версия ≠ 1 — ошибка. Любое добавление ломает все старые читатели; заголовок и таблица секций не защищены собственной суммой.
6. **Производные поля таблицы** (`mean_height`) смешивают слой провинций с рельефом: сменили высоты — кэш в таблице устарел, и никто этого не заметит.
7. **Пиксель-последовательная распаковка:** секция — один кадр zstd, декодирование дельты однопоточное.

### Ограничения, заданные раньше

`PMD1`, `mapgen`, процедурный режим, тесты и детерминизм сохраняются (ADR-0004). Физика и изменяемое состояние мира раздельны (ADR-0004 §2). Новых зависимостей нет (ADR-0001, правило 7 `AGENTS.md`): zstd и FNV-1a уже есть в `core`. Исторические корректировки хранятся отдельно от современной основы (ADR-0004 §6). Деление 1708 года не подменяет структуру 1703 (ADR-0004 §1). Игровое состояние (владельцы, войны) живёт только в `World`.

## Замеры PMD1 (throwaway, не коммитятся)

Процедурная карта `mapgen --width W --height H --provinces 400 --seed 1`, релизный `mapgen.exe` (MSVC Release, 12 потоков); загрузка 8192×4096 — три прогона (0,51-0,52 с), 16384×8192 — два (1,96-2,04 с); для разбивки загрузки — одноразовая программа на той же библиотеке zstd.

| Показатель | 8192×4096 | 16384×8192 |
|---|---|---|
| Файл PMD1 | **14 346 012 Б (13,7 МиБ)** | **41 949 492 Б (40,0 МиБ)** |
| секция высот | 13 576 508 Б (94,6%, 0,20 от сырых) | 40 104 760 Б (95,6%, 0,15) |
| секция провинций | 431 655 Б (3,0%) | 975 859 Б (2,3%) |
| секция материалов | 322 146 Б (2,2%) | 852 404 Б (2,0%) |
| таблица | 15 555 Б | 16 321 Б |
| Сырые слои в памяти | 160 МиБ (64 + 64 + 32) | 640 МиБ |
| Загрузка `read_map_file` | **0,51 с** | **2,0 с** |
| из них: чтение файла | 17 мс | не измерено |
| из них: распаковка zstd | 133 мс | 508 мс |
| из них: FNV-1a по сырым байтам | **172 мс** | 711 мс |
| из них: декодирование дельты | **205 мс** | 808 мс |
| Генерация / запись | 2,7 с / 0,61 с | 11,3 с / не измерено |

Выводы по замерам:

- Загрузка укладывается в бюджет ADR-0003 (≤ 10 с) с большим запасом, но **72% времени — не распаковка, а проверка FNV по сырым данным и однопоточное декодирование дельты** (первое — 1 нс/Б по 168 МБ, второе — последовательная зависимость с делением `i % width` на каждом пикселе). Оба шага устраняются форматом (см. §2): сумма по сжатым байтам (≈ 14 МБ вместо 168 МБ) и независимые плитки для параллельного декодирования.
- Процедурные высоты — не оценка для реальных: у настоящего DEM шум выше (в процедурной карте 3,2 бита/пиксель). См. §7.
- Пик памяти при загрузке PMD1: файл + сырая секция + декодированный слой (для высот ≈ 14 + 64 + 64 МиБ), то есть секция живёт в двух копиях.

## Решения (кратко)

| # | Вопрос | Решение |
|---|---|---|
| D1 | Разделение | Два контейнера: **физический** (`kind=1`) и **провинций** (`kind=2`); третий вид (`kind=3`) — поправки. Провинции привязаны к физике «ключом берега» (`coast_key`), а не к её полному содержимому |
| D2 | Контейнер | Магия `PMD2`, минорная версия в заголовке, **таблица чанков** сразу за заголовком, чанки с id из четырёх ASCII-символов и версией, флаг «критический»; неизвестный необязательный чанк пропускается |
| D3 | Растры | Тайловые растровые чанки (плитка 1024², `u8`/`u16`), та же дельта+плоскости+zstd, что в PMD1, внутри плитки; `raw_hash` — по каноническому построчному растру (не зависит от размера плитки и версии zstd) |
| D4 | Контрольные суммы | FNV-1a 64: `header_hash` (заголовок + таблица), `stored_hash` (по сжатым байтам, проверяется всегда), `raw_hash` (по сырым, проверяется в строгом режиме/CI и служит идентичностью содержимого) |
| D5 | Вода | Растр водоёмов `WBOD` (u16, 0 = суша) + таблица `WTBL` с видом и **уровнем поверхности** каждого водоёма; растр рек `RIVR` и векторные русла `RVEC`. «Суша» определяется `WBOD`, а не порогом высоты |
| D6 | Привязка | Чанк `GEOR`: вид проекции, параметры в микроградусах, аффинная привязка пиксель → метры проекции в миллиметрах (всё целое); без PROJ в C++ |
| D7 | Провенанс | Чанк `PROV` в каждом контейнере: id источников манифеста, версии, SHA-256 файлов, шаги преобразований, применённые поправки |
| D8 | Миграция | `PMD1` читается всегда и навсегда прежним кодом; `PMD1 → PMD2` — детерминированная функция с побитовым обратным преобразованием; `mapgen` по умолчанию пишет `PMD1` |
| D9 | Вне формата | Владельцы, войны, названия, период и достоверность границ (контент E4), ключи сценария — не в PMD |

## 1. Файлы и слои

```
<каталог карты>/
  physical.pmd     kind=1   рельеф, вода, материалы, природные регионы, привязка к Земле
  provinces.pmd    kind=2   растр провинций и таблица (геометрия, соседство)
  (corrections/*.pmd kind=3 входные поправки; в игру не поставляются, см. §6)
```

| Слой | Контейнер | Что меняется → что пересобирается |
|---|---|---|
| Физический | `kind=1` | новый DEM, стилизация, материалы, реки, регионы → только `physical.pmd` |
| Провинции | `kind=2` | новые границы, деление/слияние → только `provinces.pmd` |
| Исторические данные (период, источник, достоверность, названия) | не PMD, а контент E4 | ссылаются на **ключ** провинции |
| Состояние мира | не PMD, а `World` | карта рисует палитрой/оверлеями (как сейчас `MapMode`) |

### 1.1. Правило связи: ключ берега

Растр провинций корректен, только если «провинция ≠ 0» ровно на суше. Поэтому провинции зависят не от всей физики, а от **сетки и маски суши**:

```
coast_key = FNV-1a64( width, height, raw_hash(GEOR), raw_hash(WBOD) )
```

`physical.pmd` записывает свой `coast_key` в заголовок (поле `bind_key`), `provinces.pmd` записывает тот `coast_key`, под который построены границы. Загрузчик пары сравнивает числа и при расхождении возвращает ошибку «границы построены для другого берега».

| Изменение | `physical.pmd` | `provinces.pmd` |
|---|---|---|
| Другая стилизация/сглаживание высот, материалы, реки, природные регионы, `PROV` | пересобрать | **не трогать** (`coast_key` не изменился) |
| Береговая линия или озёра изменились (`WBOD`, `GEOR`) | пересобрать | перепривязать: `mapgen provinces --rebind` (подгоняет растр под новую сушу, пересчитывает таблицу; новый файл) |
| Новые границы провинций | не трогать | пересобрать |
| Названия, период действия, достоверность | не трогать | не трогать (контент E4) |

Все производные от физики величины в слое провинций **не хранятся**: `mean_height` вычисляется загрузчиком при сборке `MapData` (один проход по растрам ≈ 30-50 мс [оценка]). Тем самым устаревшего кэша нет. Признак `coastal` определяется растром провинций и `WBOD` (граничит с водоёмом вида «море»), то есть входит в зону действия `coast_key`.

### 1.2. Что остаётся в памяти

В памяти по-прежнему одна структура `MapData` (потребители — `engine`, `apps/spike`, `tools` — не меняются). Новые поля (`water_bodies`, `rivers`, `georef`, `regions`, `provenance`) — в отдельной структуре `MapLayersV2`, необязательной в `MapData` (`std::optional`); `MapData::operator==` и тесты `PMD1` остаются как есть. Для headless-инструментов и ИИ добавляется `load_province_table(path)`: читает только `PTBL` (≈ 15 КБ), растры не распаковываются.

## 2. Контейнер PMD2

### 2.1. Заголовок (64 байта) и таблица чанков

```
 0  4  "PMD2"   (магия = мажорная версия формата)
 4  2  minor           для 2.0 равно 0
 6  2  kind            1 физика, 2 провинции, 3 поправки
 8  4  flags           2.0: 0
12  4  width           базовая сетка, пикселей
16  4  height
20  4  chunk_count     <= 64
24  8  file_size       для раннего обнаружения обрезки
32  8  content_id      FNV-1a64 по (kind, затем для каждого чанка: id, version, instance, raw_hash) в порядке таблицы
40  8  bind_key        kind=1: собственный coast_key; kind=2: coast_key физики, под который построены границы; kind=3: 0
48  8  reserved        2.0: 0
56  8  header_hash     FNV-1a64 по байтам 0..55 и всей таблице чанков
64  chunk_count x 56   таблица чанков (ниже); затем тела чанков подряд, без выравнивания
```

Запись таблицы (56 байт):

```
 0 4 id          четыре ASCII-символа, например 'HGHT'
 4 2 version     версия раскладки именно этого чанка
 6 2 flags       бит0: критический (читатель обязан понимать), бит1: тайловый растр
 8 1 codec       0 сырой, 1 zstd
 9 1 instance    0 = основной; >0 зарезервировано под региональные «заплатки» (Geo-9 #85)
10 6 reserved    0
16 8 offset      от начала файла
24 8 stored_size
32 8 raw_size
40 8 raw_hash    FNV-1a64 канонического содержимого (см. 2.3)
48 8 stored_hash FNV-1a64 хранимых байт (см. 2.3)
```

Чанки записываются в порядке возрастания `(id, instance)` — это даёт детерминированный порядок. Читатель обязан отвергать: перекрывающиеся или выходящие за `file_size` диапазоны, дубликат `(id, instance)`, ненулевые зарезервированные поля при `minor` не выше известного, `chunk_count > 64`, суммарный размер ≠ `file_size`.

### 2.2. Растровый чанк и плитки

Растровый чанк (флаг «тайловый растр») хранит `u8` или `u16` на пиксель:

```
u8  elem_bytes (1|2) | u8 shift (0..3) | u8 tile_log2 (по умолчанию 10) | u8 transform (0 нет, 1 дельта+плоскости)
u32 w | u32 h        размеры растра = ceil(width / 2^shift) x ceil(height / 2^shift)
u32 tile_count       плитки по строкам, слева направо
tile_count x { u32 stored_size; u64 stored_hash }
плитки подряд: zstd( преобразование(плитка) )
```

- `transform=1` повторяет PMD1: построчная дельта по модулю 2^16, затем младшие и старшие байты отдельными плоскостями, но **внутри плитки** (первый пиксель каждой строки плитки — абсолют). Плитки независимы: распаковываются параллельно, читаются по одной (региональная подгрузка, пересборка части) и не требуют целого сырого слоя в памяти.
- `shift > 0` — растр вдвое-вчетверо-ввосьмеро грубее базовой сетки (природные регионы не нуждаются в полном разрешении); потребитель повышает разрешение выбором ближайшего.
- Плитка по умолчанию 1024×1024: для 8192×4096 это 32 плитки по 2 МиБ (`u16`), для 16384×8192 — 128. 2^k задаёт запись, читатель принимает любое k от 6 до 12.

### 2.3. Контрольные суммы

| Сумма | Что покрывает | Когда проверяется |
|---|---|---|
| `header_hash` | заголовок и таблица чанков | всегда, до чтения чего-либо ещё |
| `stored_hash` чанка | для растра — FNV по индексу плиток (в нём лежат `stored_hash` всех плиток; плитка проверяется перед распаковкой); для таблицы-блоба — по хранимым байтам | всегда. Стоимость — один проход по сжатым байтам: ≈ 14 МБ вместо 168 МБ, **≈ 14 мс вместо 172 мс** [оценка по измеренным 1 нс/Б] |
| `raw_hash` чанка | канонические данные: растр — элементы построчно (`u16` как little endian), не зависит от `tile_log2`, дельты и уровня zstd; блоб — сырые байты | в строгом режиме (`mapgen --info --verify`, CI, тесты) и при построении `content_id`. На обычной загрузке из игры не вычисляется |
| `content_id` | идентичность содержимого файла (в том числе при другом сжатии) | сравнивается инструментами и golden-тестами |

FNV-1a остаётся (совместимость с PMD1, нет новой зависимости). Это обнаружение порчи, а не защита от подделки. Криптографические SHA-256 исходных файлов хранятся в `PROV` как данные, вычисляются в `tools/geo`, а не в C++.

**Байты сжатого файла не являются эталоном**: вывод zstd зависит от версии библиотеки. Golden-значения формата — `content_id` и `raw_hash`, а не хеш файла.

### 2.4. Версионирование и совместимость

| Что меняется | Как | Что делает старый читатель |
|---|---|---|
| Новый необязательный чанк, новое поле в конце блоба чанка с длиной, ранее нулевые зарезервированные поля | `minor` +1 | читает; неизвестное пропускает (необязательный чанк) |
| Новый критический чанк, несовместимая раскладка существующего чанка, новый `kind`, другой `codec` | новая версия **чанка** (`version`) либо мажор `PMD3` | ошибка «неподдерживаемая версия чанка/формата» с названием чанка; частично не читает |
| Любое изменение, при котором старые читатели дадут молча неверный результат | мажор (новая магия) | не откроет файл |

Правила:

1. Читатель поддерживает **все** известные версии каждого чанка (старые раскладки не выбрасываются).
2. Читатель принимает файл того же мажора с любым `minor` и версией чанка не выше известной; чанк выше известной версии: критический — ошибка, необязательный — пропуск.
3. Редактирующие инструменты (`mapgen`, перепривязка) сохраняют неизвестные необязательные чанки байт-в-байт и пересчитывают только `header_hash`, `content_id` и `offset`.
4. Читатель `PMD1` не открывает `PMD2` (ошибка 20 «bad magic»): старые сборки новых данных не читают; обратное (новый код читает `PMD1`) гарантируется навсегда.
5. Максимальные размеры проверяются до выделения памяти (как в PMD1: размеры, число чанков, потолки блобов).

## 3. Физический контейнер (`kind=1`)

### 3.1. Чанки

| Id | Крит. | Содержимое |
|---|---|---|
| `GRID` | да | `width, height` (повтор заголовка для самопроверки), `sea_level` (u16, ноль метров), `metres_per_unit_milli` (u32), `seed` (u64, для процедурных, иначе 0), версия набора материалов |
| `GEOR` | да | привязка к Земле (§3.3) |
| `HGHT` | да | высоты, тайловый `u16`, `transform=1` |
| `WBOD` | да | идентификатор водоёма на пиксель, тайловый `u16`; 0 = суша |
| `WTBL` | да | таблица водоёмов (§3.2) |
| `MATL` | да | материалы поверхности, тайловый `u8`; версия чанка = версия перечисления `Material` (сейчас 1, 10 классов); новые классы (болото, песок …) — новая версия |
| `RIVR`, `RVEC` | нет | реки (§3.4) |
| `NREG`, `NRTB` | нет | природные регионы (§3.5) |
| `PROV` | нет¹ | провенанс (§3.6) |
| `NORM` | нет | **зарезервирован**: предрасчёт нормалей/затенения (ADR-0004 §3 п. 5); пока нормали вычисляются `compute_normals` |

¹ Необязателен для чтения, но обязателен для карт, собранных из реальных данных (проверка в `tools/geo`, §6).

### 3.2. Маски воды

`WBOD` (u16): 0 — суша, k > 0 — водоём k. `WTBL` — по записи на водоём: `u16 id`, `u8 kind` (1 океан/море, 2 озеро, 3 внутреннее море — вид «солёного озера» вроде Каспия, ❓ уточнить словарь при Geo-5), `u8 flags`, `u16 surface_level` (в единицах высоты — **уровень зеркала**; для морей равен `sea_level`, для Каспия ниже, для Байкала выше), `u32 area_px`, ключ (`u16` длина + ASCII), число байт пока ≤ 40 на запись.

Инварианты (`validate_physical`): `HGHT[p] ≤ surface_level` для пикселя водоёма (ложе не выше зеркала; озёра плоские — ложе может быть равно зеркалу, если глубины в DEM нет); каждый водоём 4-связен; id в растре ≤ числа записей; `area_px` совпадает с растром. **Суша — это `WBOD == 0`**; сравнение высоты с `sea_level` для этого больше не применяется (иначе земля ниже нуля метров у Каспия считалась бы водой). Для `PMD1` правило «вода ⇔ высота ≤ sea_level» выполняется по построению (§5).

### 3.3. Проекция и географическая привязка (`GEOR`)

Все числа целые (как `metres_per_unit_milli` в PMD1): файл бит-в-бит воспроизводим, а `sim` и сохранения не касаются плавающей точки. Чанк:

```
u16 version
u8  projection   0 нет (процедурная карта), 1 Альберса (равновеликая коническая), 2 конформная коническая Ламберта,
                 3 Ламберта азимутальная равновеликая, 4 равнопромежуточная цилиндрическая   (❓ итоговый список — по Geo-5, #81)
u8  datum        0 нет, 1 WGS84
i32 lat_origin_udeg, lon_central_udeg, lat_std1_udeg, lat_std2_udeg      микроградусы
i64 false_easting_mm, false_northing_mm                                   миллиметры
i64 origin_x_mm, origin_y_mm        координаты верхнего левого угла пикселя (0,0) в плоскости проекции
i64 pixel_size_x_mm, pixel_size_y_mm   > 0; строка 0 — север
i32 bbox_min_lon_udeg, bbox_max_lon_udeg, bbox_min_lat_udeg, bbox_max_lat_udeg   охваченная область (справочно)
u32 epsg         0 = своя проекция
str proj_text    u16 длина + UTF-8, строка PROJ/WKT для внешних инструментов (справочно, источник истины — целые поля)
```

Ошибка округления до миллиметра на 10 000 км — порядка 10^-9 относительная и пренебрежима. Антимеридиан решается выбором `lon_central_udeg` (например, около 100° в. д. — Чукотка получается ≈ +90° от центра и не требует «склейки»); флага зацикливания по X нет. Прямая и обратная проекции для выбранных видов реализуются в `mapdata` на формулах Альберса/Ламберта (≈ 100 строк на вид), без PROJ; результат нужен UI (подсказки о широте/долготе) и инструментам, не `sim`. Расстояния и площади для игры берутся из таблицы провинций (§4), посчитанной офлайн.

Для процедурной карты: `projection=0`, размеры пикселя 0 (неизвестно); игра использует прежние заданные параметры геометрии.

### 3.4. Реки

- `RIVR` — тайловый `u8`: 0 нет реки, 1..255 — ранг/класс ширины русла, на сушевых пикселях и мелководье дельт; **русло врезано в `HGHT` на стадии 2** (ADR-0004 §3 п. 3), то есть `RIVR` только метка.
- `RVEC` — векторные русла для ленточных мешей (ADR-0003 P3): `u32 river_count`, на реку: `u16 id`, `u8 rank`, `u32 point_count`, затем точки `i32 x, i32 y` в 1/16 пикселя + `u8 width_class` на вершину; текстовый ключ. Оценка: 3-10 тыс. рек, 100-300 тыс. вершин → 1-3 МБ сырых, ≈ 0,5-1,5 МБ после zstd [оценка, проверить на данных Geo-3].

Реки из DEM (решение ADR-0004: HydroRIVERS по умолчанию не используется, #96) получают те же чанки; формат не зависит от источника.

### 3.5. Природные регионы

`NREG` — тайловый `u8`, допускается `shift = 2` (2048×1024: ≈ 2 МиБ сырых, после zstd десятки КБ). `NRTB` — таблица: `u8 id`, `u8 kind` (климатическая зона / орографический район), ключ-строка (например `west-siberian-plain`), справочное имя на английском. Отображаемые русские названия, климатические эффекты, события — контент E4 по ключу; формат хранит только разбиение территории. Назначение: материалы, растительность, погодные и сезонные параметры рендера, зонные события.

### 3.6. Провенанс (`PROV`, есть в обоих контейнерах)

Блоб (все строки — `u16` длина + UTF-8):

```
u16 provenance_version
str builder                         например "mapgen <git sha12>"; не должен содержать пути и имена машин
u32 manifest_version                версия формата data-sources/geodata.manifest.json
u16 source_count
  { str source_id                   id из манифеста (copernicus-dem-glo30, natural-earth-10m-physical …)
    str source_version              версия/дата набора из манифеста
    u16 file_count { str path; u8[32] sha256 } }          файлы манифеста, реально использованные
u16 step_count  { str step_id; u64 params_hash }          "reproject:albers-v1", "resample:8192x4096", "stylise:v3", …
u16 correction_count { str correction_id; u64 content_id }    применённые поправки (§6)
```

Хеш самого манифеста не записывается (он меняется при любом добавлении источника и делал бы каждую карту «устаревшей»); вместо него — id и SHA-256 использованных файлов. Тексты атрибуции в PMD не хранятся: экран «Об игре» берёт список `source_id` из `PROV` и тексты из манифеста.

## 4. Контейнер провинций (`kind=2`)

| Id | Крит. | Содержимое |
|---|---|---|
| `PIDX` | да | идентификатор провинции на пиксель, тайловый `u16`, `transform=1`; 0 = вода |
| `PTBL` | да | таблица провинций (ниже) |
| `PROV` | нет | провенанс геометрии: как получен растр (источники — оцифровка границ, id из манифеста) |

`PTBL`, запись: `id` (u16, плотный номер 1..N), **`key`** (строка, уникальный неизменный ключ, `[a-z0-9-]`; ❓ #201), `color_rgb`, `area_px`, `bbox`, `centroid`, `coastal`, соседи (`u16 id + u32 length_px`), и новые производные от привязки (`area_m2` u64, центроид `lon/lat` в микроградусах, длина границы в метрах у соседей — считаются офлайн по `GEOR`, чтобы `sim` брал расстояния и площади из таблицы целыми числами; список потребителей уточняет E21/E9). `mean_height` не хранится (§1.1). В заголовке — `bind_key = coast_key` физики.

Идентичность. Плотный `id` — индекс в растре и таблице, он может меняться между сборками границ. Контент, сценарий и всё внешнее ссылаются на **ключ**; соответствие `ключ → id → ProvinceId мира` строит загрузчик сценария. Политика сохранений и совместимости карт — ❓ #201.

Инварианты `validate_provinces(physical, provinces)`: все инварианты `validate_map` (связность областей, симметрия соседства, уникальные цвета, согласованность таблицы с растром), «провинция ≠ 0 ровно там, где `WBOD == 0`», `bind_key == physical.coast_key`, уникальность и допустимость ключей.

## 5. Миграция PMD1 → PMD2

`migrate_pmd1(const MapData&) -> {PhysicalLayer, ProvinceLayer}` — чистая детерминированная функция, без случайности и времени.

Физический слой из карты `M` (ширина `W`, высота `H`, `sea_level = s`):

| Чанк PMD2 | Получается из PMD1 |
|---|---|
| `GRID` | `W, H, s, metres_per_unit_milli, seed`, версия материалов 1 |
| `GEOR` | `projection=0`, `datum=0`, размеры пикселя 0, остальное 0, `proj_text=""` |
| `HGHT` | `M.heights` без изменений |
| `WBOD` | `1` в каждом пикселе с `heights[i] ≤ s`, иначе `0` (в PMD1 других вод нет) |
| `WTBL` | единственная запись: `id=1, kind=1 (море), surface_level=s, area_px = число таких пикселей`, ключ `sea` |
| `MATL` | `M.materials` без изменений |
| `PROV` | `source_count=0`, шаг `migrated-from-pmd1` с `params_hash` = FNV-1a64 четырёх `hash` секций PMD1 (по порядку) |
| реки, регионы | отсутствуют (необязательные, загрузчик подставляет пустые) |

Слой провинций: `PIDX = M.provinces`; запись `PTBL` каждой провинции копирует `id, color_rgb, area_px, bbox, centroid, coastal, neighbors`, `key = "p" + десятичный id с дополнением нулями до 4 знаков` (`p0001`; ❓ #201), метрические поля нулевые (нет привязки), `bind_key = coast_key` построенной физики.

Обратный путь «загрузить PMD2 как `MapData`»: высоты, провинции и материалы берутся как есть; `mean_height` вычисляется как `sum(heights) / area_px` (целочисленное деление, тот же алгоритм, что `compute_province_stats` в `map_validate.cpp`); `province_list` собирается из `PTBL`; `seed`, `sea_level`, `metres_per_unit_milli` — из `GRID`.

**Критерий корректности (golden-тест):** `load(migrate(M)) == M` побитово для каждой карты `M`, прошедшей `validate_map`. На любом входе, нарушающем «вода ⇔ высота ≤ s», миграция возвращает ошибку, а не искажает данные.

### 5.1. Чтение PMD1 «навсегда»

`load_map(path)` читает первые четыре байта: `PMD1` → существующий `read_map_file`/`deserialize_map` **без изменений** (код, коды ошибок, тесты, `roundtrip.cmake`); `PMD2` → новый путь, который принимает `physical.pmd` с соседним `provinces.pmd` из того же каталога. Игра и спайк используют `load_map`; процедурная генерация, `mapgen --out` и все существующие тесты по-прежнему работают на `PMD1`. Запись `PMD1` не удаляется и не ломается добавлением `PMD2`.

### 5.2. Тесты формата и фикстуры

В репозиторий (в `tests/data/maps/`, вне `assets/`, общим объёмом не более 100 КБ) коммитятся малые **файлы-фикстуры**, а не только генерация на лету:

| Фикстура | Проверяет |
|---|---|
| `v1_tiny.pmd` (96×48, 8 провинций, seed 3) | неизменность чтения `PMD1`; вход миграции |
| `v2_tiny_physical.pmd`, `v2_tiny_provinces.pmd` | чтение эталонных `PMD2`; озеро с уровнем ≠ `sea_level` и река в составе |
| `v2_unknown_optional.pmd` | неизвестный необязательный чанк и больший `minor` читаются, чанк пропущен и сохраняется при пересохранении |
| `v2_unknown_critical.pmd`, `v2_future_chunk_version.pmd` | ошибка с указанием чанка |
| `v2_stale_bind.pmd` | пара из чужого берега → ошибка привязки |

Golden-значения (`content_id`, `raw_hash` каждого чанка, `coast_key`) лежат в тесте и изменяются только осознанно. Запись PMD2 проверяется по `content_id` и обратным чтением, **не побайтовым сравнением файла** (вывод zstd зависит от версии библиотеки). Дополнительно: цикл «битый бит в каждой области файла → ошибка, не падение», проверка потолков размера, нулевые размеры плиток, `tile_log2` вне диапазона.

## 6. Исторические корректировки и как они присоединяются

ADR-0004 §6: исторические поправки (убрать водохранилища XX века и плотины, вернуть русла и поймы, прежнюю береговую линию и дельты, не включать современные города и дороги) не должны быть «запечены» в физический слой без следа. Решение:

1. Поправки — **отдельные входные контейнеры** `kind=3` (по одному на тему: `volga-reservoirs`, `neva-delta` …). Каждый содержит: `id` поправки; ссылки на **id источников из манифеста** (и опционально на факты в `docs/dev/…`), обоснование, степень достоверности (документировано / реконструировано / приблизительно), порядок применения; полезная нагрузка — маска и знаковая дельта высот (`i16`, тайловый), переопределение водоёмов (`WBOD`/`WTBL`-патч), правки русел (`RIVR`/`RVEC`-патч). Область действия — прямоугольник базовой сетки.
2. Применяются **на стадии 2 сборки** (`mapgen import`) детерминированно в заданном порядке после ресемплинга и до вычисления материалов; результат — обычный `physical.pmd`.
3. `physical.pmd` в `PROV` записывает список применённых поправок (`correction_id` + `content_id` контейнера поправки). Любой набор поправок воспроизводим из репозитория; смена набора меняет `content_id` физики и, если изменился берег, `coast_key` (тогда провинции перепривязываются, §1.1).
4. Игровой код поправок не читает: в поставку идёт только результат. Хранить входные поправки в Git можно всегда (они малы и меняются по темам); решение по хранению больших файлов — #200.
5. Проверка в CI без сети (`tools/geo`): все `source_id` из `PROV` существуют в манифесте; для карт с `PROV` вида «реальные данные» источники имеют `status: ready` (или явное исключение); `correction_id` присутствуют в каталоге поправок.

Исторические данные, которые **не** относятся к PMD: административные единицы 1703 года, периоды действия, источник и достоверность границ, названия, поселения — контент E4, ссылаются на ключ провинции (ADR-0004 §2, Geo-7 #83).

## 7. Оценка размера и скорости загрузки полной карты

Полная карта: ~400 провинций, 8192×4096 (рабочая гипотеза) и 16384×8192 (региональные тайлы, Geo-9 #85).

### 7.1. Размер

База — измеренный PMD1 (таблица замеров), добавки — оценки.

| Часть | 8192×4096 | Основание |
|---|---|---|
| Высоты (`HGHT`) | **13,6 МБ** на процедурных данных; **для реальных 10-25 МБ** [оценка: 4-8 бит/пиксель на суше при ≈ 55% суши и нулях на море; квантование высот до ≥ 1 м/ед. убирает ~3 бита шума] | измерено 3,2 бита/пиксель для процедурной карты; реальный DEM шумнее; уточняет Geo-5/Geo-3 |
| Растр провинций (`PIDX`) | 0,4-0,5 МБ | измерено 0,43 МБ |
| Материалы (`MATL`) | 0,3-0,5 МБ | измерено 0,32 МБ |
| Водоёмы (`WBOD`+`WTBL`) | 0,05-0,4 МБ | похож на `PIDX` |
| Реки (`RIVR`+`RVEC`) | 0,5-2 МБ | §3.4 |
| Регионы (`NREG`, shift 2) | < 0,1 МБ | §3.5 |
| Таблицы, `GEOR`, `PROV` | < 0,1 МБ | измерено 15 КБ для таблицы |
| Накладные расходы PMD2 (заголовок, таблица чанков, индексы плиток) | < 10 КБ | §2 |
| **Итого** `physical.pmd` | **≈ 12-30 МБ** | |
| `provinces.pmd` | **≈ 0,5 МБ** | |

Для 16384×8192 — примерно ×3 по высотам (измерено: 40 МБ против 13,6 МБ на процедурной карте): **≈ 35-90 МБ**. Распаковка zstd на уровне 19 при сборке релиза даёт ещё ≈ 10-20% [не измерено; скорость распаковки от уровня почти не зависит]. Вклад `provinces.pmd` — единицы процентов, **что и делает перепривязку границ почти бесплатной для репозитория**; пересборка физики — десятки МБ за раз (отсюда вопрос #200).

### 7.2. Скорость загрузки

| Этап (8192×4096) | PMD1 (измерено) | PMD2, один поток (оценка) | PMD2, 8 потоков (оценка) |
|---|---|---|---|
| чтение файла | 17 мс | 17 мс | 17 мс |
| проверка сумм | 172 мс (по сырым) | ≈ 15 мс (по сжатым) | ≈ 15 мс |
| распаковка zstd | 133 мс | 133 мс | ≈ 20 мс |
| декодирование дельты | 205 мс | ≈ 80 мс (строки без деления на каждом пикселе) | ≈ 15 мс |
| `mean_height`, сборка `MapData` | в файле | ≈ 40 мс | ≈ 40 мс |
| реки, регионы, вода (распаковка) | нет | +20-40 мс | +10 мс |
| **Итого** | **0,51 с** | **≈ 0,3-0,35 с** | **≈ 0,12-0,15 с** |

16384×8192: PMD1 — 2,0 с (измерено); PMD2 — ≈ 1,2-1,4 с на одном потоке, ≈ 0,4-0,5 с на 8 потоках (оценка). Оба варианта значительно лучше бюджета «загрузка карты ≤ 10 с» (ADR-0003 §3). Реальные цифры PMD2 снимает Geo-17 (#209); если оценка не подтвердится, ничто в формате не мешает.

Память при загрузке: без промежуточных копий секций — файл + итоговые слои: для 8192×4096 пик ≈ 25 МиБ (файл + плитки в работе) сверх итоговых слоёв в 160 МиБ, тогда как у PMD1 сверх слоёв ≈ 140 МиБ (файл + сырая секция + декодированный слой). Видеопамять и CPU-копии — по ADR-0003.

| Атрибуция и тексты лицензий | манифест `data-sources/`, экран «Об игре» |
| Режимы карты, палитры | `engine`/`game` (уже так) |
| Тайловые сжатые текстуры для GPU (BC), детальные текстуры материалов | производные данные рендера, не PMD |

Правило ADR-0004 §2 сохраняется: физический слой не знает о владельцах; симуляция не знает о пикселях. `mapdata` по-прежнему зависит только от `core`.

## Последствия

- Появляется возможность менять границы и рельеф независимо; перепривязка границ к новому берегу — отдельный явный шаг.
- Формат расширяем без поломки читателей (необязательные чанки, `minor`), а миграция `PMD1` строго проверяема побитовым round trip.
- Загрузка не медленнее PMD1 и примерно в 3-4 раза быстрее; в формате заложены плитки (параллелизм, региональные заплатки Geo-9).
- Усложняется загрузка пары файлов (проверка `bind_key`, `load_map_set`), растёт число видов ошибок.
- Требуется работа: 8 задач ниже. Формат нельзя считать окончательным, пока не решены Geo-5 (проекция), #200 (хранение), #201 (ключи).
- Снимок размера на реальных данных появится только после Geo-3; оценки §7 пересматриваются тогда же.

## Отклонённые альтернативы

- **Расширить PMD1 «на месте»** (новые секции за счёт `flags`/`section_count`). Старые читатели отвергают такой файл, слои остаются слитыми; именно поэтому нужна новая магия.
- **Один контейнер PMD2 со всеми слоями**, с возможностью заменять секции. Просто, но пересборка границ всё равно переписывает 15-90 МБ в Git; двух файлов достаточно и они независимо версионируются.
- **Привязывать провинции к полному содержимому физики** (`content_id`). Любая правка материалов или высот сделала бы границы «устаревшими»; ключ берега устраняет это ложное срабатывание.
- **Хранить `mean_height` и другие производные от рельефа в провинциях.** Кэш молча устаревает; пересчёт на загрузке дешёв (≈ 40 мс).
- **GeoTIFF/PNG16/NetCDF как контейнер игры.** Тяжёлые зависимости (GDAL/libtiff) в рантайме, нет нужных нам контрольных сумм и привязки провинций; GDAL остаётся внешним инструментом стадии 1 (ADR-0004).
- **Внешний сжимающий кодек вместо zstd** (например, Blosc, lz4) или специализированный кодек для высот. Новая зависимость; zstd с дельтой уже даёт 3-4 бита/пиксель на процедурных данных. Пересмотреть, если реальные высоты окажутся тяжелее оценки (§7).
- **Криптографическая сумма (SHA-256) для файлов PMD.** Нужна только для внешнего провенанса (хранится как данные); для обнаружения порчи FNV-1a достаточен, а реализация в C++ потребовала бы кода или зависимости.
- **Хранить проекцию как PROJ/WKT-строку и разбирать в игре.** PROJ — зависимость; целочисленные параметры плюс справочная строка дают то же без неё.
- **Float в файле (метры, градусы).** Нарушает идею воспроизводимости бит-в-бит между платформами; целые мм и микроградусы достаточны.

## Решения владельца (2026-11-08)

- Хранение (#200): физический слой **вне Git**, в Git манифест с SHA-256 и малый `provinces.pmd`.
- Ключи провинций (#201): **обязательное поле** PMD2; сохранение хранит только `ProvinceId` мира, соответствие «ключ → ProvinceId» строится при загрузке сценария.
