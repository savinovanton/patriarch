# Формат сохранений: справочник

Статус: **принят** вместе с [ADR-0011](../adr/0011-saves.md) (E13-T01, 2026-11-13). Это единый справочник по всему, что лежит на диске и что делает игру «продолжаемой»: контейнер `PSV`, раскладка мира (`kStateSchema`), реестры разделов и тегов команд, формат реплея и журнала команд, политика версий и совместимости, каталог, имена файлов, автосохранения. Раньше раскладка была размазана по ADR-0006 и комментариям `src/sim/world_io.cpp`, `save.hpp`, `replay.hpp`.

Единственный источник правды по номерам разделов и тегов команд — **этот документ**: новый раздел или тег добавляется строкой в таблицу §5/§6 в том же PR, что и код (см. чек-листы §7.4).

Связано: ТЗ FR-SAVE-1/2, NFR-PERF-5/6, NFR-DET-1; ADR-0001, ADR-0006 (D5, D6), ADR-0011; [E13](../epics/E13-saves.md); решения владельца #357 (каталог), #358 (автосохранения).

Условные обозначения: «сейчас» — состояние `main` на 2026-11-13; **[T0N]** — какая задача E13 это реализует; `[предл.]` — число/значение предложено агентом и меняется в данных или параметрах без пересмотра формата.

## 1. Какие форматы есть

| Формат | Магия / слово | Версия сейчас | Что хранит | Где определён | Читается |
|---|---|---|---|---|---|
| Контейнер сохранения | `PSV1` + `u16 format_version` | **2** (`kSaveFormatVersion`, с T02; версия 1 — `kSaveFormatVersionLegacy`) | сжатая полезная нагрузка + (v2) сводка | `src/sim/save.cpp` | всеми версиями ≥ 1 навсегда |
| Состояние мира | слово `u32 schema` в начале полезной нагрузки | **11** (`World::kStateSchema`) | ядро + блок разделов | `src/sim/world_io.cpp`, `world_economy_io.cpp` | всеми схемами 1…текущая |
| Раздел блока расширения | `u16 id`, `u16 version` | по таблице §5 | часть состояния мира | читатель каждого раздела | версиями из таблицы §5 |
| Реплей | `PRP1` + `u16 version` | **1** (`kReplayFormatVersion`) | входные команды и контрольные хеши | `src/sim/replay.cpp` | версия 1 |
| Журнал команд | `PCL1` + `u16 version` | **1** (`CommandLog::kFormatVersion`) | принятые/отклонённые команды | `src/sim/command_log.cpp` | версия 1 |
| Кодирование одной команды | тег (с T03 — varint) + `u32 actor` + тело | общее для `PSV` (отложенные команды), `PRP1`, `PCL1` | | `write_command`/`read_command` | |
| Настройки игрока | `settings.pd` (текст `.pd`) | ключ `settings_version = 1` **[T09]** | не относится к партии | `src/data` | см. §9.7 |

Все целые — little endian. Имена и перечисления в файлах — числа, не строки (стабильны навсегда). Хеши — FNV-1a 64 (`core::HashStream`).

Главный принцип: **партия = (контейнер → полезная нагрузка → `World::save_state` + отложенные внутренние команды)**. Системы не хранят постоянного состояния вне `World` (AGENTS.md §5.3), поэтому любая загрузка продолжает ровно с того места, где остановилась.

## 2. Контейнер `PSV`

### 2.1 Версия 1 (читается всегда, пишется до T02)

```
off  size
  0    4  "PSV1"                      семейство формата, не меняется
  4    2  u16 format_version = 1
  6    2  u16 flags = 0               любой установленный бит = ошибка
  8    8  u64 uncompressed_size       ≤ 2 ГиБ (kMaxPayload)
 16    8  u64 payload_hash            FNV-1a 64 несжатой нагрузки
 24    8  u64 compressed_size         обязан равняться остатку файла
 32    …  zstd-кадр
```

Полезная нагрузка (до сжатия): `World::save_state()` (§3), затем `u32 pending_count` и столько команд (`write_command`) — команды, которые системы выпустили, но мир ещё не применил (внутренние). Хвостовые байты — ошибка.

### 2.2 Версия 2 — с блоком сводки **[T02]**

Версия 2 = версия 1 + **несжатая сводка** между заголовком и zstd-кадром. Магия остаётся `PSV1`: старая сборка, получив файл версии 2, видит `version > 1` и показывает **«сохранение создано более новой версией игры»** (код 22) — ровно то сообщение, которое нужно (см. ADR-0011 «Отклонённые альтернативы»: другая магия дала бы «не сохранение Patriarch»).

```
off  size
  0    4  "PSV1"
  4    2  u16 format_version = 2
  6    2  u16 flags = 0               биты 0…15 зарезервированы
  8    4  u32 summary_size            1 … 16 384 (kMaxSummary)
 12    8  u64 summary_hash            FNV-1a 64 байт сводки
 20    8  u64 uncompressed_size
 28    8  u64 payload_hash
 36    8  u64 compressed_size
 44    summary_size   сводка (§2.3)
 44+summary_size …     zstd-кадр (compressed_size байт, до конца файла)
```

Полезная нагрузка, её хеш, zstd и порядок проверок — как в версии 1; **раскладка мира и `kStateSchema` версией контейнера не затрагиваются**. Сводка **не** входит в `payload_hash` (иначе переименование сохранения потребовало бы перепаковки): у неё свой `summary_hash`. Читатель сводки читает первые 44 + `summary_size` байт (≤ 16.4 КиБ) и **не касается zstd**: цель — единицы миллисекунд на файл, скан 1000 файлов ≤ 100 мс (бюджет E13 §6.4).

Писатель всегда пишет последнюю версию; «сохранить в старом формате» не существует. Читатель читает все версии ≥ 1 всегда (политика §7.1).

### 2.3 Сводка (summary)

Последовательность полей **`u16 key | u16 length | bytes`** по возрастанию `key`, без повторов; неизвестный ключ **пропускается** (так сводка растёт без смены версии контейнера); отсутствие обязательного ключа — повреждённая сводка. Все строки — UTF-8 без нулевого байта, не длиннее указанного; число полей ≤ 64.

| key | Поле | Тип | Обяз. | Смысл |
|---:|---|---|---|---|
| 1 | `game_version` | UTF-8 ≤ 64 Б | да | версия сборки-автора; **только для показа и диагностики**, совместимость по ней не решается |
| 2 | `state_schema` | u32 | да | слово схемы из полезной нагрузки; при полной загрузке обязано совпасть, иначе «повреждено» |
| 3 | `scenario` | UTF-8 ≤ 64 Б | да | идентификатор сценария (`m1`, позже — сценарии E30) |
| 4 | `content_hash` | u64 | да | хеш совместимости набора контента (`ContentRegistry::content_hash()` = `economy().meta.rules_hash`); **0** — партия без набора контента (демо, `dynasty`), проверка пропускается |
| 5 | `player_dynasty` | u32 | да | `DynastyId` рода игрока; `0xFFFFFFFF` — режим «наблюдатель» (нет игрока) |
| 6 | `dynasty_key` | UTF-8 ≤ 64 Б | нет | ключ данных рода («golitsyn»); текст берёт UI из таблиц локализации |
| 7 | `head_name` | UTF-8 ≤ 96 Б | нет | имя главы рода, **уже разложенное** на момент сохранения (для несовместимых файлов, у которых таблицы имён чужие) |
| 8 | `head_age` | u8 | нет | возраст главы, лет |
| 9 | `date` | i32 | да | игровая дата (`Date::days()`) |
| 10 | `treasury` | i64 | нет | казна рода игрока, копейки; нет — экономика выключена |
| 11 | `goal_key` | UTF-8 ≤ 64 Б | нет | ключ текущей цели (E30) |
| 12 | `goal_progress_ppm` | u32 | нет | прогресс цели, 0…10⁶ |
| 13 | `play_time_s` | u64 | да | реальное игровое время партии, секунды (не время симуляции) |
| 14 | `kind` | u8 | да | 0 ручное, 1 авто (ротация), 2 быстрое, 3 авто при выходе |
| 15 | `name` | UTF-8 ≤ 256 Б, 1…64 символа | нет | имя, данное игроком (ручные); у автосохранений нет |
| 16 | `saved_at` | i64 | да | Unix-время UTC в секундах, часы ОС; **не читается симуляцией**, нужно для сортировки «новые сверху» и выбора слота ротации |
| 17 | `world_hash` | u64 | да | `WorldHash::total` на момент сохранения: диагностика и матрица «сохранил → продолжил» (T12); **не** сверяется при загрузке (миграция может законно его изменить) |
| 18 | `tick` | i64 | да | `calendar.tick_count()` |
| 19 | `ironman` | u8 | нет | зарезервировано под M2 (режим «без перезагрузок»); в M1 всегда 0 или нет |
| 20 | `preview` | bytes | нет | зарезервировано под скриншот-превью M2 (E5/E26) |
| 21…63 | — | | | свободны для сводки; выдаёт T02/следующие эпики строкой в этой таблице |

**Реализовано (T02):** `SaveSummary`, `summary_from_world(world)` (схема, дата, тик, хеш набора контента, `world_hash`, версия сборки; **часы не читаются** — `saved_at`, `play_time_s`, сценарий, род игрока, глава, казна, вид и имя заполняет вызывающий, T05), `serialize_save(world, pending, summary)` и прежняя перегрузка без сводки (минимум из мира, детерминированно), `read_save_summary(bytes[, file_size])` / `read_save_summary(path)` (читает не больше 44 + 16 КиБ, zstd не трогает; для версии 1 возвращает `SaveInfo` без сводки — каталог показывает «Старый»), `SaveData::summary` и `SaveData::format_version` у `deserialize_save` (для версии 1 — минимум из мира, `game_version` пуст). Писатель **подрезает** строки до пределов по границе символа, выбрасывает NUL и невалидный UTF-8, ограничивает прогресс цели 10⁶ и неизвестный вид приводит к ручному, а превью, которое не помещается в 16 КиБ, не пишет: он не способен создать файл, который не прочтёт читатель. Известные ключи 1…20 читаются строго (длины, диапазоны), неизвестные пропускаются. Порядок проверки схемы: п. 7 §2.4 выполняется после чтения мира, как записано; отказ 28 — раньше разжатия.

Строка 7 хранит уже готовый текст сознательно: сводка — «лицо» файла, а таблица имён зависит от набора контента, которого у несовместимого файла может не быть. Язык интерфейса на это поле не влияет (имя — собственное).

### 2.4 Порядок проверок при загрузке **[T07]**

1. Заголовок: магия, версия, флаги, размеры (`compressed_size` = остаток файла).
2. Сводка (v2): `summary_hash`, обязательные поля. Здесь уже решается совместимость (§8): схема, набор контента.
3. Размеры: `uncompressed_size ≤ kMaxPayload`; защита от «бомбы zstd» — буфер выделяется по заявленному размеру после его проверки.
4. `core::decompress` → `payload_hash`.
5. `World::load_state` (схема ≤ текущей; миграции; `check_invariants`).
6. Отложенные команды; хвостовых байтов нет.
7. Сверка `summary.state_schema` с словом схемы нагрузки.
8. Совместимость набора контента для сценария с контентом (как `save_error` в `simcli`): `rules_hash` мира = хеш загруженного набора.
9. Сборка сессии (`assemble_session`, E30-T10) — те же системы в том же порядке, что у новой партии.

Для файла версии 1 пункты 2 и 7 пропускаются; сводки нет (§9.4).

### 2.5 Коды ошибок

Существующие коды `core::Error` (не меняются): контейнер 20 (формат/размеры/флаги), 21 (нет пути миграции), 22 (версия новее), 23 (хеш нагрузки), 24 (отложенные команды); диск 30…34 (открытие/запись/переименование/чтение); мир 10; реплей 40; журнал команд 1. **T02** добавляет коды контейнера **25…29** (сводка повреждена, нет обязательного поля, сводка слишком велика, версия схемы в сводке новее, расхождение схемы сводки и нагрузки), **T05** — коды диска **35…39** (нет места, нет прав, имя/путь недопустимы, занят другим процессом, прочее). Конкретные номера и тесты на каждый — в задачах; номера кодов не показываются игроку (§8.2).

**Реализовано (T02), коды сводки:** 25 — сводка повреждена (хеш, обрыв поля, ключи не по возрастанию/повтор/ключ 0, больше 64 полей, неверная длина или значение известного поля, не UTF-8, NUL, пустая сводка); 26 — нет обязательного поля; 27 — `summary_size` > 16 384 (определяется по одному заголовку); 28 — `state_schema` в сводке новее `kStateSchema` (отказ до разжатия; `read_save_summary` такой файл **читает**, чтобы список мог его показать); 29 — схема сводки и слово схемы нагрузки не совпали. Ошибки zstd при разжатии идут как есть кодами `core::decompress` (1 — ошибка zstd, 2 — размер не совпал); T07 сводит их к «повреждено». Версия 0 и версия > 2 — код 22 (версия судится **до** флагов и остального заголовка: новый писатель мог их переложить).

## 3. Полезная нагрузка: `World::save_state()`

```
u32 schema                       1 … kStateSchema
ядро (схема 1)                   часы, потоки ГСЧ, рода и их списки, провинции,
                                 таблица слотов персонажей + запись E1 на каждый слот
-- блок расширения, схема ≥ 2 --
u32 world_flags                  бит 0 = режим династии, остальные 0
u16 section_count                ≤ kMaxSections (96, с T03; до него было 32)
section_count × { u16 id | u16 version | u32 byte_length | bytes }   id строго по возрастанию
```

За `save_state()` в полезной нагрузке `PSV` идут отложенные внутренние команды (§2.1); сам `save_state()` их не знает.

Правила читателя (подробно — ADR-0006 D6): каждый раздел читается отдельным `ByteReader` на `byte_length` байт и **обязан быть израсходован полностью**; неизвестный `id`, неподдерживаемая `version`, раздел с `min_schema` больше схемы файла, нарушение порядка, `schema > kStateSchema` — **ошибки загрузки, не падения**; отсутствие раздела = состояние по умолчанию; «пустое не пишется». Каждый счётчик и ссылка проверяются до выделения памяти (`plausible`, `id < capacity`, перечисления в известных значениях). После чтения — `rebuild_derived_indexes()` и `check_invariants()`; непустой отчёт — ошибка. Производные данные (список живых, дети, очередь жизненных событий, накопитель архива) **не хранятся**.

## 4. Реплей и журнал команд

- **`PRP1`:** `"PRP1" | u16 version | u64 seed | i32 start_day | u64 scenario_id | i64 total_ticks | i64 checkpoint_interval | u32 command_count | { i32 day | command }* | u32 checkpoint_count | { i64 tick | 6 × u64 hash parts }* | u64 checksum`. Реплей — полный вход прогона (сид, принятые внешние команды, контрольные хеши); играется на **той же сборке и том же сценарии**, версия реплея старой сборки после изменения симуляции воспроизведена быть не обязана (это инструмент тестов и отладки, не пользовательский формат; экспорт реплея из сейва — M2/E27).
- **`PCL1`:** `"PCL1" | u16 version | u32 count | { i32 date | u8 source | u8 outcome | command }* | u64 checksum` — журнал всех обработанных команд, нужен тестам и отладке; **в сохранение партии не входит**, запись в сейв не попадает.
- **Команда:** `tag | u32 actor | тело`. Тег — см. §6 (с T03 — varint; для тегов < 128 байты прежние). Тело — по виду команды (`Writer`/`read_command` в `command_log.cpp`). Внутри `PSV` команды — это список отложенных внутренних команд.

Правила совместимости реплея и журнала — §7.2.

### 5.1 Ёмкость: `kMaxSections = 32 → 96` **[T03]**

В `world_io.cpp` лимит `kMaxSections = 32` — это проверка здравого смысла для `section_count`, а не размер реестра. Одновременно в файле присутствуют только **непустые** разделы, но в худшем случае плана: E7 7 + E9 9 + E8 ≤ 16 + E11 ≤ 16 + E10 8 + E12 12 + E30 8 ≈ **76 > 32**; E8 и E11 доводят счёт до порога раньше, чем стартует E10. Решение:

- **`kMaxSections = 96`** (= первый нераспределённый id), `static_assert`, что все id таблицы `kSections` меньше этого значения; `section_count ≤ 95` фактически. Очень большое значение не нужно: неизвестный `id` и так отвергается, а память ограничена `byte_length`/`plausible`.
- **Порядок:** T03 выполняется **до** E11-T03 и E10-T03 (до первой задачи, чей счёт разделов может превысить 32); после E8-T03 и в любом месте между W-задачами. Задача меняет **только константу и проверку**, байты существующих сейвов и `kExpectedSaveBytesHash` не меняются, `kStateSchema` **не поднимается**: файл со >32 разделами возможен лишь у сборки, которая добавила схему новее, а слово схемы читается первым — старая сборка скажет «создано более новой версией», а не «неверное число разделов».
- **Реализовано (T03):** `kMaxSections = 96`, `static_assert` на id таблицы `kSections`, ридер дополнительно проверяет `plausible(section_count, 8)` (заголовок раздела — 8 байт). Реальных разделов сейчас 16, поэтому тест «40 / 96 / 97 разделов» использует **тестовый хук** `pat/sim/state_test_hooks.hpp` (`ScopedTestSections`: писатель добавляет N разделов с id ≥ 41 по одному `u32`, ридер принимает ровно такие; по умолчанию выключен и байты не меняет).
- Эпик, которому нужны `id ≥ 96`, поднимает лимит в своей W-задаче по тому же правилу (кратно 32) и вносит блок в таблицу выше.

### 5.2 Правило выдачи блоков

1. Эпик получает блок в таблице §5 **до первой строки кода** (в ADR/спецификации эпика, E*-T01) и вносит его сюда PR'ом документа.
2. Блок кратен 4 по размеру, ≥ 8 id; запас — внутри блока эпика, а не «взаймы» у соседа.
3. Если блок исчерпан — эпик берёт следующий свободный блок с конца реестра (≥ 96) и записывает здесь; сдвиг существующих id запрещён.

### 6.1 Ширина тега **[T03]**

**Решение (ADR-0011): тип `CommandType` в памяти становится `std::uint16_t`, а на проводе тег кодируется varint (LEB128): 1…127 — один байт, 128…16 383 — два байта.**

| Вариант | Что даёт | Цена |
|---|---|---|
| A. Остаться на `u8`, компактные блоки | ничего не меняется | потолок 255 тегов на всю игру (E10 128, E12 144, E30 168 и ≈ 80 остальным — уже сейчас впритык); любой следующий эпик упрётся в потолок и потребует той же миграции позже, когда файлов и реплеев станет больше |
| B. Плоский `u16` | широкий тег | байты `write_command` меняются у всех: `PRP1 → PRP2`, `PCL1 → PCL2`, контейнер `PSV` (отложенные команды) — три формата, читать обе версии, пересчёт `kExpectedReplayBytesHash`; +1 байт на каждую команду |
| **C. `u16` в памяти + varint на проводе (выбрано)** | потолок 16 383; диапазоны блоков остаются как есть | один общий код `write/read` тега |

Почему C: для всех тегов **1…127** байты **идентичны прежним**, а все существующие теги (1…39) и блоки E8 (64…95) и E11 (96…127) лежат ниже 128. Поэтому **`PRP1`, `PCL1` и нагрузка `PSV` не меняют версии**, фикстуры и реплеи читаются без миграции, `kExpectedReplayBytesHash` и golden-значения не двигаются (AGENTS.md §5.4). Старая сборка, встретив тег ≥ 128, отвергает файл как «неизвестный тег команды» — но такие команды существуют только у сборок, где вместе с ними выросла схема мира, а слово схемы читается **раньше** отложенных команд: пользователь увидит «создано более новой версией». Реплеи и журналы с тегами ≥ 128 старые сборки не обязаны читать (§7.2).

Требования к реализации (T03) и тесты:
- Только каноническая форма: `0x81 0x00` (избыточный второй байт), тег 0, тег ≥ 16 384, обрыв на втором байте — ошибка (`read_command` вернёт `false`, а не упадёт); тест «закодировал → декодировал → те же байты» уже есть в `command_log_test.cpp`.
- Тесты границ: тег 127 (один байт), 128 и 16 383 (два байта).
- **Реализовано (T03):** `write_command_tag`/`read_command_tag` и `kMaxCommandTag = 16383` в `command_log.hpp`; `static_assert` в `command.cpp` — каждый тег в 1…16 383 и уникален; тесты — `tests/save_capacity_test.cpp`.
- Все существующие фикстуры и реплеи читаются; `kExpectedReplayBytesHash` и `kExpectedSaveBytesHash` **не меняются** (проверка, что вообще ничего из существующего не сдвинулось).
- `to_string(CommandType)`, `static_cast<std::uint8_t>(...)` по коду ищутся и заменяются; `static_assert` на уникальность тегов остаётся.

## 7. Политика версий и миграций

### 7.1 Что где версионируется

| Что | Когда поднимается | Как читается старое | Что обязательно в PR |
|---|---|---|---|
| `PSV` `format_version` | меняется **раскладка контейнера** (заголовок, порядок блоков, сжатие) | читаются все версии ≥ 1 навсегда; писатель пишет только последнюю | тест чтения файла предыдущей версии (фикстура), сообщение «более новая версия» для версии+1 |
| Сводка (ключи) | ключ добавляется — версия **не** поднимается | неизвестные ключи пропускаются; отсутствие необязательного ключа — «нет данных» | строка в таблице §2.3 |
| `kStateSchema` | любое изменение байтов `save_state`: колонка, раздел, значение перечисления, единица измерения | `World::load_state` читает схемы 1…текущая, шаги миграции — над уже загруженным миром (не над байтами) | см. чек-лист §7.4; диапазон `[1, текущая]` **не сужается в M1** |
| Версия раздела | меняется раскладка раздела | ридер раздела читает все его версии | фикстура прежней версии раздела |
| `PRP1`/`PCL1` | меняется заголовок, набор полей или кодирование **вне** тела команд | читается версия 1; новая версия — отдельное решение с чтением обеих | тест, что байты реплея демо и золотые хеши прежние |
| Тег команды | **никогда не меняется** | — | строка в §6 |
| Тело команды | поле добавляется/меняется: **новый тег** (старый остаётся читаемым) или явное решение в ADR эпика | ридер читает прежнее тело по тому же тегу | тест на обе формы |

Номер схемы мира — следующий свободный на момент слияния; два PR, меняющих формат или golden, одновременно запрещены (одна W-задача за раз, `docs/epics/README.md`).

### 7.2 Совместимость вперёд и назад

- **Назад (новая сборка читает старый файл):** всегда в рамках перечисленных версий; миграции типизированные, мир после миграции проходит `check_invariants`.
- **Вперёд (старая сборка читает новый файл):** **не поддерживается**, но отказ обязан быть понятным: версия контейнера новее → код 22; схема новее → «создано более новой версией»; никакого частичного чтения «что смогли».
- **Реплеи и журналы:** гарантированы только на сборке с тем же `scenario_id` и той же версией симуляции; формат версионирован, чтение новой версии старой сборкой — ошибка; сопровождаются golden-тестами.
- Не бывает «улучшения без миграции»: изменение значения/единицы без смены байтов — всё равно подъём схемы (прецедент: схема 10).

### 7.3 Окно поддержки

В M1 поддерживаются **все** версии с первой. Сужение окна (например, «читаем схемы не старше N») возможно только отдельным ADR с планом конвертера (E27/E29) и сообщением игроку; до этого фикстуры прежних схем читаются навсегда.

### 7.4 Чек-листы для PR

**PR, меняющий раскладку мира (колонка, раздел, перечисление, единица):**
1. Взять следующий `kStateSchema` на момент слияния (rebase перед PR).
2. Раздел: строка в §5 (id из блока своего эпика), запись `SectionInfo{id, version, min_schema}`, `static_assert` по лимиту.
3. Шаг миграции в `load_state` (пустой, если новых данных нет) — отдельный комментарий «N → N+1».
4. **Фикстура прежней схемы**: файл `tests/data/saves/<имя>_v<N-1>.psv`, команда создания в комментарии теста (создаётся на `main` до правок); тест читает её и сверяет хеш.
5. Тест round-trip посреди состояния этого раздела; запись в корпусе порчи T11 (усечения, битовые порчи, раздутые счётчики); resume-сценарий T12.
6. Если хеш пустого мира должен остаться прежним — тест на это; иначе golden меняется **осознанно** и объясняется в коммите.
7. Комментарий-описание раскладки сверху `world_io.cpp` (или `world_*_io.cpp`).

**PR, добавляющий команду:** тег из блока своего эпика (§6), запись в `TagTable` и `to_string`, `Writer`/`read_command`, тест «команда → байты → команда», строка в таблице §6.

**PR, добавляющий ключ сводки:** строка в §2.3; ридер и тест «неизвестный ключ пропускается» уже есть.

## 8. Политика совместимости при загрузке

### 8.1 Матрица

| Ситуация | Как определяется | Поведение |
|---|---|---|
| Совместимо | версия контейнера ≤ известной, схема ≤ `kStateSchema`, набор контента совпал | загрузка; миграции — молча |
| Формат новее | `format_version` > известной | **отказ**: «сохранение создано более новой версией игры»; файл **не изменяется** |
| Схема мира новее | `state_schema` > `kStateSchema` (по сводке, без разжатия; повторная проверка — слово схемы нагрузки) | **отказ** с той же формулировкой |
| Другой набор контента | `content_hash` ≠ хеша загруженного набора (оба ≠ 0) | **отказ**: «сохранение создано с другим набором данных»; в режиме `--dev` (E4-T07) проверка **пропускается** с записью в журнал; на формат и схему `--dev` не влияет |
| Повреждено | хеш сводки или нагрузки не сошёлся, обрыв, ошибка zstd или инвариантов | **отказ**: «файл повреждён»; для автосохранений — предложить предыдущее, для ручных/быстрых — `.bak` (§9.5); игра не падает |
| Старый (версия 1, нет сводки) | `format_version == 1` | загружается; в списке — по имени файла и времени изменения; совместимость выясняется при открытии |
| Не сохранение | нет `.psv` / нет магии | в списке не показывается (чужие файлы не трогаем); `.psv` с битой магией — «повреждено» |

Версия сборки (`game_version`) на совместимость **не влияет**: патч с тем же форматом, схемой и набором данных читает файл. Политика патчей с изменением контента — E27, миграции между наборами контента — E29; в M1 строгое равенство хеша.

### 8.2 Сообщения

Игроку показывается **причина**, не код. Экран «Сохранение недоступно» (`MenuDialog::SaveUnavailable`, ключи `ui.menu.unavailable.*`, `ui.menu.load.unavailable`) берёт тексты из таблиц локализации, не из жёстких строк; T07/T08 добавляют по причине ключ (`newer_format`, `different_content`, `corrupted`, `unreadable_disk`, `unknown` `[предл.]`). Подробности (код, путь, версии) — в журнал `logs\`, не в UI. Список остальных сохранений при ошибке одного не меняется.

## 9. Каталог, файлы, автосохранения

### 9.1 Каталог пользовательских данных (решение владельца, #357)

`SDL_GetPrefPath("Patriarch", "Patriarch")` — на Windows `%APPDATA%\Patriarch\Patriarch\`; внутри: `saves\*.psv`, `settings.pd`, `logs\`. Параметр `--user-dir <путь>` переопределяет каталог целиком (тесты, портативная сборка). Вызов SDL — только в приложении (`apps/`, `engine`); ядро (`sim`, `game`) получает `std::filesystem::path` готовым, платформенных допущений в именах и путях нет (облачные сохранения E28 подключаются за тем же интерфейсом). Каталог и подпапки создаются при первой записи; ошибка создания — «нельзя сохранить» (§9.7). Не путать с каталогом данных игры (`data/`), он только для чтения.

### 9.2 Файлы и имена

| Файл | Имя | Содержимое |
|---|---|---|
| Ручное сохранение | `<имя>.psv` | `kind = 0` |
| Автосохранение (ротация) | `_auto1.psv`, `_auto2.psv`, `_auto3.psv` | `kind = 1` |
| Автосохранение при выходе | `_autoexit.psv` | `kind = 3` |
| Быстрое сохранение | `_quick.psv` | `kind = 2` |
| Резервная копия | `<файл>.bak` | предыдущая копия |
| Временный | `<файл>.tmp` | пишется, потом переименовывается |

Идентификатор сохранения для `MenuActions::load_save(id)` — имя файла без расширения; **тип определяет `kind` в сводке**, а не имя. Префикс `_` зарезервирован за системными файлами: ручные имена с таким началом получают другой префикс.

Имя, введённое игроком, хранится в сводке дословно (UTF-8, 1…64 символа, без управляющих символов, без пробелов по краям). Из него строится **имя файла**:
- запрещённые символы Windows `< > : " / \ | ? *` и управляющие (< 0x20) заменяются на `-`; хвостовые точки и пробелы убираются;
- зарезервированные имена устройств (`CON`, `PRN`, `AUX`, `NUL`, `COM1…9`, `LPT1…9`, с расширением и без) получают суффикс `-`;
- кириллица и прочие символы Юникода остаются как есть (NTFS хранит UTF-16; путь строится из UTF-8 без потерь через `std::filesystem::path(std::u8string)`; тест с «Перед заговором 1708»);
- длина: **путь целиком ≤ 240** символов (запас под `.psv.bak`; не полагаемся на длинные пути Windows), основа имени не короче 16, иначе «путь слишком длинный»; одна часть — ≤ 255 UTF-16-единиц;
- коллизия: если файл с таким именем уже есть — это **перезапись** того же сохранения (UI спрашивает подтверждение, T10), если имена различаются, но дают один файл — к основе добавляется ` (2)`; проверка существования — по файловой системе (NTFS регистронезависима сама).

### 9.3 Запись **[T05]**

1. На границе тика берётся неизменяемая копия мира (`std::shared_ptr<const World>`) + отложенные внутренние команды + поля сводки.
2. Фон: `serialize_save` (сводка + zstd) и запись; **один сейв за раз**, новые запросы ждут или объединяются (автосохранение при занятой записи — пропускается). Запись не меняет мир и не попадает в `CommandLog`.
3. Файл пишется как `<файл>.tmp`, потом проверяется (заголовок и сводка перечитываются, размер совпал), потом: если ручной/быстрый и старый файл есть — он переименовывается в `.bak` (заменяя прежний `.bak`), затем `.tmp → <файл>`. Для автосохранений `.bak` не создаётся — предыдущая копия это следующий файл ротации.
4. Если места на диске заведомо мало (`filesystem::space` < 2 × размера последнего сохранения), запись не начинается и **прежние файлы не затрагиваются**.
5. Ошибки диска классифицируются: нет места, нет прав/только чтение, путь/имя недопустимы, файл занят (антивирус, облачная синхронизация — до 3 повторов с паузой 200 мс), прочее; у каждой — понятный текст из таблиц локализации и запись в журнал.
6. Сбой между шагами 3 и 4: остаются `.bak` и `.tmp` — каталог при сканировании считает `.bak` кандидатом на восстановление, `.tmp` игнорируется и удаляется при следующей записи того же файла.

### 9.4 Каталог сохранений **[T04]**

`SaveCatalog` (модуль `src/game`, путь передаётся снаружи): список `*.psv`, для каждого читает **только сводку** (без zstd) → строка `{id, kind, name, date, head, dynasty, treasury, goal, play_time, saved_at, compat, path}`; сортировка — по `saved_at` по убыванию, затем по времени изменения файла, затем по имени. Состояния `compat`: `Ok`, `NewerFormat`, `ContentMismatch`, `Corrupt`, `Legacy` (версия 1 без сводки — загружается, но в списке показывается по имени файла и `mtime`). Содержимое каталога не кэшируется между вызовами (кэш — задача экрана «Загрузка»). Переименование = новый файл-имя + **перезапись только сводки** (нагрузка и её хеш не трогаются); удаление — файл и его `.bak`, с подтверждением. Скан 1000 файлов ≤ 100 мс.

### 9.5 Восстановление

- «Продолжить» = самое новое **совместимое** сохранение любого вида (по `saved_at`).
- Если оно повреждено при загрузке — экран «Восстановление сохранения» предлагает **следующее по списку**; для ручного/быстрого с `.bak` — «восстановить предыдущую копию» (`.bak → файл` с обменом, повреждённый файл переименовывается в `.corrupt`, не удаляется).
- Ничто из этого не удаляет файлы без подтверждения игрока.

### 9.6 Автосохранения и быстрое сохранение (решение владельца, #358) **[T06]**

- **Автосохранение по таймеру:** реальное время работы партии, выбор «выкл./5/10/20 мин», по умолчанию **10 мин**; **3 ротируемых файла** `_auto1…3.psv`: пишется в слот с самым старым `saved_at` (отсутствующий слот — первым). **Пропуск без изменений:** если `world_hash`/`tick` совпадают с последним сохранением любого вида, ничего не пишется (пауза). Первое автосохранение — после старта партии (E30).
- **При выходе:** отдельный файл `_autoexit.psv` (`kind = 3`), не вытесняющий ротацию. (Трактовка решения #358: «3 ротируемых файла» + «сохранение при выходе»; если владелец хочет сохранять при выходе внутрь ротации — меняется только имя слота и правило выбора, формат тот же.)
- **Быстрое:** F5 — `_quick.psv` (один слот), F9 — загрузка того же слота; без подтверждения перезаписи; тост «Быстрое сохранение»; клавиши переназначаются (`settings.pd`).
- **Не в M1:** сохранение «по игровой дате», режим «без перезагрузок» (поле `ironman` в сводке зарезервировано).
- Настройки автосохранения лежат в `settings.pd` (`autosave.interval_min`, `autosave.on_exit`), умолчания — в данных.

### 9.7 `settings.pd` **[T09]**

Текстовый файл `.pd` в каталоге пользовательских данных, один профиль: ключ `settings_version = 1`; **неизвестные ключи сохраняются при записи**; повреждённый файл не блокирует запуск (умолчания, повреждённый переименовывается в `settings.pd.bad`); запись атомарна (`.tmp` + переименование). К формату сохранений не относится, версионируется собственным ключом.
