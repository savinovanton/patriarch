# Руководство автора данных `.pd`

> Статус: E4-T09. Для тех, кто пишет контент (черты, провинции, династии, события) и моды. Здесь — как писать файлы по шагам и как читать сообщения об ошибках. Справочник по каждому виду объекта — [data-reference.md](data-reference.md) (генерируется из схем).
> Подробности: формат — [data-format.md](data-format.md), схемы и коды `PD101…PD110` — [data-schemas.md](data-schemas.md), загрузка корней, переопределение, ссылки, хеш — [data-loader.md](data-loader.md).

## 1. Быстрый старт

Контент игры лежит в каталоге `data/` (не в `assets/`: реестр лицензий для данных не нужен). Файл — обычный текст `.pd` в кодировке **UTF-8** (допустим BOM), переводы строк `LF` или `CRLF`. В одном файле можно описать любое число объектов. Скопируйте похожий объект, поменяйте `id` и значения, запустите проверку — этого достаточно для большинства правок.

Минимальный файл:

```
format_version = 1

trait "greedy" {
    name_key = "trait.greedy.name"
    cost = 3
}
```

## 2. Пошагово

### Шаг 1. Заголовок

Первая запись файла всегда `format_version = 1` (версия **формата**, не контента). Нет заголовка — ошибка `PD020`; версия новее той, что понимает игра, — `PD021`.

### Шаг 2. Объект

Объект записывается как `вид "id" { поля }`:

```
trait "greedy" {
    name_key = "trait.greedy.name"
    cost = 3
}
```

- `trait` — **вид** объекта; допустимые виды и их поля — в [справочнике](data-reference.md). Неизвестный вид — `PD108` (с подсказкой «did you mean»).
- `"greedy"` — **id** объекта. Он обязателен (`PD109`, если пропущен), уникален внутри вида и одного корня (`PD112` при повторе), пишется латиницей: `greedy`, `court.embezzling_governor`. Кавычки необязательны (`trait greedy { … }` то же самое).
- Поля записываются как `ключ = значение`. Вместо `ключ = { … }` можно писать `ключ { … }`. Запятые между записями необязательны.
- Порядок полей внутри объекта и порядок объектов в файле значения не имеют; разбивать объекты по файлам можно как удобно (хеш контента от этого не меняется).

### Шаг 3. Значения

| Что | Как писать | Пример |
|---|---|---|
| Целое | цифры, знак `-` допустим | `cost = 3`, `delta = -2` |
| Дробное (`Fixed`) | десятичная точка, до 9 знаков; запись `.5`, `1.`, `1e5` запрещена | `weight = 1.5`, `base = 0.05` |
| Логическое | `yes` / `no` (не `true`/`false` — `PD018`) | `inheritable = yes` |
| Строка | в двойных кавычках; `\"`, `\\`, `\n`, `\t`, `\u{1F600}` | `name_key = "trait.greedy.name"` |
| Длинная строка | тройные кавычки, любые переводы строк | `text = """` … `"""` |
| Перечисление | идентификатор из списка в справочнике | `group = vice` |
| Дата | `Г.ММ.ДД`, **юлианский** календарь (високосный — каждый 4-й год: `1704.02.29` верно, `1703.02.29` — `PD107`) | `since = 1703.01.01` |
| Ссылка | `вид:id`, голый идентификатор или строка; объект должен существовать | `opposite = trait:honest` |
| Список | в квадратных скобках | `tags = [ "court", "money" ]` |
| Словарь | блок `ключ = значение` с одним типом значений | `skills = { stewardship = 2 }` |
| Вложенный блок | `имя { … }` или `имя = { … }`, свои обязательные поля | `chance { base = 0.05 }` |

**Числа и `Fixed`.** Игра не использует `double`: десятичная запись точно переводится в фиксированную точку (`Fixed32` — Q16.16, `Fixed64` — Q32.32) целочисленной арифметикой с усечением к нулю. Поэтому `0.1` в `Fixed32` хранится как `6553/65536`; границы допустимых значений указаны в столбце «Ограничения» справочника (`PD104` при нарушении). Деньги и прочие целочисленные величины пишите целыми.

**Идентификаторы.** Только ASCII: `[A-Za-z_][A-Za-z0-9_]*`, сегменты можно соединять точками (`court.fire`), до 256 символов. Русский текст допустим **только в комментариях и строках**.

### Шаг 4. Комментарии

`#` — до конца строки; вне строкового литерала. Комментарии и форматирование не влияют ни на что, включая хеш контента.

```
trait "greedy" {                  # жадность
    cost = 3                      # очки, 0..10
    # note = "временно отключено"
}
```

### Шаг 5. Ссылки между объектами

Поле-ссылка (`ref(trait)` в справочнике) указывает на объект того же или другого вида. Загрузчик проверяет все ссылки после чтения всех файлов (порядок файлов не важен); отсутствующий объект даёт `PD111`.

```
trait "greedy" { name_key = "trait.greedy.name"  cost = 3  opposite = trait:generous }
trait "generous" { name_key = "trait.generous.name"  cost = 2  opposite = trait:greedy }
```

Взаимные ссылки допустимы.

## 3. Сообщения об ошибках

Формат: `[корень] файл:строка:столбец: error[КОД]: текст`. Все ошибки собираются за один проход — исправляйте сверху вниз и перезапускайте проверку. Строки и столбцы считаются с 1, столбец — в символах Unicode. Коды стабильны, формулировки могут уточняться.

Реальные примеры (корень `base`, файл `traits/t.pd`):

```
[root 0 'base'] traits/t.pd:4:12: error[PD104]: value 11 is out of range (0..10)
[root 0 'base'] traits/t.pd:5:13: error[PD106]: unknown value 'vise' (allowed: vice, virtue, neutral) (did you mean 'vice'?)
[root 0 'base'] traits/t.pd:6:5: error[PD101]: unknown field 'skils' (did you mean 'skills'?)
[root 0 'base'] traits/t.pd:8:13: error[PD107]: 1703.02.29 does not exist in the Julian calendar
```

| Код | Что случилось | Что делать |
|---|---|---|
| `PD018` | написали `true`/`false` | заменить на `yes`/`no` |
| `PD014` | не закрыта `{` или `[` (позиция — открывающая скобка) | найти парную скобку; ищите пропущенную `}` ниже указанной строки |
| `PD020` | нет `format_version = 1` первой записью | добавить заголовок |
| `PD101` | неизвестное поле | опечатка? смотрите подсказку «did you mean» и [справочник](data-reference.md) |
| `PD102` | не задано обязательное поле: `missing required field 'name_key' in trait "a"` | добавить поле |
| `PD103` | неверный тип: `expected int, found string` | убрать кавычки / привести значение к типу |
| `PD104` | значение вне диапазона | уложиться в границы из справочника |
| `PD105` | поле повторено, а повтор не разрешён | оставить одно или проверить, что поле `повторяемое` |
| `PD106` | неизвестное значение перечисления (сообщение перечисляет допустимые) | выбрать из списка |
| `PD107` | такой даты нет в юлианском календаре | исправить день/месяц |
| `PD108` | неизвестный вид объекта | проверить имя вида |
| `PD109` | у объекта нет id: `'trait' needs an id: trait "name" { ... }` | дать объекту id |
| `PD110` | вместо `=` использован `>=`, `!=` и т. п. | в данных операторы сравнения не нужны (они для языка правил, E11) |
| `PD111` | ссылка на несуществующий объект: `there is no trait 'honset' (did you mean 'honest'?)` | исправить id или добавить объект |
| `PD112` | `(вид, id)` определён дважды в одном корне: `duplicate trait 'b' in the same root (first defined at …)` | переименовать или удалить дубликат |

Если внутри объекта есть **синтаксическая** ошибка (например, `PD018`), сообщаются только она и другие синтаксические ошибки: такой объект по схеме не проверяется, пока не будет исправлен синтаксис. Поэтому после правки могут появиться новые ошибки схемы — это нормально. Полный список кодов: `PD001…PD024` в [data-format.md](data-format.md), `PD101…PD110` в [data-schemas.md](data-schemas.md), `PD111…PD114` в [data-loader.md](data-loader.md).

## 4. Корни и моды: переопределение

Загрузчик принимает **упорядоченный список корней**: корень 0 — базовая игра (`data/`), следующие — моды. Для каждого корня читаются все файлы `*.pd` рекурсивно (расширение строго `.pd`, регистр важен).

- Объект мода с тем же `(вид, id)`, что и в базе, **целиком заменяет** базовый (поля не сливаются): если вам нужна «база плюс правка одного поля», скопируйте объект целиком.
- Повтор `(вид, id)` внутри **одного** корня — ошибка `PD112`, а не переопределение.
- Ссылки проверяются на итоговом наборе: мод может ссылаться на объекты базы и других модов, загруженных раньше (или позже — порядок файлов не важен, важен лишь итог переопределения).
- Порядок корней влияет на результат (поздний побеждает). Порядок файлов внутри корня и порядок объектов в файле — нет.
- Ошибки сообщаются с указанием корня: `[root 1 'mods/a'] …`.

Подробнее: [data-loader.md](data-loader.md) §2, §5.

## 5. Проверка своих файлов

- **Справочник** — [data-reference.md](data-reference.md): виды, поля, типы, обязательность, значения по умолчанию, диапазоны, допустимые значения перечислений. Он **генерируется из самих схем** утилитой `schemadoc` (`schemadoc --write docs/dev/data-reference.md`), поэтому не может разойтись с кодом; CI проверяет актуальность. Вручную файл не править.
- **Линтер** `contentlint` (**запланирован**, E4-T08): проверка всего `data/` и локализации одной командой, коды выхода, вывод для CI. До его появления ошибки видны при загрузке контента (`load_content`).
- **Горячая перезагрузка** (запланирована, E4-T07): правка видна в запущенной игре без перезапуска; при ошибке остаётся прежний контент.

## 6. Для разработчиков: как добавить новый вид объекта

1. Опишите схему (`ObjectSchema`) и добавьте её в `content_schemas()` (`src/data/content_schemas.cpp`). Каждое поле сопровождайте `.describe("…")` — одной строкой по-русски, она попадёт в справочник.
2. Перегенерируйте справочник: `schemadoc --write docs/dev/data-reference.md` и закоммитьте его вместе с изменением схемы.
3. Добавьте тест схемы (`tests/`) и данные в `data/`.

## 7. Пример: данные экономики

Первый настоящий набор данных — `data/economy/` (E9-T18): `rules.pd` (константы правил и параметры по открытым вопросам владельцу), `goods.pd`, `groups.pd`, `policies.pd`, `buildings.pd`. Он целиком описывает `EconomyRules`; значения равны `EconomyRules::defaults()` (тест `tests/economy_content_test.cpp`). Чтобы поменять баланс, правьте число в файле и перезапускайте игру — пересборка не нужна. Мод повторяет нужный объект целиком в своём корне (например, `tax_level "high" { … }`) — см. §4. Виды и поля — в [справочнике](data-reference.md); правила, связывающие несколько объектов (уникальность `slot`, полный набор групп, индексы уровней без пропусков), проверяет сборщик правил (`pat::content`, модуль `src/content`) и сообщает о нарушении кодом `PD115` с позицией `файл:строка:столбец`.

Второй набор — `data/balance/demography.pd` (E7-T07): объект `demography_rules "main"` с блоками `mortality`, `health`, `conception`, `birth`, `life_stages` целиком описывает `pat::sim::DemographyRules` (смертность и зачатие по возрасту, множители знати и здоровья, потолок детей, соотношение полов, риск родов, возрастные периоды и брачный возраст). Значения равны `kDefaultDemography` (тест `tests/demography_content_test.cpp`); таблицы по возрасту — списки ступеней `{ from_age = 15, permille = 15 }` (первая ступень с 0, возраст строго растёт, не более 16). Загрузчик — `pat::content::load_demography_content` (`src/content/demography_content.cpp`); правила, не умещающиеся в схему (порядок ступеней, `low < high` у порогов здоровья, границы возрастных периодов, риск родов в пределах 0…1000), проверяет `sim::validate` и сообщает кодом `PD115` с позицией ступени или блока. Мод заменяет объект целиком, повторив `demography_rules "main"` (блоки не сливаются). Подбор значений под допуск вымирания родов — задача E7-T19, не этого набора.

Без шага 2 упадут тест `schema_doc: …committed reference is up to date` и проверка в CI.
