# Гейт производительности (E2-T07)

Гейт сравнивает одни и те же бенчмарки двух закоммиченных ревизий на одной машине.
Результат — JSON и самостоятельный HTML; для сопоставимых данных он содержит встроенный
SVG, без внешних библиотек, скриптов и сетевых ресурсов. Сравнение не меняет эталон.

## Набор и правило сравнения

Политика находится в [bench/baselines/suite.json](../../bench/baselines/suite.json):

| Имя | Нагрузка |
|---|---|
| `core.pcg32_next/1024` | 1 024 извлечения из PCG32 |
| `core.pcg32_next/16384` | 16 384 извлечения из PCG32 |
| `sim.telemetry_tick/0/real_time` | Batch из 32 одинаково подготовленных тиков без телеметрии |
| `sim.telemetry_tick/1/real_time` | Такой же batch с телеметрией |

Используются отдельные `real_time`-измерения Google Benchmark, приведённые к
наносекундам. `cpu_time` и готовые строки median/CV не заменяют исходные повторы.
Для sim время относится к batch, а не одному тику; в отношении двух версий масштаб
одинаков. Подготовка мира, restore и формирование сводки исключены из времени sim-batch.

Capture выполняет **7 повторов**, минимум **0.5 с измерения** и **0.1 с прогрева**.
Он требует полный набор индексов `0…6` для каждого имени. Компаратор допускает минимум
5 исходных выборок; считает медиану и выборочный RSD (`stdev / mean`). При RSD любой
стороны выше **5%** строка становится `inconclusive`, даже если номинально замедлилась.
Стабильное увеличение медианы **строго больше 10%** — регрессия; ровно 10% проходит.

| Exit code | Значение |
|---|---|
| `0` | Все обязательные строки стабильны и укладываются в порог |
| `1` | Есть доказанная по этому правилу стабильная регрессия |
| `2` | Ошибка входа/сборки/capture, отсутствующие данные или несовместимые профили |
| `3` | Недостаточно выборок или слишком большой шум, регрессия не доказана |

Если одновременно есть стабильная регрессия и шумная строка, возвращается `1`.
`inconclusive` не выдаётся за зелёную проверку и не называется замедлением. Автоматических
повторов до удобного результата нет. Новый запуск имеет смысл после исправления
конкретной ошибки условий; не следует выбирать удачные повторы и удалять остальные.

Профили сравниваются строго: ОС/архитектура, CPU и его affinity/cache, фактический
компилятор из generated CMake metadata, Release, приоритет процесса, версия/сборка Benchmark и протокол
времени. Несовместимость — `2`, а не регрессия. Изменение result label между версиями
даёт предупреждение для ревью функционального изменения; `require_same_label` в suite
позволяет сделать это ошибкой. Внутри одного capture label обязан быть одинаковым.

## Запуск на Windows

Для полного сравнения достаточно подготовленного `VCPKG_ROOT` и Git-истории с обеими
ревизиями. Из корня репозитория:

```powershell
git fetch origin
python tools/bench_gate.py --suite bench/baselines/suite.json --reference bench/baselines/reference.json --work-dir out/performance-manual
```

Без `--baseline-sha` используется `source_sha` из reference, candidate по умолчанию —
текущий `HEAD`. Для сравнения PR с его базой можно явно передать полные SHA:

```powershell
$baseline = git rev-parse origin/main
$candidate = git rev-parse HEAD
python tools/bench_gate.py --suite bench/baselines/suite.json --reference bench/baselines/reference.json --baseline-sha $baseline --candidate-sha $candidate --work-dir out/performance-pr
```

Runner создаёт отдельные detached worktree и каталоги сборки. Сначала собирает **обе**
версии, затем измеряет каждую один раз. Не сбрасывает чужие изменения и не переиспользует
каталог с другой ревизией; для новой пары выберите новый `--work-dir`.
Собирается только `bench`, MSVC Release, без engine/tools/tests, ASan и Tracy.
Эти выключатели сокращают цели проекта, **не список зависимостей vcpkg**: текущий
manifest всё ещё содержит SDL3/RmlUi/FreeType; бинарный кеш переиспользуется.

На Windows capture закрепляет главный поток бенчмарка за **последним разрешённым
логическим CPU** и запускает только этот дочерний процесс с `AboveNormal` priority.
Это снижает конкуренцию с UI/прерываниями на CPU 0; глобальные настройки, частоты,
другие приложения и приоритет сборки не меняются. CPU и класс приоритета записаны
в профиль обеих сторон. Жёсткой изоляции от ОС/SMT/соседних процессов это не гарантирует.

Результаты находятся в `<work-dir>/reports/`: нормализованные и исходные JSON обеих
сторон, логи, `report.json`, `report.html`. Формирование отчёта выполняется и при ошибке.

## Capture и сравнение готовых файлов

Отдельный capture нужен для уже собранной чистой ревизии. Сначала обновите Release
бинарник; git/CMake metadata сами по себе не доказывают, что старый exe пересобран:

```powershell
cmake --build --preset win-msvc-release --target bench
python tools/bench_capture.py --source . --build-dir out/win-msvc --suite bench/baselines/suite.json --output out/sample.json
```

Capture проверяет связь build/source, отсутствие отслеживаемых изменений входов,
Release, выключенные ASan/Tracy, affinity и сырые повторы. CMake compiler-файл читается
как данные, не исполняется. В нормализованный профиль не попадают личные пути и hostname;
из raw JSON удаляются только `host_name` и `executable`, значения времени сохраняются.

Сравнение существующих нормализованных файлов не запускает бенчмарки:

```powershell
python tools/bench_compare.py compare out/baseline.json out/candidate.json --suite bench/baselines/suite.json --json out/report.json --html out/report.html
```

Дубли имён/JSON-ключей, пропущенные случаи, NaN/Infinity, неположительные времена и
aggregate-only данные отклоняются. Политика suite и входные файлы не перезаписываются.

## PR, nightly и эталон

Workflow [Performance](../../.github/workflows/performance.yml) запускается для PR,
затрагивающих бенчмарки, core/sim или их инфраструктуру. На `windows-2022` сравниваются
`pull_request.base.sha` и проверяемый merge SHA (`github.sha`) — на **одном runner**.
Это сравнение с базой PR, не с числом, измеренным на другом компьютере.

Nightly и `workflow_dispatch` повторно собирают текущую ревизию и исходную ревизию
из [reference.json](../../bench/baselines/reference.json), затем измеряют обе на том же
runner. Начальная ревизия reference — `0a330c797baf41dec08247bb6e72a8180479e593`
(E2-T06). Замороженные числа ПК разработчика не сравниваются с GitHub hardware.
Фиксированная исходная ревизия позволяет nightly заметить и накопившееся замедление.

Расписание — **20:00 UTC**, то есть **03:00 Asia/Novosibirsk следующего дня**.
GitHub может задержать плановый запуск; это не таймер с гарантированной точностью.
Отчёт публикуется в artifact `performance-report` на **14 дней**, включая HTML/SVG и
JSON; краткая таблица также попадает в job summary. Ночная задача не пишет в репозиторий.

Reference должен содержать стабильные полные данные, а его `source_sha` — уже быть
предком `origin/main`. **Не используйте unmerged PR SHA или синтетический merge SHA**,
который может исчезнуть после squash/rebase. Reference проверяется даже в PR-режиме
с явным `--baseline-sha`, чтобы ошибочное обновление не сломало только будущий nightly.

Ручное обновление — явная команда `freeze`, затем reviewable PR; подробности —
[bench/baselines/README.md](../../bench/baselines/README.md). Смена эталона не должна
скрывать замедление без объяснения причины.

## Проверка результата E2-T07

Локальная обычная пара `0a330c7 → e4f4871` прошла на Windows-ПК (i5-12400F, MSVC 19.44
Release, CPU 11, AboveNormal). Изменение медиан: +0.72% / −0.46% / −0.47% / +2.55%
в порядке suite; RSD обеих сторон 1.22–2.40%. 10 целевых Python-проверок прошли.

Первое измерение на CPU 0 с обычным приоритетом дало RSD 6–44% и `inconclusive`;
его данные сохранены в локальном `out/E2-T07-first-noisy/` и не использованы как эталон.
После изменения условий новые значения получены одним полным capture; пороги,
исходные выборки и набор работ не подправлялись ради зелёного результата.

**Ожидается подтверждение CI:** обычный PR, временная PR с реальной дополнительной
вычислительной работой около 20% и nightly/manual с опубликованным артефактом.
