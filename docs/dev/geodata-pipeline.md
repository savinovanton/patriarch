# Конвейер геоданных, стадия 1: GDAL/PROJ → промежуточные файлы (Geo-4)

> Статус: v1 (Geo-4, #80, 2026-11-26); стадия 2 — `mapgen --import` (Geo-3, #79), §11. Контекст — [ADR-0004](../adr/0004-geodata-pipeline.md) §3–4, формат карты — [ADR-0007](../adr/0007-pmd2.md), источники, загрузка и замеры — [geodata-howto.md](geodata-howto.md), лицензии — [geodata-sources.md](geodata-sources.md). Выбор проекции и разрешения — спайк Geo-5 (#81).

## 1. Что делает стадия 1

```
манифест + кэш (fetch.py)  →  tools/geo/stage1.py run  →  <work>/<проекция>/{height.i16, water.u8, coastline.pgl, rivers.pgl, stage1.json}
                                                          →  mapgen --import (Geo-3, C++ без GDAL)  →  physical.pmd + provinces.pmd (PMD2)
```

Скрипт берёт из кэша тайлы Copernicus DEM GLO-90 и слои Natural Earth 1:10m, склеивает DEM (с переносом тайлов западного полушария через 180-й меридиан), перепроецирует в одну из кандидатных проекций, ресемплирует в базовый растр 8192×4096 (усреднение), растеризует маску воды, переводит береговую линию и реки в пиксельные полилинии и проверяет результат.

**Решение владельца (2026-11-26, #80):** GDAL/PROJ — внешние офлайн-инструменты. Скрипты вызывают их программы командной строки; GDAL **не** входит в сборку, `vcpkg.json` и CI. Сам `stage1.py` — только стандартная библиотека Python 3.10+; тесты (`tests/tools/test_geo_stage1.py`) проверяют чистую логику без GDAL.

## 2. Установка GDAL/PROJ (Windows)

Рекомендуемый путь — conda-окружение `patriarch-geo` из канала conda-forge (а не QGIS/OSGeo4W):

```powershell
winget install CondaForge.Miniforge3 --scope user
# новый терминал (Miniforge Prompt или PowerShell после `conda init powershell`):
conda create -n patriarch-geo -c conda-forge --override-channels python=3.12 gdal pyproj
```

**Зафиксированные версии** (окружение владельца, 2026-11-26): **GDAL 3.13.3, PROJ 9.9.0**, pyproj 3.8.0, Python 3.12, канал conda-forge. Чтобы воспроизвести их точно: `conda create -n patriarch-geo -c conda-forge --override-channels python=3.12 gdal=3.13.3 proj=9.9.0 pyproj=3.8.0`.

Скрипт проверяет версии при старте: GDAL должен совпадать по `major.minor` (3.13), PROJ — не ниже 9.9.0. Другая версия GDAL — только с ключом `--allow-other-gdal`; фактические версии всегда записываются в `stage1.json` (`provenance.tools`), так что результаты разных версий различимы. При смене версии обновите `PINNED_GDAL`/`MIN_PROJ` в `stage1.py` и этот раздел.

**Как скрипт находит GDAL** (по порядку): `--gdal-bin DIR` → переменная `PATRIARCH_GDAL_BIN` (каталог программ) → `PATRIARCH_GEO_PYTHON` (путь к `python.exe` окружения; программы берутся из `<окружение>\Library\bin`) → `PATH` (активированное окружение) → стандартные пути `~\miniforge3\envs\patriarch-geo`, `~\miniconda3\…`, `~\mambaforge\…`. Активировать окружение не обязательно: для неактивированного скрипт сам выставляет дочерним процессам `PROJ_DATA`, `GDAL_DATA` и `PATH`. Если ничего не найдено — ошибка с перечнем проверенных мест и ссылкой на этот раздел (код 2).

```powershell
python tools\geo\stage1.py check-tools      # "GDAL 3.13.3 and PROJ 9.9.0: OK" и пути программ
```

Запускать `stage1.py` можно любым Python 3.10+ (системным или из окружения).

## 4. Запуск: от манифеста до промежуточных файлов

1. **Записать файлы в манифест** (`data-sources/geodata.manifest.json`, правила — [geodata-howto.md](geodata-howto.md) §5).
   - Natural Earth: пять архивов `ne_10m_{ocean,minor_islands,lakes,coastline,rivers_lake_centerlines}.zip` (уже записаны с SHA-256, см. §9).
   - DEM: список тайлов GLO-90 для области карты печатает `python tools\geo\stage1.py tiles --tile-list tileList.txt > tiles.json`. Здесь `tileList.txt` — перечень существующих тайлов из корня бакета `copernicus-dem-90m`; без него в список попадут и морские ячейки, которых нет. Вставьте массив в `files` записи `copernicus-dem-glo90`.
2. **Скачать:** `python tools\geo\fetch.py --only copernicus-dem-glo90 --only natural-earth-10m-physical --allow-unverified` (первый раз печатает SHA-256 и размеры для записи в манифест).
3. **Проверить рамку** (данных не нужно): `python tools\geo\stage1.py frame` — проецирует опорные точки (Калининград, мыс Дежнёва, о. Рудольфа, мыс Лопатка, Владивосток …) и соседей-фон (Стокгольм, Стамбул, Исфахан, Пекин) и печатает запас до края холста в пикселях; код 1, если обязательная точка вне холста.
4. **Построить:** `python tools\geo\stage1.py run [--projection albers|lcc|laea|all]` (по умолчанию все три; пока источники не помечены `ready` — с `--allow-unverified`). `--dry-run` печатает команды GDAL, ничего не запуская и не записывая. Одна проекция на полном наборе строится за минуты, на пробном — за ≈ 50 с.
5. **Проверить:** `run` сам вызывает проверку; отдельно — `python tools\geo\stage1.py validate <work>\lcc` (`--no-hashes` — без пересчёта SHA-256).

Список параметров проекций: `python tools\geo\stage1.py projections`.

## 5. Кандидатные проекции (для Geo-5)

Все параметры — **[предл.]**, окончательный выбор — Geo-5. Эллипсоид WGS84, `x_0 = y_0 = 0`, холст 8192×4096, пиксель 1300 м (10 650 × 5 325 км). Центральный меридиан 100° в. д. ставит Чукотку примерно на +90° от центра, так что «склейки» по X не нужно (ADR-0007 §3.3). Холст сдвинут на север, потому что «банан» России в конических проекциях поднимается к Калининграду и Чукотке.

| id | Проекция | PROJ | Центр холста | GEOR `projection` |
|---|---|---|---|---|
| `albers` | равновеликая коническая Альберса | `+proj=aea +lat_0=58 +lon_0=100 +lat_1=47 +lat_2=69` | (0, +680 км) | 1 |
| `lcc` | конформная коническая Ламберта | `+proj=lcc +lat_0=58 +lon_0=100 +lat_1=47 +lat_2=69` | (0, +680 км) | 2 |
| `laea` | азимутальная равновеликая Ламберта (запасная) | `+proj=laea +lat_0=62 +lon_0=100` | (0, +300 км) | 3 |

Стандартные параллели 47° и 69° выбраны по правилу 1/6 для полосы ≈ 42–75° с. ш.

Замер `frame` (GDAL 3.13.3, 2026-11-26), запас до края холста в пикселях:

| Точка | albers | lcc | laea |
|---|---|---|---|
| мыс Дежнёва (верх) | 102 | 91 | 49 |
| о. Врангеля | 250 | 255 | 253 |
| о. Рудольфа | 401 | 318 | 418 |
| Пекин (низ, фон) | 103 | 114 | 68 |
| Стамбул (лево, фон) | 204 | 222 | 286 |

Все обязательные точки и точки фона помещаются во всех трёх проекциях. При центре холста (0, 0) мыс Дежнёва в `laea` выпадал за край на 182 пикселя, в конических проекциях запас был 30–40 пикселей.

## 6. Формат промежуточных данных (v1)

Каталог `<work>/<id проекции>/`. Все растры — без заголовка, строка 0 — север, столбец 0 — запад, порядок байт little-endian. Каждый растр сопровождается ENVI-заголовком `*.hdr` от GDAL: с ним файл открывается в QGIS, стадия 2 заголовок не читает. Пиксель `(c, r)` покрывает в плоскости проекции `x ∈ [origin_x + c·p, origin_x + (c+1)·p)`, `y ∈ (origin_y − (r+1)·p, origin_y − r·p]`.

### 6.1. `stage1.json`

```json
{
  "format": "patriarch-geo-stage1", "format_version": 1,
  "projection_id": "lcc", "width": 8192, "height": 4096,
  "vertical_datum": "EGM2008 (Copernicus DEM heights, metres)",
  "area": {"west_udeg": 15000000, "south_udeg": 28000000, "east_udeg": 195000000, "north_udeg": 82000000},
  "georef": { ...поля чанка GEOR (ADR-0007 §3.3) целыми: projection, datum, lat_origin_udeg, lon_central_udeg,
              lat_std1_udeg, lat_std2_udeg, false_easting_mm, false_northing_mm, origin_x_mm, origin_y_mm,
              pixel_size_x_mm, pixel_size_y_mm, bbox_*_udeg, epsg, proj_text },
  "provenance": {
    "manifest_version": 1,
    "sources": [{"id": "copernicus-dem-glo90", "version": "...", "files": [{"path": "...", "sha256": "..."}]}, ...],
    "steps": [{"id": "reproject:lcc-v1", "params_hash": "0x…"}, ...],
    "tools": {"gdal": "3.13.3", "proj": "9.9.0"}
  },
  "files": {
    "height":    {"path": "height.i16",    "sha256": "…", "size": 67108864, "type": "int16le", "unit": "m", "nodata": -32768},
    "water":     {"path": "water.u8",      "sha256": "…", "size": 33554432, "type": "uint8", "codes": {"0": "land", "1": "sea", "2": "lake"}},
    "coastline": {"path": "coastline.pgl", "sha256": "…", "size": …, "type": "pgl1"},
    "rivers":    {"path": "rivers.pgl",    "sha256": "…", "size": …, "type": "pgl1"}
  }
}
```

- `georef` копируется стадией 2 в `GEOR` без изменений. Долготы `bbox` — в [−180°, 180°]; рамка через антимеридиан записывается как `bbox_min_lon > bbox_max_lon` (RFC 7946 §5.2): для области 15° в. д. – 165° з. д. это `(15000000, −165000000)`; так её принимает `validate_georef` (Geo-3; прежний обход «весь диапазон долгот» тоже остаётся допустимым). Точная область дополнительно хранится в `area` (`east_udeg` > 180° значит «восточнее 180-го меридиана»).
- `provenance` — заготовка чанка `PROV` (ADR-0007 §3.6): id и версии источников, SHA-256 использованных файлов, шаги с `params_hash` (FNV-1a 64 от канонического JSON параметров шага, строка `0x` + 16 hex, чтобы не терять точность в JSON-парсерах). Поле `builder` заполняет стадия 2.
- `files.*.sha256` — защита от подмены и порчи промежуточных файлов; `validate` её проверяет.

### 6.2. `height.i16` — высоты

`int16` LE, **целые метры** над геоидом EGM2008 (высоты Copernicus DEM как есть), `−32768` — нет данных (море вне тайлов DEM, отсутствующие тайлы). Усреднение `-r average` по всем исходным пикселям (≈ 90 м) внутри пикселя 1,3 км, округление до целого метра делает GDAL. Стадия 1 **не** стилизует рельеф и не чистит DSM от леса и застройки. Это делает стадия 2: на 1,3 км/пиксель средняя высота полога почти не влияет на результат. Стадия 2 также переводит метры в `u16` с `sea_level` и `metres_per_unit_milli` (PMD).

### 6.3. `water.u8` — маска воды

`uint8`: 0 — суша, 1 — море/океан, 2 — озеро. Порядок растеризации (шаг `water:ne10m-v2`, Geo-3): весь холст = 1, рамка области карты (проецированная, рёбра уплотнены через 0,25°) = 0, океан Natural Earth = 1, затем малые острова = 0, затем озёра = 2; пиксель попадает в маску, если его центр внутри полигона. Углы холста за пределами области (Арктика севернее 82° с. ш., Тихий океан восточнее 165° з. д.) — открытое море: источники туда не заходят, и в v1 эти места ошибочно становились «сушей без данных». Стадия 2 строит из маски `WBOD`/`WTBL` (ADR-0007 §3.2, §11 ниже). **Каспий** (проверено при Geo-3) лежит в слое `ne_10m_ocean` и получает код 1 — отдельная 4-связная компонента моря; Аральское море Natural Earth 1:10m показывает в современном (высохшем) виде, исторические поправки — Geo-6. Отдельный вид «внутреннее море» (`kind = 3`) стадия 1 не выделяет: ❓ словарь видов — Geo-5.

### 6.4. `coastline.pgl`, `rivers.pgl` — полилинии (PGL1)

Текст ASCII, перевод строки LF, поля через один пробел:

```
PGL1 <kind> <width> <height> <subpixel> <count>      kind: coastline | river; subpixel = 16
L <n> <rank> <points> <key>                          n = 1..count по порядку; rank 0..255; points ≥ 2; key [a-z0-9-]{1,28}
<x> <y>                                              points строк; целые в 1/16 пикселя, 0 ≤ x ≤ 16·width, 0 ≤ y ≤ 16·height
…
```

- Координаты в тех же единицах, что вершины `RVEC` (ADR-0007 §3.4): `x = round((X − origin_x)·16 / p)`, `y = round((origin_y − Y)·16 / p)`, округление половины вверх, вычисление в точной рациональной арифметике от десятичного текста GeoJSON (точность 1 м).
- `rank` — `scalerank` Natural Earth (меньше — значимее). `key` — ASCII-slug имени (`name`), иначе `-`.
- Линия, выходящая за холст, режется на куски внутри холста; соседние совпадающие точки удаляются; куски короче 2 точек отбрасываются.
- Реки Natural Earth здесь — для проверки и первичной разметки. По решению #96 основные русла строятся из DEM на стадии 2 (Geo-3/Geo-14).

### 6.5. Соответствие слоям PMD2

| Промежуточный файл | Чанк PMD2 (ADR-0007) | Кто преобразует |
|---|---|---|
| `height.i16` | `HGHT` (u16, `sea_level`, стилизация, врезка русел) | стадия 2 |
| `water.u8` | `WBOD` + `WTBL`, `MATL` воды | стадия 2 (§11) |
| `rivers.pgl` (+ DEM) | `RVEC`, `RIVR` | стадия 2 (Geo-14) |
| `coastline.pgl` | проверка согласования берега и маски | стадия 2 |
| `stage1.json` → `georef` | `GEOR` | копируется без изменений |
| `stage1.json` → `provenance` | `PROV` | дополняется `builder` |

## 7. Антимеридиан

Тайлы DEM западного полушария (Чукотка восточнее 180°, Аляска как фон) собираются в отдельный VRT. Его привязка сдвигается на +360° (`gdal_translate -a_ullr`), после чего он склеивается с восточными тайлами в одну мозаику с долготами 15…195°. Источник для `gdalwarp` задаётся как `+proj=longlat +datum=WGS84 +lon_wrap=180`, поэтому обратное преобразование выдаёт долготы в [0°, 360°) и попадает в сдвинутые тайлы. Векторы режутся двумя прямоугольниками `[15°, 180°]` и `[−180°, −165°]`, а затем проецируются: PROJ сам нормализует долготу относительно `lon_0 = 100°`. Пробный прогон подтвердил, что тайлы по обе стороны 180° легли одним непрерывным блоком (§9).

## 8. Проверки и детерминизм

`validate` (и конец `run`) проверяет:
- формат и версию `stage1.json`, наличие всех файлов, размер и SHA-256;
- размеры растров (`width·height·2` и `width·height` байт), порядок байт в ENVI-заголовке;
- коды маски воды только 0/1/2;
- высоты в пределах −450…9000 м;
- «дыры»: суша без данных DEM. Больше 1% пикселей суши — ошибка, меньше — предупреждение;
- разбор PGL1 и совпадение заголовков с размером холста.

**Детерминизм стадии 1** (ADR-0004 §3 п. 6) обеспечивают закреплённые версии GDAL/PROJ и скрипт:
- точное преобразование без аппроксимации (`-et 0`), `SAMPLE_GRID=YES`;
- целочисленные параметры холста; рациональная арифметика для полилиний.

Повторный прогон Albers на тех же данных дал побайтно одинаковые `height.i16`, `water.u8` и `rivers.pgl` при многопоточном `gdalwarp` (`NUM_THREADS=ALL_CPUS`). Бит-в-бит воспроизводимость **между** версиями GDAL не гарантируется; поэтому версии записываются в `stage1.json`.

## 9. Пробный прогон на реальных данных (2026-11-26)

Скачано в кэш (≈ 22 МБ): пять архивов Natural Earth (их SHA-256 и размеры записаны в манифест; статус набора остаётся `unverified`) и шесть тайлов GLO-90: `N65/N66 E179`, `N65/N66 W180`, `N66 W170` (мыс Дежнёва), `N55 E037` (Москва). Тайлы — во временном манифесте вне репозитория: полный список DEM записывается при полной загрузке (§4 п. 1).

Результат `run` для трёх проекций (≈ 50 с на проекцию):
- Чукотка из тайлов по обе стороны 180° легла непрерывно (столбцы 6161–6364 в `lcc`), Москва — в столбцах 1475–1570.
- Маска воды: ≈ 11,3–11,5 млн пикселей моря и ≈ 170 тыс. пикселей озёр.
- Береговая линия: ≈ 600 полилиний и 62 тыс. точек; реки — ≈ 560 полилиний и 72 тыс. точек.
- `validate` ожидаемо сообщает о «дырах» DEM: загружено 6 тайлов из тысяч.

Найдено и исправлено в ходе прогона: GeoJSON без EPSG-кода читается GDAL как WGS84, и `gdal_rasterize` молча не прожигал озёра. Поэтому полигоны для растеризации идут через GeoPackage.

Найдено при полном прогоне Geo-3: (1) углы холста вне области становились «сушей без данных» — теперь там море (§6.3); (2) рамка обрезки `-clipsrc` из четырёх углов после проекции давала хорды вместо дуг параллелей, и у южного края (Тихий океан, 28–33° с. ш.) оставалась ложная суша ≈ 1 млн пикселей — теперь рамка — файл `tmp/area_wgs84.geojson` с вершиной через 0,25° (`area_geojson`). После исправлений `validate`: 24 пикселя суши без данных DEM.

## 10. Ограничения и открытые вопросы

- Полный прогон (Geo-3, 2026-11-26): 6468 тайлов GLO-90, 19,25 ГиБ (оценка в 10 ГБ занижена вдвое); замеры и порядок — [geodata-howto.md](geodata-howto.md) §7. Запись полного списка тайлов с SHA-256 в манифест репозитория — вместе с переводом набора в `ready` (Geo-5).
- HydroLAKES (#78, CC BY 4.0) пока не подключён: структура архива [проверить] при загрузке; озёра — из Natural Earth.
- GLO-30 для детальных регионов (европейская Россия) — Geo-9.
- Береговая линия Natural Earth на севере России неточна (Geo-1): стадия 2 сверяет её с DEM.
- Исторические поправки (водохранилища XX века и т. п., ADR-0004 §6) — отдельный проход (Geo-6), не стадия 1.

## 11. Стадия 2: `mapgen --import` (Geo-3)

```powershell
mapgen --import <work>\lcc <выход> [--provinces 400 --seed 1 --threads 0 --zstd-level 3] [--preview карта.png]
```

Читает `stage1.json`, `height.i16`, `water.u8` (`read_stage1`, `src/mapdata/map_import.*`; JSON разбирает строгий `pat/core/json_reader.hpp`), строит пару слоёв (`import_stage1`), записывает `physical.pmd` и `provinces.pmd` (`write_map_set`), загружает их обратно через `load_map` и сверяет с построенной картой (код 3 при расхождении). Процедурный режим и `PMD1` по умолчанию не изменились (`mapgen --out`). GDAL не нужен. Результат бит-в-бит одинаков при любом числе потоков (тест `import: the result does not depend on the number of threads`).

Правила (все числа — **[предл.]**, константы в начале `map_import.cpp`):

| Слой | Правило |
|---|---|
| Вертикальная шкала | `metres_per_unit_milli = 150` (0,15 м на единицу), `sea_level = 8192`: представимы −1228,8 … +8601 м; выше/ниже — обрезка с подсчётом (`clamped`) |
| Высоты суши | DEM как есть (округление до единицы); суша с высотой ≥ 0 м не опускается ниже `sea_level + 1`; суша ниже нуля (Прикаспийская низменность) остаётся ниже `sea_level` — суша определяется `WBOD`, а не высотой (ADR-0007 §3.2) |
| Дыры DEM | суша без данных получает высоту ближайшего (обход в ширину по суше, в порядке строк) пикселя с данными; масса суши совсем без данных — 1 м |
| Водоёмы | 4-связные компоненты каждого кода в порядке строк: моря `sea`, `sea-2`…, озёра `lake`, `lake-2`…; Каспий — море (`kind = 1`, зеркало = `sea_level`) **❓ по умолчанию**: отдельный вид «внутреннее море» и его реальный уровень (−28 м) — после решения Geo-5 |
| Озёра | плоские: дно = зеркало = высота самого низкого пикселя суши на берегу (сток); озеро без берега — медиана своих отсчётов DEM |
| Дно моря | синтетическое: 48 единиц (7,2 м) на пиксель точного евклидова расстояния до ближайшего не-моря, не глубже −1228,8 м |
| Материалы | море: `DeepWater` глубже 2400 единиц, иначе `ShallowWater`; озеро — `ShallowWater`; суша по порядку: снег выше снеговой линии `4800 − 55·(φ − 28)` м, скалы при уклоне > 0,20 или в 1000 м под снеговой линией, тундра при `φ + h/300 > 67`, холмы при уклоне > 0,05 или выше 1500 м, пляж на берегу моря ниже 5 м, затем пояса: степь южнее 52° с. ш. (лесостепь с 50,5°), смесь леса и полей до 56,5°, лес севернее (с прогалинами до 60°). Границы поясов и тундры сдвинуты низкочастотным шумом генератора (`generated_noise`, до ±3° широты, длина волны ≈ 350 пикселей): параллель в конической проекции — длинная дуга или почти прямая, и без шума пояса выглядели как циркульные линии. Широта — обратная проекция `GEOR` (`pat/mapdata/geo_projection.hpp`, эллипсоид WGS84, сверено с PROJ) |
| `GEOR`, `PROV` | `GEOR` из `stage1.json`; `PROV` = провенанс стадии 1 (`sha256: null` → нули, число таких файлов печатается) + `builder = "mapgen import"` + шаг `import:stage2-v1` (хеш параметров) |
| Провинции | **заглушка** до оцифровки границ (Geo-7, #83): разбиение суши тем же алгоритмом, что у процедурной карты (`partition_provinces`, `--provinces`, `--seed`), плюс по провинции на каждую массу суши, куда не попало ни одного зерна (острова); ключи `p0001`…, `PROV` шаг `provinces:placeholder-v1` |

Острова: граф провинций реальной карты несвязен, поэтому для карт с привязкой (`GEOR projection ≠ none`) связность графа больше не требуется (`validate_province_graph` — только для процедурных карт); ❓ решение владельца — #786.

Не входит в Geo-3 (следующие задачи): русла из DEM и чанки `RIVR`/`RVEC` (`rivers.pgl` пока не читается; Geo-14 — формат готов), сверка `coastline.pgl` с маской, регионы `NREG`, стилизация рельефа и очистка DSM от леса, исторические поправки (Geo-6).

Известное ограничение отображения: спайк и шейдер считают водой `высота ≤ sea_level` (из `MapData`), поэтому суша ниже нуля (север Прикаспия) рисуется водой, а озёра выше уровня моря — плоской сушей цвета воды. Исправление — передать в рендер маску `WBOD` (задача рендера, не формата).
