# contentlint: проверка контента и локализации

> Статус: E4-T08 (готово). Код — `tools/contentlint` (библиотека `patriarch::contentlint` + программа `contentlint`), тесты — `tests/contentlint_test.cpp` и ctest `contentlint_*`, корпуса — `tests/data/contentlint/{good,bad/*}`. Зависит только от `core`, `data`, `loc`, `content`, `sim` — без движка, собирается и на Linux.
> Формат `.pd` — [data-format.md](data-format.md), загрузка корней — [data-loader.md](data-loader.md), локализация — [localization.md](localization.md), руководство автора — [data-authoring.md](data-authoring.md).

## 1. Что делает

Одна команда проверяет **весь контент и все таблицы строк** и печатает **все** найденные проблемы (не только первую), отсортированно:

1. **Контент** — каждый корень читается загрузчиком (`load_content` со схемами `content_schemas()`): синтаксис `.pd`, типы и диапазоны (`PD0xx`, `PD101…PD110`), повторы и неразрешённые ссылки между объектами (`PD111`, `PD112`), нечитаемые файлы (`PD113`), миграции (`PD114`). Если загрузка прошла без ошибок, на том же реестре запускаются сборщики правил экономики и демографии (`build_economy_rules`, `build_demography_rules`): правила **между** объектами, например два товара с одним `slot`, — `PD115`. Загрузка выполняется один раз, диагностики не дублируются. При ошибках загрузки сборщики пропускаются (строка `note:` об этом): их входной реестр неполон.
2. **Локализация** — таблицы `loc/<язык>/**/*.pd` всех корней читает `pat::loc::load_localization`: синтаксис сообщений, плюрализация, повторы ключей (`LC001…LC016`, см. [localization.md](localization.md) §7).
3. **Покрытие переводов** — по данным `Localizer::coverage()` (ключи языка сравниваются с языком по умолчанию; коды `CL001…CL003`, `CL006`).
4. **Ссылки на ключи** — ключи, на которые никто не ссылается (`CL004`), и ключи из явного списка, которых нет в таблицах (`CL005`).

Проверка [определений M1](m1-definitions.md) также выполняется после успешной загрузки.
Она проверяет слоты навыков и черт, ссылки из модификаторов навыков и взаимность
противоположных черт. Для сопоставления провинций с картой сценарий вызывает
`content::bind_pmd1_provinces()` с конкретной картой.

## 2. Запуск

```powershell
contentlint [--root DIR]... [--lang ru] [--fallback en[,de]] [--strict] [--format text|github]
            [--used-keys FILE]... [--scan DIR]... [--no-scan] [--ignore-unused ПРЕФИКС]...
            [--no-unused] [--no-rules] [--help]
.\out\win-msvc\tools\contentlint\Debug\contentlint.exe --root data --strict --ignore-unused ui.
```

| Параметр | Смысл |
|---|---|
| `--root DIR` | корень контента; повторяется: первый — база игры, следующие — моды (как в `load_content`). По умолчанию `data` |
| `--lang CODE` | язык, на котором написаны тексты, эталон покрытия (по умолчанию `ru`) |
| `--fallback CODE[,CODE]` | языки, у которых **должны** быть таблицы (цепочка после основного), например `en`; нет таблицы — `CL006` |
| `--strict` | предупреждения считаются ошибками (в выводе они печатаются как `error`, код выхода 1) |
| `--format text` / `github` | обычные строки или аннотации GitHub Actions (§4) |
| `--used-keys FILE` | список ключей, на которые ссылается код или данные: по одному в строке, `#` — комментарий; повторяется |
| `--scan DIR` | каталог для поиска ссылок на ключи (повторяется); заменяет умолчание |
| `--no-scan` | искать ссылки только в самих корнях контента |
| `--ignore-unused ПРЕФИКС` | ключи с этим префиксом никогда не считаются неиспользуемыми (повторяется) |
| `--no-unused` | не проверять неиспользуемые ключи |
| `--no-rules` | пропустить проверки между объектами (проверка мода без базы или маленького корпуса) |

Параметры со значением можно писать и как `--root=DIR`.

## 3. Коды выхода

| Код | Когда |
|---|---|
| `0` | нет ошибок (и нет предупреждений при `--strict`) |
| `1` | есть хотя бы одна ошибка (при `--strict` — и предупреждение) |
| `2` | ошибка использования или ввода-вывода: неизвестный параметр, нет значения, корень или `--scan` — не каталог, не читается `--used-keys`, неожиданное исключение |

Программа не падает на мусоре: пустые и обрезанные файлы, нули и невалидный UTF-8, вложенность в десятки тысяч скобок, гигантские числа и строки — всё это превращается в диагностики (тесты `contentlint: garbage input…`).

## 4. Формат вывода

`text` (по умолчанию): `файл:строка:столбец: error[КОД]: сообщение`, как в [data-authoring.md](data-authoring.md) §3, но без префикса `[root N '…']` — путь уже включает каталог корня (`data/economy/goods.pd:12:5: …`). Строки и столбцы с 1; для проблем без позиции пишется только файл, для общих — только `error[КОД]: …`. Предупреждения — `warning[КОД]: …`. Сортировка по `(файл, строка, столбец, код, сообщение)`, порядок вывода не зависит от порядка обхода каталогов. После проблем идут строки `note: …` (что просканировано, что пропущено, покрытие по языкам) и итог `contentlint: N object(s) checked, E error(s), W warning(s)`.

`github`: те же проблемы в виде команд рабочего процесса, которые GitHub показывает как аннотации к файлу и строке:

```
::error file=data/economy/goods.pd,line=12,col=5,title=PD111::unresolved reference: …
::warning file=data/loc/ru/ui.pd,line=40,col=1,title=CL004::key 'ui.x' is not referenced by any scanned file
```

Спецсимволы экранируются по правилам GitHub (`%`, переводы строк, а в имени файла и заголовке ещё `:` и `,`). Строки `note:` и итог — обычный текст в журнале.

## 5. Коды `CL`

| Код | Уровень | Смысл | Место |
|---|---|---|---|
| `CL001` | предупреждение | ключ есть в языке по умолчанию, но нет в языке X | определение в языке по умолчанию |
| `CL002` | предупреждение | ключ есть в языке X, но нет в языке по умолчанию (лишний, опечатка в ключе) | определение в языке X |
| `CL003` | предупреждение | у ключа другой набор параметров, чем в языке по умолчанию (`{n}` против `{m}`) | определение в языке X |
| `CL004` | предупреждение | ключ языка по умолчанию не упоминается ни в одном просканированном файле (§6) | определение ключа |
| `CL005` | **ошибка** | ключ из `--used-keys` не определён ни в одном языке цепочки | строка списка |
| `CL006` | предупреждение | у языка из `--lang`/`--fallback` (или у языка по умолчанию, когда другие таблицы есть) нет таблиц | — |

Остальные коды приходят от загрузчиков без изменений: `PD…` (данные и синтаксис), `LC…` (таблицы строк).

## 6. Неиспользуемые ключи: источники ссылок и эвристика

Единственный надёжный источник — явный список `--used-keys` (его можно получить, например, из логов `requested_missing_keys()` или сгенерировать). Кроме него по умолчанию просматриваются:

- файлы `*.pd` самих корней вне `loc/` (`name_key = "trait.greedy.name"`);
- каталоги `src` и `apps` **рядом с первым корнем** (для `--root data` это репозиторий): файлы `*.cpp`, `*.hpp`, `*.h`, `*.cc`, `*.rml` (файлы больше 8 МБ пропускаются). `--scan DIR` заменяет этот выбор, `--no-scan` отключает его.

Эвристика: текст разбивается на токены из символов `[A-Za-z0-9_.]`; токен (без ведущих и замыкающих точек), равный ключу таблицы языка по умолчанию, считает ключ использованным — в кавычках, в разметке, в комментарии, где угодно. Токен, заканчивающийся точкой и содержащий не менее двух точек (`"ui.month."` — ключи собираются на лету: `"ui.month." + name`), считает использованными все ключи с таким префиксом.

Ограничения (поэтому `CL004` — предупреждение):

- **ложные «неиспользуемые»**: ключ строится сложнее, чем префикс + имя; читается из файла, которого нет среди просканированных; — добавьте его в `--used-keys` или `--ignore-unused ПРЕФИКС`;
- **ложные «используемые»**: ключ упомянут только в комментарии или в строке, не имеющей к тексту отношения.

Ссылки на несуществующие ключи эвристика **не находит** (она ищет только известные ключи); их ловит `CL005` по явному списку и, во время работы, `Localizer::requested_missing_keys()` (заполнитель `[[ключ]]`).

**Временное исключение в CI.** Таблица `data/loc/ru/ui.pd` написана заранее, окна UI пока используют зашитые литералы, поэтому на `data/` линтер вызывается с `--ignore-unused ui.`. Когда UI начнёт читать таблицу (подключение к `Localizer`), параметр нужно убрать в `.github/workflows/ci.yml` и в `tools/contentlint/CMakeLists.txt`.

## 7. CI и тесты

- **CI**: job `contentlint` в `.github/workflows/ci.yml` — минимальная сборка на Linux (`linux-gcc` без тестов и бенчмарков, цель `contentlint`) и запуск `contentlint --root data --strict --ignore-unused ui. --format github`.
- **ctest**: `contentlint_data_clean` (реальный `data/` зелёный), `contentlint_good_corpus` (маленький полный корпус зелёный при `--strict`), `contentlint_detects_{schema,reference,loc_duplicate,loc_plural}` (корпуса ошибок в `tests/data/contentlint/bad/`; шаблон `WILL_FAIL`, как у `schemadoc_check_detects_diff`: линтер обязан завершиться с ненулевым кодом).
- **doctest** (`tests/contentlint_test.cpp`): точные коды и позиции на тех же корпусах, формат GitHub, коды выхода 0/1/2, сортировка и детерминизм, мусорные входы, покрытие, неиспользуемые ключи, разбор `--used-keys`.

## 8. Как добавить проверку

1. Новая проверка — функция в `tools/contentlint/lint.cpp`, которая добавляет `Finding` (`make_finding(Severity::Warning|Error, файл, позиция, "CL0nn", текст)`) в `Report::findings` до сортировки. Место (файл и позиция) берите у источника проблемы (`Localizer::origin`, `LoadError`), чтобы аннотация попала на нужную строку.
2. Предупреждение или ошибка? Проверка, которая может ошибаться (эвристика), — предупреждение: `--strict` в CI всё равно превратит его в ошибку, но локально им можно пренебречь. Нарушенное правило данных — ошибка.
3. Добавьте код в таблицу §5 и тест в `tests/contentlint_test.cpp` (на нужном корпусе в памяти — `MemorySource`).
4. Правила, которые знает только потребитель контента (например, согласованность провинций карты и определений, E4-T05), делайте сборщиком в `src/content` с кодом `PD115`; линтер подхватит его, добавив вызов рядом с `build_economy_rules` в `lint()`.
