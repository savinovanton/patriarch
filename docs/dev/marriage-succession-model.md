> Статус: **спецификация v1** (2026-11-13), задача E8-T01 ([#296](https://github.com/savinovanton/patriarch/issues/296)). ## 1. Что здесь решено и что нет

Документ фиксирует **форму состояния и контракты**, а не баланс:

1. какие таблицы и колонки добавляет E8 в `World`, их типы, единицы, диапазоны, кто пишет и кто читает (§4);
2. какие статьи ведомости и проводки нужны, как устроены приданое, возврат и вдовья доля (§5);
3. в каком порядке и когда работают системы, какие очереди и потоки ГСЧ (§6);
4. команды: теги блока 64…95, поля, кто выпускает, `validate` и коды причин отказа (§7);
5. формулы допустимости, оценки партии, порядка наследования, спора, регентства, узурпации — таблицами со значениями `[предл.]` (§8) и их `Breakdown` (§9);
6. события для E11 и интерфейсы к E10/E12/E14/E15/E17/E31 (§10);
7. данные (§11), инварианты (§12), сейв, хеш, миграция, golden (§13), бюджеты (§14);
8. контракты моста «снапшот → UI» для UI-D09 (доски 04–08, 12, 13) и «Совета рода» (доски 60–64, 71, 80) (§15);
9. соответствие историям, #263 и #265 (§16), открытые вопросы (§17), правки других документов (§18), поправки к задачам T02…T25 (§19).

## 3. Типы и единицы

| Величина | Тип | Единица / диапазон |
|---|---|---|
| Деньги | `int64` (`economy::Kopecks`) | копейки; все суммы E8 ≥ 0 (знак задаёт статья) |
| Даты | `Date` (`kNoDate` = нет) | юлианский календарь, дни |
| Очки (`accept_score`, `council_score`) | `int32` | «очки», усечение к нулю; веса — промилле (`_permille`, 1000 = ×1,0) |
| Вероятности | `int32` | промилле, 0…1000 |
| Мнение | `Fixed32` −100…100 | как E7-T17 |
| Честь | `int32` −1000…10000; единство `Fixed32` 0…100 | как E7-T14 |
| Идентификаторы записей | `u32`, растут, **не переиспользуются** (счётчик в сейве) | `0` недопустим |
| Перечисления в сейве | `u8` / `u16` | числа навсегда, значения только добавляются в конец |
| Степень родства | `u8` 0…15; 0 = нет связи в пределах поиска | римский счёт: вверх до общего предка + вниз (§8.2) |

Весь расчёт — целые и `Fixed`; `float`/`double`, `unordered_*`, `rand` запрещены (AGENTS.md §5.1). Порядок обхода — по возрастанию id или явному ключу; ничьи — по `(birth_date, id)`.

## 4. Таблицы

Все — члены `World` (приватные, доступ через методы; `const`-чтение для снапшота), все копируются со снапшотом и входят в `operator==`. Размеры ограничены константами, превышение — отказ команды (`TableFull`), а не рост без предела.

### 4.1 `NegotiationTable` — переговоры (идущие)

Строки по возрастанию `id`, ≤ `kMaxNegotiations = 512` `[предл.]`. Существует только состояние «идёт»: завершённые уходят в кольцо исходов (§4.2).

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `u32` | номер из `next_negotiation_id` |
| `initiator` | `DynastyId` | дом, пославший посредника (актор) |
| `groom`, `bride` | `CharacterId` | участники; живые, на момент отправки допустимые (`check_marriage`) |
| `groom_house`, `bride_house` | `DynastyId` | дома участников **на момент отправки** (для разбора, если потом сменится дом) |
| `sent`, `answer_due` | `Date` | дата отправки и срок ответа (`sent + answer_days`) |
| `cost_kop` | `i64` | фактически списано одной проводкой `marriage_envoy` (дорога + дары + дозволение) |
| `dowry_kop` | `i64` | приданое по правилу на момент отправки; на нём строится ответ и помолвка |
| `dowry_source` | `DynastyId` | дом, платящий приданое (обычно `bride_house`; для вдовы с требованием — дом покойного мужа, §5.3) |
| `dispensation` | `u8` | 1 — оплачено «дозволение Церкви» (степени 5–6, Q1) |
| `dowry_tier` | `u8` | **резерв M2** (торг): всегда 0 |
| `state` | `u8` | `1 Pending`; значения 2… — резерв M2 (`Countered`) |

### 4.2 `NegotiationOutcomeRing` — итоги ответов (кольцо 64)

Нужен, чтобы тултип отказа и летопись объясняли ответ **после** того, как состояние мира изменилось (прошлые разложения не пересчитываются — economy-model §10).

| Колонка | Тип | Смысл |
|---|---|---|
| `seq` | `u32` | порядковый номер исхода (растёт) |
| `negotiation` | `u32` | номер переговоров |
| `initiator`, `groom`, `bride`, `responder` | id | дом-ответчик — `responder` |
| `sent`, `answered` | `Date` | |
| `result` | `u8` | `1 Accepted` (создана помолвка), `2 Refused`, `3 Withdrawn`, `4 Void` (участник умер/стал недопустим) |
| `reason` | `u16` | при `Void` — первый код `MarriageDenial`; при `Refused` — код слагаемого с наименьшим вкладом (`ScoreTerm`); иначе 0 |
| `score`, `threshold` | `i32` | итог и порог |
| `terms[8]` | `i32` | слагаемые верхнего уровня в порядке `ScoreTerm` (§8.4); `Σ terms == score` |

### 4.3 `BetrothalTable` — помолвки

По возрастанию `id`, ≤ `kMaxBetrothals = 1024`.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `u32` | `next_betrothal_id` |
| `groom`, `bride`, `groom_house`, `bride_house` | id | как в переговорах |
| `contracted` | `Date` | |
| `wedding_not_before` | `Date` | не раньше: максимум из дат совершеннолетия жениха (16 лет) и невесты (15), `contracted + wedding_delay_days` |
| `wedding_deadline` | `Date` | `wedding_not_before + wedding_grace_days`; по истечении без свадьбы помолвка снимается (`GraceExpired`) |
| `dowry_kop`, `dowry_source` | `i64`, `DynastyId` | договорное приданое и плательщик |
| `claim_marriage` | `u32` | если приданое — вдовья доля, номер брака-источника (§5.3), иначе 0 |
| `dispensation` | `u8` | дозволение оплачено |
| `origin` | `u8` | `1 Negotiation`, `2 Command` (договор, событие, сценарий) |

Участник состоит **не более чем в одних активных переговорах или помолвке** (инвариант §12); индекс `engagement_[id]` (`0` нет, `1` переговоры, `2` помолвка) — производный, не сохраняется, пересобирается при загрузке и поддерживается инкрементально.

### 4.4 `MarriageTable` — записи браков, заключённых по правилам E8

По возрастанию `id`, ≤ `kMaxMarriageRecords = 4096`; при заполнении вытесняется самая старая **завершённая** запись без требования (`claim_kop == 0`).

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `u32` | `next_marriage_id` |
| `groom`, `bride`, `groom_house`, `bride_house` | id | `bride_house` — дом **происхождения** невесты (куда возвращается приданое) |
| `wedding` | `Date` | |
| `dowry_kop` | `i64` | выплачено при свадьбе |

### 4.5 `PersonStatusTable` — статусы персонажей

По возрастанию `character`; строка есть, только если хотя бы одно поле не по умолчанию.

| Колонка | Тип | Смысл |
|---|---|---|
| `character` | `CharacterId` | живой или архивный |

Пострижённый — вне рынка браков, наследования, регентства, должностей; лишённый прав — вне наследования, регентства, уделов и не может быть предложен в брак своим домом (§8.1). Оба статуса необратимы в M1 (команда «помиловать» — M2).

### 4.8 `DisputeTable` — споры о наследстве

По возрастанию `dynasty`, ≤ 1 на род.

| Колонка | Тип | Смысл |
|---|---|---|
| `dynasty` | `DynastyId` | |
| `predecessor` | `CharacterId` | умерший глава |
| `reason` | `u8` | `1 CloseScores`, `2 UnpopularHeir`, `3 NoAppointment` |
| `opened`, `resolve_by` | `Date` | `resolve_by = opened + dispute_days` |
| `claimants_n` | `u8` | 2…4 |
| `claimants[4]` | `{CharacterId, i32 score}` | очки и порядок претендентов на момент открытия, по убыванию очков, затем `(birth_date, id)`; порядок сохраняется для временного управления (#486) |

Пока спор открыт, `head` рода **пуст**: ни политика E8, ни запасное правило E7 окончательного главу не назначают. Родом управляет `caretaker` — первый живой претендент из сохранённого порядка на момент открытия; при его смерти действует следующий (#486). Это производный запрос над `claimants`, без отдельной колонки или нового раздела сейва. Умершие претенденты остаются в снимке порядка; временная власть не означает окончательный титул. Пределы отдельных полномочий уточняются до T16; случай малолетнего управляющего требует решения до T17 (§17, #491).

### 4.9 `LandGrantTable` — уделы (Q3, вариант A)

По возрастанию `province`: `{province, holder, granted_on}`. Держатель — взрослый член рода; он же управитель провинции (`administrator`, E9) и получает лояльность. Провинция остаётся собственностью рода. Смерть держателя: удел возвращается главе (система находит по таблице, §6.3).

### 4.11 Оценка памяти

Таблицы вместе при типичной партии (≈ 100 родов, 30 переговоров, 100 помолвок, 1 500 записей браков за 75 лет, 200 статусов): ≤ 150 КБ, при пределах констант — ≤ 400 КБ. Бюджет раздела сейва E8 — ≤ 100 КБ на 100 родов (эпик §6.5).

### 5.2 Расходы

| Событие | Кто платит | Проводка | Условие |
|---|---|---|---|
| `SendMarriageEnvoy` | `initiator` | `post_money(initiator, marriage_envoy, −cost)` **одной** проводкой; `cost = road + gifts + dispensation` (разложение — `Breakdown`, §9) | казна ≥ `cost` (`can_afford`: долг ничего не покупает, как у стройки); без экономики расход 0 |
| Свадьба | `dowry_source` → дом жениха | `transfer(dowry_source, groom_house, dowry_out, dowry_in, dowry_kop)` | всегда; казна может уйти в минус (долг — состояние E9); при насыщении двигается меньшая сумма (правило `transfer`) |
| Возврат при пострижении | дом жениха → `bride_house` | `transfer(groom_house, bride_house, dowry_out, dowry_in, refund)` | `refund = dowry_kop × tonsure_refund_permille / 1000` (500‰ `[предл.]`, Q4) |
| Вдовья доля | дом покойного мужа → дом нового жениха | `transfer(groom_house_old, new_groom_house, dowry_out, dowry_in, claim)` | при свадьбе вдовы, §5.3 |
| Реформа закона | род | `post_money(dynasty, court_upkeep, −reform_money_kop)` одной проводкой (статья 103 уже выпущена E9) | казна ≥ цены (`can_afford`), §8.8; новая статья не нужна |
| Отозванный посредник | — | возврат `withdraw_refund_permille` (0‰ `[предл.]`) через `post_money(…, marriage_envoy, +x)` | без нового кода |

Мир без экономики: все денежные шаги — пустые (`can_afford = true`, проводок нет), приданое хранится числом, но не двигается; `check_invariants` не требует баланса.

### 5.3 Вдовья доля (Q5 #293)

Модель без личных денег:

1. При свадьбе приданое уходит дому жениха (§5.2). В записи брака `dowry_kop` зафиксировано.
2. Когда **муж умер**, принадлежность жены к дому определяется отдельным решением D13/#488; её регентство в роде ребёнка не требует переноса (#487). Запись переходит в `Widowed`, а `claim_kop = dowry_kop × widow_claim_permille / 1000` (1500‰ `[предл.]`: приданое целиком плюс «вдовья часть» имущества 500‰). Деньги не двигаются: требование — обязательство дома мужа перед вдовой.
3. Пока вдова остаётся в доме, требование молчит; когда она умирает, требование **снимается** (запись `Closed/BothDead`, деньги остаются у дома).
4. Когда вдова **выходит замуж** (в другой дом), приданым нового брака становится её требование: `dowry_source = groom_house_old`, `dowry_kop = claim_kop` (а не стандартное приданое дома происхождения); требование исполняется `transfer`-ом при новой свадьбе, запись прежнего брака закрывается. Если новый муж — из дома покойного (внутри рода) — требование снимается без выплаты.
5. Вдовец — ничего.

Так выполняются инварианты: деньги не создаются и не теряются (все движения — `transfer`), возврат при пострижении ≤ выплаченного, вдова «сохраняет приданое и вдовью долю» (Q5).

## 6. Время: системы, порядок, очереди, случайность

### 6.1 Системы E8

Ставятся **отдельной функцией** `install_family_systems(simulation, content)` после систем E7 (`dynasty.*`) и до `economy.*`; до E8-T24 в `dynasty.v1` не входят. Каждая система — без собственного состояния (всё в `World`), эффекты — внутренние команды (применяются в начале следующего тика).

| № | Имя | `Cadence` | Что делает |
|---:|---|---|---|
| 1 | `marriage.negotiations` | Daily | обходит `NegotiationTable`; для строк с `answer_due ≤ today` считает ответ (§8.4) и выпускает `RespondMarriage`; строки с умершим участником — `RespondMarriage{Void}` |
| 2 | `marriage.weddings` | Daily | обходит `BetrothalTable`: `wedding_not_before ≤ today` и допустимо — `Wed`; участник умер/недопустим или `wedding_deadline < today` — `BreakBetrothal{Void…}`. Также обходит `MarriageTable`: активная запись с мёртвым супругом — `SettleWidowhood` |
| 3 | `marriage.godparents` | Daily | от `godparent_cursor` до `capacity`: для живых новорождённых без крёстных — `AssignGodparents` (§8.7); курсор двигается командой (сейв самодостаточен) |
| 4 | `marriage.matchmaker` | Daily | ИИ-подбор (§8.9): род по слоту `is_monthly_slot(dynasty.index, today)`, не более одного предложения за слот |
| 5 | `succession.regency` | Daily | обходит `RegencyTable`: совершеннолетие подопечного → `DismissRegent{Majority}`; регент/подопечный умер → пере-назначение или конец; годовщина проверки → бросок и `RegencyCheck` (§8.6) |
| 6 | `succession.dispute` | **Monthly** | по `DisputeTable`: ежемесячное падение единства (`AdjustUnity`); `resolve_by ≤ today` → два броска и `ResolveSuccessionDispute`. Заодно: род без главы, без спора, без регентства и не вымерший → открыть/назначить заново (страховка, §8.5) |

Порядок «ответ → свадьба → крёстные → подбор → регентство → спор» нужен затем, чтобы подбор ИИ видел состояние после сегодняшних ответов и свадеб, а проходы по малым таблицам не зависели друг от друга. Все обходы — по возрастанию `id`/ключа; параллельное исполнение не используется (`SerialExecutor`).

Хук цикла «глава умер» (D8): `Simulation::tick`, блок «Resolve against the final membership» вызывает `config.succession_policy->resolve(world, dynasty, predecessor) → ordered internal commands` вместо `fallback_successor`; без политики — как в E7.

### 6.2 Очереди и даты

Очередей-индексов E8 **не заводит**: все таблицы малы (≤ 512/1024/4096 строк), обход при ежедневном запуске стоит доли микросекунды (§14), а состояние — только в таблицах, поэтому «загруженный» и «непрерывный» мир не различаются. Исключение — `godparent_cursor` (состояние, сохраняется).

Даты срабатывания — **значения в строках** (`answer_due`, `wedding_not_before`, `wedding_deadline`, `resolve_by`, годовщины регентства `started + n лет` по правилу `anniversary_in_year`). «Ровно в срок» означает: обработка в первый запуск системы с `дата ≥ срок`; повторно строка не обрабатывается, потому что команда-результат её удаляет или двигает счётчик (`checks_done`, `next_*`). Ничья на один день — по возрастанию `id`.

Сейв **мира** (не симуляции) между выпуском внутренней команды и её применением теряет её, как у смертности и родов (ADR-0006 S4); продолжение восстановит событие на следующий день, потому что состояние в таблицах не изменилось. Сейв **симуляции** несёт `pending_internal` и не расходится.

### 6.3 Реакции на смерть (D7)

| Событие | Кто и когда | Что |
|---|---|---|
| Умер участник переговоров/помолвки | `World::die` (синхронно) | строка удаляется; в кольцо исходов — `Void` с `reason = NotAlive`; помолвка — запись летописи; деньги за посредника не возвращаются |
| Умер супруг по записи `Active` | система 2, день 1 после смерти | `SettleWidowhood`: `widowed_on`, `Widowed` + требование, траур, летопись |
| Умер действующий регент / подопечный | система 5 | регент — назначается следующий по приоритету (§8.6); подопечный — это и есть умерший глава, запускается преемство |
| Умер держатель удела | система 5 (проход по `LandGrantTable`) | удел снят, управитель провинции снят |
| Умер назначенный наследник / опекун | не чистится сразу | при следующем применении закона запись признана недействительной; `check_invariants` разрешает «умершего» в этих полях (как мнения в ADR-0006 D1) |

### 6.4 Потоки ГСЧ

| Поток | Кто | Сколько бросков |
|---|---|---|
| `dynasty.regency` | `succession.regency` | **1** `bounded(1000)` на годовую проверку регента, всегда (проверка опасна, если бросок `< risk_permille`) |
| `dynasty.dispute` | `succession.dispute` | **2** на разрешение спора, всегда: (1) вмешательство императора `bounded(1000)` против `imperial_intervention_permille`; (2) победитель — взвешенный выбор `bounded(Σ весов)` |

Больше случайности в E8 нет: ответ рода, свадьба, ИИ-подбор, крёстные, порядок наследования — детерминированные функции состояния. Потоки создаются по имени при первом броске; существующие потоки и хеши демо не меняются. Случайное решает **система при эмиссии**, `apply` — чистая бухгалтерия (правило E7-T12).

### 7.2 Общие правила `validate` / `apply`

1. Отказ — `Rejection` (`UnknownEntity`, `NotAuthorized`, `InvalidArgument`, `InvalidState`) + `detail` + `code` (F6): `code` — первая причина из набора `MarriageDenial`/`SuccessionDenial` (§7.3, §7.4), **полный список** даёт чистая функция (`check_marriage`, `check_succession_command`), которую вызывает UI.
2. `apply` предполагает пройденную `validate` против того же состояния, ничего не решает случайно и не проверяет заново; все эффекты — детерминированная бухгалтерия.
3. «Действующий глава» (`acting_head`, T17): кроме `AssignRegent`/`DismissRegent` и внутренних, команды E8 требуют, чтобы у дома-актора он был (иначе `NoActingHead`).
4. При регентстве запрещены `ChangeSuccessionLaw`, `SetHeir`, `Disown`, `GrantLand`, `Tonsure` (причина `RegencyActive`): регент не должен перекраивать род в свою пользу; браки и помолвки разрешены. При открытом споре действует `caretaker` по #486: сам факт спора не означает общего отказа `NoActingHead`/блокировки управления. Пределы отдельных полномочий управляющего согласуются до T16 (§17).
5. Расход (`SendMarriageEnvoy`) списывается в `apply` ровно одной проводкой; проверка средств — в `validate` (`can_afford`) по **тем же** `Breakdown`-функциям, что показывает UI.

### 8.2 Родство: кровное, свойство, духовное (Q1 #289)

**Степень — римский счёт:** число шагов вверх от одного до ближайшего общего предка плюс число шагов вниз до другого (родные братья — 2, дядя и племянница — 3, двоюродные — 4, двоюродная племянница — 5, троюродные — 6). Из-за ограничения «до 6-й» достаточно подниматься на **3 поколения** с каждой стороны: предки до 3-го колена (≤ 14) пересекаются за O(14²) на пару, без обхода всего рода.

| Вид | Правило (значения — данные) | Результат |
|---|---|---|
| Кровное | степень ≤ `blood_forbidden_degree` (6 `[предл.]`): 1–4 — абсолютный запрет; 5–6 — **дозволение** | коды 30 / 31 |
| Свойство | родственник нынешнего **или бывшего** (в т. ч. умершего) супруга: степень связи с супругом = степень свойства; запрет ≤ `affinity_forbidden_degree` (4 `[предл.]`); пары среди `spouse` и `ex_spouses` обоих | код 32 |
| Духовное | по колонке `godparent[2]` (E7-T03): (1) крёстный ↔ крестник; (2) крёстный ↔ родитель крестника (кумовство); (3) два крестника одного восприемника | код 33, всегда |

Счёт и числа подлежат сверке по источникам отдельной проверкой данных (Q1); `[проверить]` остаётся в данных, не в коде. В `check_marriage` вычисляется `KinResult {blood_degree, affinity_degree, spiritual}` (0 = нет связи в пределах поиска); UI показывает «Близкое родство» / «Не выявлено» (макет 05).

### 8.4 Оценка партии и `accept_score` (T05)

Одна функция `score_match(world, rules, view_house, own_member, other_member, dowry, role) → ScoreBreakdown` считает 8 слагаемых с точки зрения дома `view_house`; **ответ рода** — это значение с точки зрения `responder`, **оценка партии для игрока** — с точки зрения инициатора (то же значение, те же слагаемые).

| № (`ScoreTerm`) | Код `Breakdown` | Слагаемое | Формула (целые, усечение к нулю) | Вес `[предл.]` |
|---:|---:|---|---|---|
| 0 | 10001 | `honor_gap` | `clamp(honor_other − honor_own, −600, 600) × w / 1000` | `honor_weight` = 150‰ |
| 1 | 10002 | `rank_gap` | `−rank_step_penalty × max(0, rank_own − rank_other)` (ранги по `rank_thresholds`, F4) | 40 за ступень |
| 2 | 10003 | `dowry` | `± dowry_kop × dowry_points_per_100rub / 10000`; «+», если `view_house` получает приданое (дом жениха), «−», если платит | 4 очка за 100 ₽ (`dowry_points_per_100rub`; приданое 270 ₽ ≈ ±11) |
| 3 | 10004 | `relation` | `dynasty_relation(own, other) × w / 1000` (§8.4.1) | `relation_weight` = 500‰ |
| 4 | 10005 | `opinion_of_proposer` | мнение действующего главы `view_house` об инициаторе (E7-T17) × `w` | 500‰ |
| 5 | 10006 | `member_quality` | (здоровье − 50) × 200‰ + (плодовитость − 50) × 200‰ (**только** для невесты) + (сумма навыков − 40) × 150‰ | дети слагаемых: 10010 `health`, 10011 `fertility`, 10012 `skills` |
| 6 | 10007 | `age_gap` | `−age_gap_penalty × max(0, модуль разницы возрастов − age_gap_free)` | 8 за год сверх 10 |
| 7 | 10008 | `external` | `political_gain` (10009) + `faith_penalty` (10013): в M1 = 0, хуки E12/E15/E31 | — |

`accept_score = Σ terms`; **согласие**, если `accept_score ≥ accept_threshold` (0 `[предл.]`); результат всегда определяется состоянием на день ответа, без ГСЧ. Для равных по чести и рангу домов со стандартным приданым и нулевыми отношениями ответчик-жених (получает приданое) даёт счёт ≈ +20 — согласие, ответчик-невеста (платит) — ≈ 0…+5, то есть граничный случай, который решают честь, отношения и качество партии; при разнице чести 400 и ранга в ступень счёт ≈ −80 — отказ с понятной причиной. Калибровка весов — T24. Монотонность: растёт при росте чести инициатора, отношений, качества участника; падает при росте приданого, которое платит ответчик.

**Последствия ответа** (`RespondMarriage.apply`):

| Исход | Эффекты |
|---|---|
| Согласие | строка переговоров → помолвка (`Betrothal` с датами по §4.3, `origin = Negotiation`, `dowry_kop` из строки); при `dispensation` — честь инициатору `−dispensation_honor`; мнение дома-ответчика об инициаторе `+marriage_accepted_opinion` (+5); запись в кольцо и летопись |
| Отказ | строка удалена; мнение ответчика об инициаторе `−marriage_refused_opinion` (−5, причина 101); пара блокируется на `refusal_cooldown_days`; запись в кольцо (слагаемые) и летопись; деньги не возвращаются |
| `Void` | участник умер/стал недопустим: строка удалена, кольцо с `reason`; мнение не меняется |

**Прогноз для UI** (`forecast`): корзина «вероятно / неясно / маловероятно» по сумме **публичных** слагаемых (0–3 и 6: честь, ранг, приданое, отношения родов и возраст) относительно порога с допуском `forecast_margin` (15); непубличные (4, 5, 7) в прогноз не входят, так что ответ не раскрывается заранее; полная раскладка показывается только после ответа.

**Реализация T05** (`src/sim/marriage_rules.hpp`, `marriage_score.hpp`; тесты `tests/marriage_score_test.cpp`). `evaluate_match(world, rules, groom, bride, dowry, MatchContext)` считает оба взгляда сразу (`MatchEvaluation.scores[Groom/Bride]`), `accept_score(eval, side, Breakdown*)` отдаёт нужный вместе с деревом 10000. Сверх таблицы выше (значения `[предл.]`, все — в `MarriageRules::defaults()`): **коридоры** — слагаемое приданого ограничено ±`dowry_points_cap` = 30, политвыгода ±`political_gain_cap` = 30, штраф веры 0…`faith_penalty_cap` = 100, разница возрастов считается не более `age_gap_years_cap` = 30 лет сверх свободных десяти; граница каждой шкалы — `term_bounds`/`score_bounds`. Слагаемое 5 считается по **партнёру** (тому, кого дом принимает), плодовитость — только когда им является невеста. Мнение (слагаемое 4) — действующий глава дома ответчика об главе дома-инициатора; для дома самого инициатора и без инициатора — 0. `dynasty_relation` (слагаемое 3), политвыгода и штраф веры приходят числами `MatchContext` (`relation` — из T06, хуки — из E12/E15/E31; в M1 нули), у политвыгоды и штрафа веры — по числу на каждый дом. Причина отказа — код `Breakdown` слагаемого с наименьшим значением (при равенстве — первого по порядку `ScoreTerm`). Добавлен код **10204** `dowry_limit` (зажим к коридору приданого, чтобы дерево 10200 складывалось точно).

#### 8.4.1 `dynasty_relation(a, b)` — «Отношения родов» (#263 п. 5)

Целое −100…100: среднее ненулевых мнений, которые хранят живые члены дома `a` о членах дома `b` и наоборот (E7-T17; пара «действующий глава ↔ действующий глава» исключается — она отдельное слагаемое 4), плюс `marriage_tie_bonus` (+5 `[предл.]`) за каждый живой брак между домами (не более 3), без изменения исходных мнений. Разложение: `opinion_mean` (10020), `marriage_ties` (10021). Бейдж макета «Отношения родов +24» — это значение.

### 8.5 Порядок наследования `resolve_successor` (T14)

`resolve_successor(world, rules, dynasty, predecessor) → SuccessionResult {winner, order[], kind, dispute?}`; `order[]` — полный упорядоченный список с причиной каждой строки (`HeirReason`: 1 `EldestSon`, 2 `YoungestSon`, 3 `Appointed`, 4 `CouncilChoice`, 5 `SonLine` (внук по сыну), 6 `Daughter`, 7 `DaughterLine`, 8 `Brother`, 9 `Nephew`, 10 `Kin`), по нему строятся «первый наследник / следующий по линии» (макет 60).

**Допустимость кандидата** (для всех законов): живой член рода; не пострижён и не лишён прав; законный или узаконенный (`illegitimate_inherit = no` `[предл.]`); не сам предшественник. Несовершеннолетние допустимы (будет регент, §8.6).

**Женщины** (GDD 01 §6.2): `female_succession = if_no_adult_male` — женщина допустима, только если среди допустимых **нет живых совершеннолетних мужчин рода**, либо она названа по закону «назначение»; значения `never`, `always` — данные. Глава-женщина получает `female_head_honor` (−10, причина «женщина-глава») и маркер повышенного риска оспаривания (хук для E17/E12).

**Построение порядка** — классы по GDD 01 §6 в таком порядке: (1) линия сыновей предшественника, (2) линия дочерей, (3) братья и их линии, (4) племянники и их линии, (5) прочие члены по близости родства. Внутри линии — **обход потомков в порядке старшинства с представлением**: для каждого ребёнка по порядку закона — он сам (если допустим), затем его потомки (если он мёртв или недопустим, потомки встают на его место, прежде следующих детей). Детей сортирует `(birth_date, id)`.

**Подтверждено #485:** при майорате допустимый внук от умершего старшего сына занимает место старшей ветви и идёт раньше живого младшего сына; сначала все живые дети, а лишь затем внуки — неверный порядок.

| `Minorat` | младший первым | первый в порядке | — |
| `Partition` | как `Majorat` | первый в порядке | удел-раздел остальным взрослым сыновьям (§8.10) |
| `Appointment` | — | `designated_heir`, если допустим; иначе — **спор** (`NoAppointment`) | порядок для показа — как `Majorat` |
| `FamilyCouncil` | по очкам совета | кандидат с наибольшим `council_score`, если отрыв ≥ `council_clear_margin`; иначе **спор** (`CloseScores`) | детерминированные очки, без голосования (Q2 #290) |

**Очки совета** (`council_score`, очки): навыки `(сумма пяти) × 400‰` (0…40) + возраст `min(max(age − 16, 0), 34) × 500‰` + близость (сын +30, дочь +15, брат +20, племянник +10, прочие 0) + симпатия `среднее мнение других взрослых членов × 500‰` (±50) + `loyalty_head × 200‰` (±20) + благочестие `piety × 100‰` (0…10) − 10 за статус «узаконенный» − 15 за пол «женщина» (если допущена). `council_clear_margin = 15`. Разложение — `Breakdown` (§9).

**Спор из-за непопулярного наследника** (законы майорат/минорат/раздел): если у законного наследника `support < dispute_support_threshold` (−20; `support` = среднее мнение других взрослых членов + `loyalty_head × 500‰`), и есть соперник — второй в порядке взрослый кандидат, чьи очки совета не ниже очков наследника, — открывается спор (`UnpopularHeir`). Включается флагом `unpopular_dispute_enabled`.

**Претенденты спора** — до 4 лучших по очкам совета в пределах `dispute_margin` (20) от лучшего (законный наследник всегда включён); очки претендента = `council_score + (законный наследник ? lawful_bonus = 10 : 0) + (назначенный ? 20 : 0)`.

**Временное управление (#486):** первый претендент в сохранённом порядке на момент открытия становится `caretaker`; `acting_head` возвращает его, не назначая окончательным главой. При смерти управляющего берётся следующий живой претендент в том же порядке; изменение текущих очков само по себе не переставляет управляющих. Итог спора определяется отдельно. Пределы отдельных команд уточняются до T16; исполнение власти малолетнего caretaker согласуется до T17 (§17, #491), автоматическое регентство над ним этим решением не вводится.

**Страховка:** род без главы, без спора, без регентства и не вымерший (например, глава лишён звания событием) получает преемника тем же алгоритмом при `predecessor = invalid` — классы строятся от «ближайшего по линии» к последнему умершему главе (хранится в летописи `HeadChanged`) или, если его нет, по `council_score`.

### 8.6 Регентство (T17)

**Когда:** победитель преемства моложе 16 лет → он становится главой (`Succeed`), и в тот же тик назначается регент (`AssignRegent`). **Кандидаты** — живой, совершеннолетний, допустимый (не пострижён, не лишён прав) член рода **либо мать-вдова другого рода**, кроме подопечного и смещённого (`excluded`), по приоритету (GDD 01 §6.3, порядок — данные `regent_priority`):

| Приоритет | Кандидат | `RegentKind` |
|---:|---|---|
| 1 | мать подопечного (вдова предшественника), в том числе другого рода без смены её принадлежности (#487) | 1 Mother |
| 2 | опекун по завещанию (`guardian`) | 2 Guardian |
| 3 | старший по возрасту совершеннолетний дядя по отцу | 3 Uncle |
| 4 | кандидат с наибольшим `council_score` среди совершеннолетних | 4 Council |
| 5 | никто — опека короны (E12) | 5 Imperial |

**Полномочия матери по #487 не зависят от D13/#488:** она сохраняет свой род; власть над родом ребёнка даёт строка `RegencyTable`. `Command::actor` остаётся `DynastyId` **управляемого рода**, а действующее лицо и основание его полномочий определяются через `acting_head`/регентство, без подмены актора родом матери. Для остальных кандидатов действует обычное требование членства. При `Imperial` регента нет, действующий глава — подопечный (игрок не блокируется), проверки узурпации нет; E12 позже подменяет `AssignRegent` на назначение опекуна.

**Годовая проверка** (`succession.regency`, в годовщину `started`): `RegencyCheck{dynasty, risk_permille, usurp}`; бросок — `dynasty.regency`, `usurp = roll < risk_permille` (всегда один бросок).

```
risk_permille = clamp(regency_base_permille
                      + A × D × W / regency_divisor
                      + trait_mods + (50 − unity) × unity_weight, 0, regency_cap)
A = max(0, ambition_regent)                       0…100
D = (100 − loyalty_head_regent) / 2               0…100   (лояльность главе = подопечному)
W = clamp((16 − age_ward) × 5 + (100 − health_ward) / 2, 0, 100)   слабость наследника
```

Для матери другого рода `loyalty_head` относится к главе **её** рода, а не автоматически к подопечному. Источник лояльности ребёнку и применение этой ветви риска требуют решения до T17 (§17); #487 не утверждает подмену значения или новое поле состояния.

| Ключ | `[предл.]` | Смысл |
|---|---:|---|
| `regency_base_permille` | 15 | фон |
| `regency_divisor` | 2500 | при A=60, D=60, W=65 даёт ≈ 94‰ |
| `unity_weight` | 2 | слабое единство повышает риск |
| `regency_cap` | 600 | |
| `trait_mods` | по таблице «черта → ‰» | «честолюбивый» +40, «верный» −30 и т. п. (каталог E7-T08) |

Пример: мать (A=10, D=10, W=65): ≈ 2,6‰ + 15‰ ≈ 18‰ в год; честолюбивый дядя (A=60, D=60): ≈ 110‰ в год. **Узурпация** (`usurp = 1`, исход M1 — `seize`): регент становится главой (`SetDynastyHead` внутри `RegencyCheck.apply`), регентство снимается, подопечный остаётся членом рода; единство `−usurpation_unity` (15), честь `−usurpation_honor` (20); мнения членов о регенте `−30`; хук `on_regent_usurpation` (E11) и точка расширения E14 (устранение подопечного).

Для чужеродной матери этот `seize` **не определён**: прямой `SetDynastyHead` нарушит членство главы в роде. #487 разрешает регентство с сохранением рода, но не захват главенства, перенос матери или другой исход; механический эффект требует отдельного решения до T17 (§17).

**Смещение** (`DismissRegent{Dismissed}`): допустимо, если `support = Σ` по взрослым членам: `(−opinion_of_regent) × 500‰ + (loyalty_head_member − 0) × 100‰` ≥ `dismiss_support_threshold` (60 `[предл.]`) **или** последний `last_risk_permille ≥ dismiss_risk_threshold` (100‰); цена — единство `−5`, честь `−10`; назначается следующий кандидат (регент не возвращается). **Конец** — день 16-летия: `DismissRegent{Majority}`, ровно раз (строка удаляется той же командой).

### 8.7 Крёстные (T13, решение #135)

`AssignGodparents{child, godparents[2]}` выпускается для живого новорождённого, чей id ≥ `godparent_cursor`. Кандидаты: живые взрослые (≥ 16) члены рода отца и (если иной) рода матери, кроме родителей, ребёнка и **его родных братьев/сестёр**; оценка кандидата = `(член рода отца ? 20 : 10) + мнение родителей о нём (среднее, ±50 × 300‰) + близость родства (дядя/тётка +10) − 5 за каждые 10 лет разницы с 35 годами`; выбираются двое лучших (по возрастанию `(−score, id)`), восприемник-мужчина и восприемница-женщина, если есть в списке (иначе любые двое); если кандидатов меньше двух — столько, сколько есть. ### 8.9 ИИ-подбор партий `marriage.matchmaker` (T20)

В слот рода `is_monthly_slot(dynasty.index, today)` ИИ-род (не из `player_dynasties`, их список передаёт сценарий в `MatchmakerContent`; игрок управляет своими членами сам):

1. берёт **одного** члена: взрослого, свободного, не в переговорах/помолвке, не лишённого прав/пострижённого, по `(birth_date, id)`;
2. обходит `world.living()` одним проходом, дешёвый предфильтр (пол, возраст, `engagement_`, не свой дом, не из дома игрока `ai_may_propose_to_player = no`), затем `check_marriage`;
3. для оставшихся считает `score_match` с точки зрения своего дома и — зная ответ — `accept_score` ответчика (детерминированно, ИИ «знает» правила); отбрасывает тех, кому ответ — отказ, и тех, у кого `match_value < matchmaker_min_value` (0);
4. выбирает максимум по `(match_value ↓, id ↑)` и, если казна позволяет, выпускает `SendMarriageEnvoy` (обычная команда, актор — свой дом).

Один бросок ГСЧ не нужен. Результат зависит только от состояния и слота, поэтому воспроизводим. Бюджет: § 14.

### 8.10 Раздел и уделы (T18, Q3 #291)

При `Partition` после `Succeed` система выпускает `PartitionEstate{dynasty, predecessor, assignments}`: провинции рода, которыми прежде управлял глава (или вся `provinces_of`, если управителей нет), делятся между **взрослыми сыновьями предшественника, кроме нового главы**, поровну по числу провинций с остатком старшим; порядок — по `(birth_date, id)` сыновей и по возрастанию `province` (детерминированно). Каждому достаются `LandGrant`, управитель (`AssignProvinceAdministrator` внутри `apply`), `loyalty_head +10`, и (если вышло ≥ 1) своя **ветвь** (`create_branch` без имени; UI подписывает «Ветвь <имя>»). Провинции остаются у рода (`owner` не меняется). `GrantLand` — то же для одной провинции по воле главы: `+10` лояльности держателю; прежний держатель (если был) лояльность `−5`.

### 13.2 Хеш и версия схемы

- **Части хеша** (`ExtPart`, блок 8…15, ADR-0006 D7): 8 `Negotiation` (раздел 17 вместе с счётчиками), 9 `Betrothal`, 10 `MarriageRecord`, 11 `PersonStatus`, 12 `Succession` (раздел 21: наследники, уделы, курсор), 13 `Regency`, 14 `Dispute`, 15 — резерв. Часть **0 и вне `total`**, пока таблица пуста; хеш — FNV по строкам в порядке хранения (как `pregnancy_hash`). Поэтому мир без данных E8 имеет прежний `total`.
- **`kStateSchema`**: на 2026-11-13 равна 11 (E7-T12); T03 берёт **первый свободный номер на момент слияния** (по текущему состоянию — 12) и поднимает его **один раз** на все таблицы, раздел 36 экономики (коды 16 и 112, §5.1) и часть ADR-0011. Остальные задачи E8 схему не меняют. Любое изменение байтов после T03 — отдельный подъём (ADR-0011 §7).
- **Миграция «N−1 → N»:** пустые таблицы E8, `next_* = 1`, `godparent_cursor = 0`; ledger-раздел старого файла читается по кодам (новые строки нулевые). Шаг — типизированный, над загруженным миром.
- **Фикстуры** (чек-лист §7.4 `save-format.md`): прежняя схема уже представлена (`tests/data/saves/dynasty_v11_pregnancy.psv`, схема 11), но в ней нет экономики, поэтому **первым коммитом T03, до правок формата**, кодом `main` создаётся ещё одна фикстура прежней схемы — мир с экономикой, займом и закрытым месяцем (проверка раздела 36 и хеша счетов при добавлении кодов); вторым — фикстура новой схемы с переговорами, помолвкой, регентством, спором и уделом. Тест читает обе, сверяет хеши и пересохраняет в те же байты.
- Корпус порчи (T11 E13): усечения, битые перечисления, раздутые счётчики для **каждого** из разделов 16…23.

### 13.3 Хеш счетов экономики стабилен по кодам (F3)

В `world_economy_io.cpp` подхеш `Accounts` сейчас включает `kLines` и все плотные строки. T03 меняет его так, чтобы прежние миры хешировались **теми же числами**: хешируются первые `kLegacyLedgerLines = 31` строк позиционно и `u64 kLegacyLedgerLines` вместо `kLines`; строки кодов, выпущенных позже (16, 112 и последующие), входят парами `(u16 код, i64 значение)` в порядке возрастания кода **только если ненулевые**. Тест: хеш M1-экономики, `simcli_m1` и фикстур экономики не меняются. Если реализатор сочтёт это нецелесообразным, единственная допустимая альтернатива — один согласованный в issue пересчёт golden экономики в T03 (не «по ходу»).

| Что | Когда меняется |

### 15.4 Контракты и риски моста

1. **Команда в паузе (F7).** Команды применяются внутри `Simulation::tick`; в паузе макеты показывают результат немедленно. Рекомендация (решение владельцу, Q8.7): команда E8 в паузе исполняется как `Runner::step(1)` (один день), что безопасно для реплея и детерминизма; мост не придумывает «применить без тика». До решения мост показывает `Submitting` до следующего снапшота.
2. **Снапшот.** Мост работает от иммутабельной копии `World` (ADR-0002 P5), не обращается к потокам симуляции.
3. **Причины — стабильные числа.** UI берёт текст по `(команда, code)`; новых «жёстких» строк нет.
4. **Реформа и `SetHeir` из карточки персонажа.** Кнопка «Назначить наследником» на досках 12/13 при законе, отличном от «назначения», открывает реформу `Майорат → Назначение` с предвыбранным наследником (одна команда `ChangeSuccessionLaw{Appointment, heir}`), а не отдельное действие.
