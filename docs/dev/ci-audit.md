## 3. Находки

### 3.1. Кэш vcpkg на Windows не работает (hit rate 0 %)

Шаг `Cache vcpkg binaries` находит ключ `vcpkg-Windows-<hash(vcpkg.json, CMakePresets.json)>` (179 МБ), но vcpkg пишет `Restored 0 package(s)` и собирает все 14 портов заново в каждом Windows-job (benchmark, freetype, rmlui, sdl3 и т. д.: ~2.2 мин). Причина: ключ не зависит от образа раннера. Кэш создан 2026-11-11, образ `windows-2022` с тех пор обновился (сейчас `20261112.366.7`), хеш компилятора в ABI vcpkg изменился, а `actions/cache` при точном совпадении ключа ничего не сохраняет, поэтому устаревший кэш не обновляется никогда (до правки `vcpkg.json`). На Linux кэш работает (`Restored 7 package(s)` за 0.1 с), но job Tracy каждый раз собирает `tracy` и `pthreads`: общий ключ ОС сохраняет job без фичи `tracy`.

Потери: ~2.2 мин × 5 Windows-job ≈ 11 мин раннеров за прогон, −2 мин критического пути; плюс Performance.

### 3.2. ctest идёт последовательно

В тестовых пресетах нет `execution.jobs`, а CI не передаёт `-j`. Тесты регистрирует `doctest_discover_tests`: 1340–1624 процессов на прогон, по одному на тест-кейс. Под ASan запуск процесса дорогой, отсюда 19.3 мин; в Tracy-сборке клиент Tracy стартует в каждом процессе (7.3 мин против 1.0 мин у обычного gcc Debug). У раннеров 4 vCPU. Параллельному запуску ничего не мешает: временные файлы и каталоги в `tests/` именованы уникально для каждого тест-кейса (`TempDir` добавляет метку времени; `fresh_dir`/`temp_path` и фикстуры окон используют разные имена).

### 3.3. MSBuild собирает проекты по одному, clang-cl — по одному файлу

`cmake --build --preset win-*` без `--parallel` запускает MSBuild без `/m`: в логе один узел (`1>`), проекты идут строго друг за другом. У cl.exe внутри проекта есть `/MP` (`cmake/PatriarchCompileOptions.cmake`), а у clang-cl `/MP` нет, поэтому clang-cl компилирует файлы проекта последовательно: `patriarch_tests` в clang-cl debug собирается 6.5 мин, вся сборка 10.4–14.9 мин против 5.3–9.6 у MSVC.

### 3.4. Отмена push-прогонов на `main`

`concurrency: ci-${{ github.ref }}` с `cancel-in-progress: true` действует и на `main`: при частых слияниях 31 из 40 push-прогонов отменены, то есть результат слияния на `main` проверяется полностью редко. Для PR это правильно (новый push заменяет старый). Это не ускорение, а вопрос покрытия; вынесено на решение владельца (§5).

### 3.5. Флак `Performance regression`

11 провалов из 74. В разобранных провалах сборка проходит, а вердикт — `Performance: regression`: `bench_gate.py` меряет сначала baseline, потом candidate (по ~25 с), один раз; дрейф производительности общей ВМ между двумя фазами превышает порог 10 %. Job не на критическом пути (7.7 мин) и запускается только при изменениях `src/core`, `src/sim`, `bench`, CMake, `vcpkg.json`. Варианты исправления меняют чувствительность гейта — на решение владельца (§5).

### 3.6. Прочее

- **Таймауты.** У job в `ci.yml` нет `timeout-minutes` (по умолчанию 360 мин): зависший тест (например, рендер или ожидание ввода) держит раннер 6 часов и блокирует очередь. У Performance таймаут 40 мин есть.
- **Повторы конфигурации.** Каждый из 11 сборочных job отдельно поднимает vcpkg и конфигурирует CMake (на Windows 3.4–3.8 мин, из них ~2.2 мин — сборка портов из §3.1). После исправления кэша остаётся ~1 мин на job; объединение job ради этого не окупается (растёт время прогона).
- **Дубли сборок.** `contentlint` собирает себе отдельную Linux-сборку (2.2 мин), хотя тот же бинарник собирается в `Linux gcc RelWithDebInfo`; `Linux gcc Debug` и `Linux gcc Tracy client` — две Debug-сборки GCC, отличающиеся только Tracy. Объединение меняет состав/имена проверок — на решение (§5).
- **Кэш компиляции** (ccache/sccache) не используется. На Linux сборки 3–5.5 мин, не на критическом пути; на Windows sccache требует генератор Ninja вместо `Visual Studio 17 2022`, то есть CI начнёт собирать иначе, чем локально. Пока не предлагается.
- **Фильтры `paths`** в `ci.yml` (`'**'`, `'!**/*.md'`, `'docs/dev/data-reference.md'`) корректны: изменения только в `*.md` CI не запускают, генерируемый справочник схем проверяется. Риск на будущее: если владелец включит защиту `main` с обязательными проверками CI, PR только с `*.md` будет ждать проверки, которая не запустится; тогда нужен job-заглушка или `paths` внутри job. В `performance.yml` фильтры соответствуют тому, что влияет на замер.
- **Артефакты и логи** небольшие: `bench-smoke` (JSON) на каждый прогон MSVC, отчёт clang-tidy, отчёт Performance (10 файлов), логи тестов только при падении; хранение 7–14 дней. Кэши занимают ~1.3 ГБ из 10 ГБ лимита репозитория. Менять нечего.

## 5. На решение владельца (меняют состав проверок или покрытие)

Оформлены отдельным issue `type:decision` + `needs:owner` (номер — в §6).

1. **Отмена прогонов на `main`.** Вариант: `cancel-in-progress` только для `pull_request`; на `main` прогоны идут в очереди (GitHub держит один ожидающий, промежуточные пропускаются). Плюс: каждое состояние `main` после серии слияний проверено полностью. Минус: больше занятых раннеров в часы слияний, PR чаще ждут в очереди.
2. **Флак Performance.** Варианты: (а) чередовать замеры baseline/candidate (ABAB…) и сравнивать медианы; (б) при вердикте `regression` перемерить обе стороны и падать только при повторе; (в) поднять порог с 10 % (ослабляет гейт); (г) на PR только отчёт, падение — в ночном прогоне. (а)/(б) правят `tools/bench_gate.py`, гейт не ослабляют, но меняют его поведение.
3. **Перенос части job с PR на push в `main` / ночь** (Tracy, clang-tidy report-only, clang-cl debug). Экономия раннеров ~30 мин за прогон PR, но ошибка обнаружится уже после слияния.
4. **Объединение дублей:** `contentlint` как шаг `Linux gcc RelWithDebInfo` (−2.2 мин раннера, исчезает отдельная проверка с этим именем); `Linux gcc Debug` убрать, если достаточно Debug-сборки с Tracy (теряется проверка Debug без Tracy).
