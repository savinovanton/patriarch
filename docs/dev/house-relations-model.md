## 3. Состояние

### 3.1 Уровни

```
enum class FeudLevel : u8 { None = 0, Cooling = 1, Rivalry = 2, Feud = 3 };
```

Уровень **направленный**: `level(holder, target)` определяется мнением `opinion(holder → target)` (`Fixed32`). У пары два уровня; **эффективный** уровень пары — больший из двух (решение по [#526](https://github.com/savinovanton/patriarch/issues/526), вариант A).

| Уровень | Вход: мнение ≤ | Остаётся, пока мнение ≤ (гистерезис 8) | Название в игре |
|---|---:|---:|---|
| `Cooling` | −20 | −12 | «Охлаждение» |
| `Rivalry` | −40 | −32 | «Соперничество» |
| `Feud` | −65 | −57 | «Вражда» |

Правило (`feud_level_for(opinion, current, rules)`): `next = max( max L : opinion ≤ enter[L] , max L ≤ current : opinion ≤ stay[L] )`, `None`, если множества пусты. Чистая функция, без `float`.

### 3.2 Таблица `FeudTable`

Разреженная, по возрастанию `(lo, hi)`, `lo < hi` — идентификаторы персонажей одного рода. Строка (24 байта):

| Поле | Тип | Смысл |
|---|---|---|
| `lo`, `hi` | `u32`×2 | пара, `lo < hi` |
| `level_lo_hi` | `u8` | уровень `opinion(lo → hi)` |
| `level_hi_lo` | `u8` | уровень `opinion(hi → lo)` |
| `peak` | `u8` | наибольший уровень текущего эпизода (сбрасывается примирением) |
| `flags` | `u8` | бит 0 `Dirty` (пересчитать завтра), бит 1 `Reconciled` (была формальное примирение) |
| `since` | `i32` | день, когда эффективный уровень пары последний раз **вырос** (для «свежести» §7.3) |
| `truce_until` | `i32` | день конца перемирия; `kNoDate` — нет |
| `mediation_ready` | `i32` | день, с которого снова можно посредничать; `kNoDate` — можно |

Строка существует, пока выполнено хотя бы одно из: любой уровень > 0; `truce_until > today`; `mediation_ready > today`; `Dirty`. Иначе её удаляет `SetFeudLevel.apply` (или месячный проход). Потолок таблицы — **4 096 строк** `[предл.]` (§15); при переполнении вытесняется строка с наименьшим эффективным уровнем (ничья — наименьший `(lo, hi)`), её уровень будет выведен заново из мнений.

Методы `World` (индексируемое состояние — только через них): `feud_rows()`, `feud_pair(a, b)`, `feud_level(holder, target)`, `feud_effective_level(a, b)`, `set_feud_level(holder, target, level, today)` (из `SetFeudLevel.apply`), `begin_truce`, `set_mediation_ready`, `mark_feud_dirty(a, b)`; `die` вызывает `erase_feud_pairs_of(c)`.

### 3.3 Почему таблица, а не только вывод

| Вариант | Итог |
|---|---|
| Только производная «по требованию» | Отвергнут: нет гистерезиса (уровень мерцает на пороге при каждом `AdjustOpinion`), нет `from → to` для `on_feud_level_changed`, негде хранить перемирие и кулдаун посредничества |
| Поле уровня в записи мнения `OpinionEntry` | Отвергнут: меняет раскладку раздела 6 и хеш мнений **всех** миров, пара становится несимметричной |
| **Разреженная таблица пар (выбрано)** | Малая (сотни строк), «пустое не пишется», не трогает раздел мнений; истина по-прежнему в мнениях — таблица лишь кэш с памятью |

### 3.4 Объём

Ожидаемо 1…5 % живых персонажей участвуют в паре уровня ≥ 1 → 250…1 000 строк × 24 Б = 6…24 КБ; потолок 4 096 строк = 96 КБ. Раздел сейва ≤ 100 КБ, хеш — один проход.

## 4. Причины

### 4.1 Принципы

1. Причина — **наблюдаемое событие или состояние мира**, а не бросок: «глава назначил наследником младшего», «родственник получил должность, на которую подходил ты».
2. Причина записывается как слагаемое мнения под своим кодом `OpinionReason`; поэтому разложение «почему мне не нравится брат» уже есть в `opinion_sources` и в тултипе (до 3 причин и «прочее», F1).
3. Причины двух видов: **разовые** (событие → дельта один раз) и **давление** (пока условие истинно, раз в месяц — шаг к потолку; после — обычное затухание).
4. Давление ≥ 2 очка/мес (F2); один шаг = `min(шаг, потолок − |вклад кода|)`; вклад кода читается из `opinion_sources` (детерминированно).
5. Сумма «чужих» причин E8/E10 (201…205, 301…303) учитывается как есть: E7-T25 их **не дублирует**.

## 5. Расчёт уровней

### 5.1 Проход по держателю (месячный слот)

Для каждого живого `holder` с `is_monthly_slot(holder.value(), today)` (в порядке возрастания id):

1. **Давление** (§4.3, причины 42а, 48, 49): для каждой пары `(holder, target)`, подходящей условию, `add_opinion` шаг (с потолком, §4.1 п. 4); перемирие подавляет 42 и 48 (§5.3).
2. **Оценка**: по каждой записи `opinions_from(holder)` с мнением ≤ `enter[Cooling]`, а также по каждой строке таблицы, где `holder` — сторона, считается `feud_level_for` и сравнивается с хранимым.
3. Для расхождения система выпускает `SetFeudLevel{holder, target, level, reason}` (≤ одной на пару в день; порядок — `(holder, target)` по возрастанию).

Записи, где `holder`/`target` умер, чистятся прежним `decay_opinions`; строки таблицы с умершим удаляет `die`.

### 5.2 Проход A (ежедневный, дешёвый)

Строки с `Dirty` или `truce_until ≤ today` или `mediation_ready ≤ today`: пересчитать оба направления теми же функциями, сбросить `Dirty`; закончилось перемирие — `SetFeudLevel{…, TruceEnded}`; кулдаун прошёл — очистка поля. Такие строки бывают единицами в день. Метку `Dirty` ставят `MediateFeud`, `GiftToMember` и хуки причин §4 (`relations::apply_cause`); изменения мнений, сделанные кодом E8/E10 без хука, видны **в слот держателя, не позже чем через 28 дней**.

### 5.3 Перемирие

После режима «примирить» пара получает `truce_until = today + truce_months` (24 мес `[предл.]`). Пока перемирие действует: (1) давления 42 и 48 на этой паре **не применяются**; (2) эффективный уровень, вычисленный из мнений, ограничивается `Cooling` для последствий §6; (3) если мнение любого направления опускается до `enter[Rivalry]`, значит, разовая причина действительно возобновила ссору: `SetFeudLevel{…, TruceBroken}` сбрасывает перемирие, последствия возвращаются. Отдельного «свежего оскорбления» не нужно.

### 5.4 Пример временной шкалы (расчёт на бумаге, проверит E7-T37)

Старший сын 24 лет `proud` назначен наследником; брат 22 лет `proud`, очки совета рядом, остался вторым. Месячный шаг: `HeirRivalry` −3, `TraitClash` −2, итог −5, затухание +1 → чистый −4/мес до потолков: через 5 мес −20 (`Cooling`), через 10 −40 (`Rivalry`: вклады −30 и −20 упираются в потолки, мнение −44…−50). Глава умирает: `Succeed` и спор → `HeirRivalry` б) −4 и `DisputeLoser` −20: мнение проигравшего → победителя ≈ −65…−70 → `Feud` на 3…4-й месяц. После `MediateFeud` (мощность 24 → +12 с каждой стороны) и перерыва в 180 дней, ещё одного посредничества и `Reconcile` — перемирие на 24 мес.

## 6. Последствия

### 6.1 По уровням `[предл.]`

Эффективный уровень пары = больший из двух направленных (§3.1). Единство и совет считают пару один раз.

| Уровень | Единство, очков/мес на пару | Сотрудничество (`factor`) | Совет рода | Прочее |
|---|---:|---:|---|---|
| `Cooling` | −0,5 | 1,00 | — | значок в окнах; событие «охлаждение» (по желанию контента) |
| `Rivalry` | −1,5 | 0,75 | `council_score` кандидата −5 за каждого соперника-избирателя (≤ −15) | события «соперничество» раз в 12 мес по паре |
| `Feud` | −3,0 (оба направления: −4,0) | **0 — отказ** ([#529](https://github.com/savinovanton/patriarch/issues/529)) | −10 за каждого врага-избирателя (≤ −30); враг не может быть регентом/опекуном противника | события «вражда» раз в 6 мес по паре; отказ службы |

Потолок давления на единство рода **−6 очков в месяц** `[предл.]`; при потолке в журнале единства есть причина `HouseConflict` (§11).

### 6.2 Единство

Система `dynasty.relations.unity` раз в месяц: по строкам таблицы суммирует давление по родам; `AdjustUnity{dynasty, −min(Σ, cap), reason = kStandingReasonHouseConflict (10)}` (только ненулевые). Дрейф E7-T14 (+1/мес к 50) остаётся: охлаждение (−0,5) его не перебивает, соперничество на одной паре снижает единство на ≈ 0,5 в месяц, вражда на одной паре — на ≈ 2 в месяц. Примирение возвращает единство `+2` разово (`reason = 11 Reconciliation`).

### 6.3 Функция `cooperation`

```
Cooperation cooperation(const World&, const RelationsRules&, CharacterId a, CharacterId b, CooperationKind kind);
struct Cooperation { std::int32_t factor_permille; FeudDenial denial; }  // 1000 = полностью, 0 + denial = отказ
enum class CooperationKind : u8 { Marriage, Office, Council, Regency, Order };
```

Чистая, читает только `FeudTable` и мнения; разложение — `Breakdown` 15200. Потребители:

| Кто | Где | Что делает |

| E8 | `check_marriage`/`validate` `SendMarriageEnvoy` | если `level(M → acting_head) = Feud` для члена M — отказ `MarriageDenial::FeudRefusal` с причиной в тултипе; `AssignGodparents` — штраф кандидата −∞ при `Feud` с родителем |
| E8 | `council_score` | слагаемое `feud_penalty` (§6.1) |
| E8 | `AssignRegent` | враг рода-опекаемого — не кандидат |
| E10 | `validate` `AssignOffice`/`PetitionForOffice` | при `Feud(M → acting_head)` кандидат M отказывается: `OfficeDenial::FeudRefusal` |
| E10, E10-T22 | эффект должности и портфеля | умножает силу на `factor` пары `(holder, acting_head)` (0,75 на соперничестве) |
| E17 (M2) | `OrderMember` | отказ при `Feud`, мягче при `Rivalry` |

Решения [#529](https://github.com/savinovanton/patriarch/issues/529) (принуждение за цену) и [#526](https://github.com/savinovanton/patriarch/issues/526) меняют только данные и один флаг «вопреки» в командах потребителей.

## 7. Примирение

### 7.1 Способы

| Способ | Что даёт | Кто платит |
|---|---|---|
| **Время** | затухание 1 очко/мес; постоянные причины (42, 48) продолжают давить, пока верны условия | — |
| **Посредничество** (`MediateFeud`, режим `Soften`) | +Δ к мнению каждой стороны о другой, кулдаун 180 дней | деньги рода |
| **Примирение** (`MediateFeud`, режим `Reconcile`) | подтягивает мнения до пола −10, перемирие 24 мес, единство +2 | деньги рода |
| **Дар** (`GiftToMember`) | получатель → глава +, получатель → его враг +½ | деньги рода |
| **Брак** | компенсационный брак обиженного (причина 53), межродовое +10 `MarriedInto` (E8) | условия брака |
| **События E11** | эффекты `mediate_feud`, `gift_to_member`, `change_opinion` (54, 55) | по событию |

Цена: по решению владельца ([#527](https://github.com/savinovanton/patriarch/issues/527)) **деньги рода (статья 106) или ресурс «влияние»**, выбор при каждом действии — поле `pay` команд 23 и 24; у действия две цены в данных, обе видны в предпросмотре ([influence-model.md](influence-model.md) §6; значения влияния — «3,0 × уровень» для смягчения и «6,0 × уровень» для примирения `[предл.]`).

### 7.2 `MediateFeud{a, b, mode}`

`Command::actor` — род, чей глава посредничает; обе стороны — живые взрослые члены этого рода. Режимы: `Soften = 1`, `Reconcile = 2`.

**Допустимость** (`validate`, все отказы — коды `FeudDenial`): режим допустим для данного состояния; `a ≠ b`; нет строки пары или эффективный уровень 0 → `NoConflict`; `mediation_ready > today` → `OnCooldown`; `Reconcile` при уровне `Feud` в любом направлении → `FeudTooDeep` (сначала смягчить); недостаточно денег на счёте рода → `NotEnoughMoney`.

**Если глава — сторона** (посредничать некому): мощность ×0,5, цена ×1,5 `[предл.]` — глава «уступает сам».

**Мощность** (`mediation_power`, очки, `Breakdown` 15000):

```
power = 10                               (15001 основа)
      + навык «Дипломатия» главы         (15002, 0…20)
      + (opinion(a→head) + opinion(b→head)) / 20   (15003 уважение, −10…+10)
      + бонус черт главы                 (15004: diplomat +4, courtier +2, merciful +2, cruel −3, proud −2)
      − 8, если эффективный уровень вырос менее 90 дней назад (`since`)   (15005 свежесть обиды)
      − 4 × (уровень − 1)                (15006 глубина ссоры)
Δ = clamp(power / 2, mediate_min = 3, mediate_max = 20)
```

**Soften:** каждой стороне, чьё мнение о другой **отрицательно**, `add_opinion(+Δ, 50 Mediated)`; `mediation_ready = today + 180`; `mark_feud_dirty`. Цена: `mediation_cost_kop × эффективный_уровень` (3 000 коп × уровень) **или** `mediation_soften_influence × уровень` (3,0 очка × уровень) по полю `pay`.

**Reconcile** (оба направленных уровня ≤ `Rivalry`): каждой стороне с мнением < −10 `add_opinion(−10 − мнение, 51 Reconciled)`; `truce_until = today + truce_months`, `peak = 0`, `Reconciled`; `AdjustUnity(+2, 11)`; заметка летописи 111; `mediation_ready = today + 365`. Цена: `reconcile_cost_kop × уровень` (8 000 коп × уровень) **или** 6,0 очка × уровень по полю `pay`.

Если мощность мала (Δ = 3), эффект всё равно применяется: игрок видит его в предпросмотре заранее, **случайности нет**.

### 7.3 «Свежесть»

`since` обновляется, когда эффективный уровень вырос. Посредничество сразу после ссоры слабее — этим дизайн заставляет подождать, а не «закрывать» ссору деньгами в тот же день.

### 7.4 `GiftToMember{recipient, pay, amount}`

Актор — род (глава). Получатель — живой взрослый член рода (не сам глава). При `pay = Money`: `amount` — копейки, `amount ≥ gift_min_kop` (1 000), деньги — расход 106; при `pay = Influence` («покровительство», [influence-model.md](influence-model.md) §6): `amount` — сотые очка, `amount ≥ 100`, деньги не списываются, эффект на мнение тот же из расчёта 1,0 очка ≈ 1 000 коп (`+2` за 1,0 очка, ≤ +10). Эффект: `recipient → acting_head`: `+min(2 × amount/1000, 10)` (причина 52, потолок вклада +30); если у получателя есть направленный уровень ≥ `Cooling` к кому-то в роду — самому враждебному (мнение ниже всех, ничья — меньший id) ещё `+½` от этой дельты (утешение). Причина 44 `Favouritism` может сработать на **других** равных получателю (§4.2).

### 7.5 Брак как примирение ([#530](https://github.com/savinovanton/patriarch/issues/530))

E8 `Wed` (хук E7-T29): если женится член M с направленным уровнем ≥ `Cooling` к главе или родственнику, и ранг супруга выше ранга M ≥ 1 (E8 §8.8, «свадьба вверх») — `M → глава +10` и `M → сильнейший враг +5` (причина 53, потолок вклада +15). Для вражды между **родами** действует существующее +10 `MarriedInto` (E8); бракам внутри рода мешает степень родства.

### 7.6 ИИ-глава ([#532](https://github.com/savinovanton/patriarch/issues/532))

Рекомендация A: для ИИ-рода (не из `player_dynasties`) система в слот рода выбирает пару с эффективным уровнем `Feud` (по `(уровень ↓, мнение ↑, lo ↑, hi ↑)`) и, если хватает денег и нет кулдауна, выпускает `MediateFeud{Soften}` (актор — род); не чаще одного на слот. При уровне `Rivalry` ИИ молчит.

## 8. Системы и порядок

### 8.1 Системы E7-T25

Ставятся отдельной функцией `install_relations_systems(simulation, content)` **после** систем E7 (`dynasty.*`), E8 (`marriage.*`, `succession.*`), E10 (`court.*`) и **до** `economy.*`; `events.resolve` и `events.dispatch` остаются последними (E11 §12.3). Без собственного состояния, эффекты — внутренние команды (применяются в начале следующего тика) и прямые `World::add_opinion`, как у `dynasty.opinions` и `dynasty.standing`.

| № | Имя | `Cadence` | Что делает |
|---:|---|---|---|
| 1 | `dynasty.relations` | Daily | проход A (§5.2) и проход B для слота держателей (§5.1); ИИ-посредничество по слоту рода (§7.6) |
| 2 | `dynasty.relations.unity` | Monthly | давление вражды на единство родов (§6.2) |

Порядок «мнения затухли → единство дрейфует → E8/E10 сегодня записали причины → вражда пересчитана → экономика» нужен, чтобы пересчёт видел сегодняшние причины и не зависел от порядка внутри E8/E10.

### 8.2 Задержка эффекта

`SetFeudLevel` применяется на следующей границе тика: событие E11 о смене уровня придёт на следующий день после пересчёта. `MediateFeud`/`GiftToMember` применяются сразу, а новые уровни — проходом A на следующий день; игроку прогноз показывает `MediationPreview`.

## 9. Случайность и детерминизм

- **Ни одного потока ГСЧ** (D4); тест «`world.rng()` не создаёт потоков при работе систем» (как проверки E8-системы).
- Порядок: держатели по возрастанию id; цели по возрастанию id; строки по `(lo, hi)`; кандидаты ИИ — по ключу с `id` на ничьей; нет `unordered_*`, `float`, адресов в ключах.
- Вся арифметика — `Fixed32`/целые; деления `/ 20`, `/ 2`, `×0,5` — целочисленные с фиксированным округлением к нулю (`Fixed32::raw`), оно записано в тестах.
- Команды выпускаются **не более одной на пару в день**, в порядке `(lo, hi)`; `apply` предполагает пройденную `validate` против того же состояния и ничего не решает.
- Реплей: `MediateFeud` и `GiftToMember` — внешний ввод, пишутся в `PRP1`; `SetFeudLevel` повторно порождается системой.

## 15. Производительность (5 000 живых + ~20 000 архивных)

Архив в проходах не участвует (`die` чистит строки таблицы). Бюджет `[предл.]` — не более **0,1 мс/день** на `dynasty.relations` и ≤ 0,5 мс в месяц на `dynasty.relations.unity`:

| Операция | Оценка | Основание |
|---|---|---|
| Проход B: слот держателей | ≈ 180 держателей × ≤ 30 записей ≈ 5 400 проверок/день ≈ 30…60 мкс | 5 000/28; одна проверка — сравнение `Fixed32` |
| Давление черт | ≈ 180 × ≤ 39 членов рода ≈ 7 000 проверок/день, но только при наличии пар из таблицы | отсечка по `traits` через маску допустимых черт |
| Проход A | единицы строк в день | `Dirty`, перемирия, кулдауны |
| Единство, месяц | один проход по ≤ 4 096 строкам ≈ 50…100 мкс | `dynasty.relations.unity` |
| Память | строка 24 Б × ≤ 4 096 = 96 КБ | §3.4 |
| Сейв | раздел 8 ≤ 100 КБ, часть хеша 38 — один проход | |
| Стресс-профиль | `stressgen` добавляет граф мнений с долей враждебных пар 5 % и пары `Feud`/перемирия | E7-T37 |

Работа считается в `WorkBudget` (`context.budget.spend`): число проверок.

## 16. Сейв, схема, миграция, golden

- **Схема** `kStateSchema` поднимается на единицу «на момент слияния» (ADR-0006, [save-format.md](save-format.md) §7.4), задача E7-T26 (W-очередь, §19). Шаг «N → N+1» пуст: таблица пуста.
- **Раздел 8** `feud_pairs`, версия 1, `min_schema` = выданная схема: `u32 rows | rows × {u32 lo, u32 hi, u8 level_lo_hi, u8 level_hi_lo, u8 peak, u8 flags, i32 since, i32 truce_until, i32 mediation_ready}` (24 Б). Пустой раздел не пишется. Ридер: `plausible(rows, 24)`, `lo < hi`, строго по возрастанию, уровни ≤ 3, `peak` ≤ 3, обе стороны — члены **одного** рода и живы, строка не «пустая» (§3.2), иначе ошибка загрузки (не падение).
- **Раздел 9** `feud_meta` — резерв (если понадобятся счётчики); 10…15 — резерв E7.
- **Часть хеша** `ExtPart` **38** `Feud` (хеш строк; пусто = 0 и вне `total`, ADR-0006 D7); 39 — резерв. Блок 38…39 — по правилу ADR-0011 §5.2 п. 3 («следующий свободный блок»); блок выдан этой спецификацией (строки в [save-format.md](save-format.md) §5 и ADR-0006 D6); E7-T26 меняет статус на «в коде» и записывает часть 38 в ADR-0006 D7 и `ExtPart`.
- **Теги** 22…24 — таблица [save-format.md](save-format.md) §6 и `TagTable` (`static_assert` уникальности).
- **Политика golden:** таблица пуста во всех существующих сценариях, поэтому `demo.v1`, `dynasty.v1`, `PRP1` и `kExpectedSaveBytesHash` не меняются (D15). **Закреплённые хеши `simcli_m1` меняются** ровно в двух задачах: E7-T27 (новый файл данных попадает в хеш контента) и E7-T37 (подключение систем) — обе помечены «G» и идут по одной ([README эпиков](../epics/README.md)). F1 (свёртка по модулю) меняет хеш мнений только в мирах с ≥ 4 причинами в одной записи.
- **Фикстуры:** `tests/data/saves/dynasty_v<N-1>.psv` (создаётся на `main` до правок), round-trip с непустой таблицей и перемирием, корпус порчи (усечения, раздутые счётчики, неупорядоченные и «пустые» строки).

### 18.2 Приёмочные сценарии (E7-T37)

- **REL-A1.** *Дано:* два взрослых `proud` брата, один — наследник. *Тогда:* через 10 месяцев пара `Rivalry`, `HeirRivalry` и `TraitClash` видны в разложении, единство падает.
- **REL-A2.** *Дано:* глава назначил наследником младшего сына. *Тогда:* старший: `HeirPassedOver −12`, E8 `201 −15` к главе; причины в тултипе.
- **REL-A3.** *Дано:* пара `Feud`. *Тогда:* `SendMarriageEnvoy` для члена, враждующего с главой, отклонён `FeudRefusal`; `AssignOffice` — тоже.
- **REL-A4.** *Дано:* пара `Feud`, деньги есть. *Когда:* `MediateFeud{Soften}` дважды с интервалом 180 дней, затем `Reconcile`. *Тогда:* уровни спускаются, перемирие 24 мес, единство +2; `Reconcile` при `Feud` отклонён `FeudTooDeep`.
- **REL-A5.** *Дано:* перемирие. *Когда:* разовая причина −40. *Тогда:* перемирие сброшено `TruceBroken`, уровень вернулся.
- **REL-A6.** Детерминизм: два прогона с одним seed → один хеш; сейв посреди перемирия и кулдауна → тот же хеш, что без перезагрузки; потоков ГСЧ не создано.
- **REL-A7.** Производительность: 5 000 живых + 20 000 архивных, профиль `year60`, `dynasty.relations` p95 ≤ 0,1 мс.
- **REL-A8.** 20 лет без игрока на ≥ 10 seed: нет вражды без записанных причин; доля пар `Feud` в роду ≤ порога калибровки.

Модельные тесты (E7-T05-стиль): случайные последовательности `AdjustOpinion`/`MediateFeud`/`GiftToMember`/`Die`; после каждого шага `check_invariants()`; сравнение с наивным пересчётом уровней.
