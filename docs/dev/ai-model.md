## 1. Что здесь решено и что нет

Документ фиксирует **форму состояния, интерфейсы и контракты**, а не баланс:

1. какие таблицы добавляет E17 в `World`, их колонки, кто пишет и кто читает (§4);
2. интерфейс агента, режимы рода, функция видимости `AiView`, `CommandSink` и резервирования (§5);
3. время: системы и их место в тике, бюджет WU, очки внимания, тиры и повышение тира, случайность; поправка GDD 07 §8.8 (§6);
4. команды: теги 192…199, поля, кто выпускает, коды отказа и причин (§7);
5. утилити: 7 целей, 8 архетипов, 3 уровня сложности, гистерезис, обязательства, кулдауны — с числовыми примерами для AI-A1…A8 (§8) и их `Breakdown` (§10);
6. контракты планировщиков по доменам E8, E10, E12, E9, E16, E11, E31, E15; что домены обязаны выставить как чистые функции и как гейтятся их временные ИИ; ИИ → игрок (§9);
7. объяснимость (§11), каталог E11 (§12), данные (§13), инварианты (§14), сейв, хеш, миграция, golden (§15);
8. AI-only харнес, метрики и допуски для 3–4 родов (§16), бюджеты (§17), мост и dev-окно (§18), граница M1/M2 (§19), соответствие историям (§20), решения владельца (§21), правки других документов (§22), поправки к задачам T02…T19 и оценка (§23).

## 3. Типы и единицы

| Величина | Тип | Единица / диапазон |
|---|---|---|
| Полезность, нужда, возможность | `i32` | «очки полезности»; `need`, `opportunity` — 0…1000 (‰); итог −10 000…10 000 |
| Веса, множители, доли | `i32` | промилле (`_pm`, 1000 = ×1,0) |
| Очки внимания (AP) | `u16` | целые очки; кап 2 × пополнение ≤ 40 |
| Единицы работы (WU) | `u32` | абстрактные; калибровка 1 WU ≈ 0,1…0,2 мкс (T05) |
| Деньги | `int64` (`economy::Kopecks`) | копейки |
| Даты | `Date` (`kNoDate` = нет) | дни |
| Ключ объекта | `u64` | `kind << 56 | id` (вид объекта: персона, вакансия, провинция, армия, заговор, род, событие) |
| Идентификаторы (`seq` журнала) | `u32`, растут, не переиспользуются | `0` недопустим |
| Перечисления в сейве | `u8` / `u16` | числа навсегда, значения только добавляются |

Весь расчёт — целые; `float`/`double`, `unordered_*`, `rand` запрещены. Обход — по возрастанию id или явному ключу; ничьи — по `(значение ↓, ключ ↑)`.

### 5.1 Интерфейс агента и планировщика

```cpp
// pat/sim/ai/agent.hpp (набросок; T04)
struct PassContext {
    const AiView& view;          // единственный вход в мир (const World& внутри, видимость §5.3)
    const AiRules& rules;
    WorkBudget& wu;              // квота ИИ (D6)
    CommandSink& out;            // validate + резервирования (§5.4)
    DecisionLogWriter& log;      // до 8 записей за проход, применяются командой 193
    std::uint64_t pass_seed;     // §6.5
};

class Agent {
public:
    virtual ~Agent() = default;
    [[nodiscard]] virtual AgentKind kind() const = 0;
    virtual void perceive(PassContext& ctx, Knowledge& k) = 0;                // своё и видимое
    virtual void deliberate(PassContext& ctx, const Knowledge& k, GoalSet& goals) = 0;  // §8
    virtual StepResult act(PassContext& ctx, const GoalSet& goals, PlanFrame& frame) = 0; // §9
    virtual void explain(PassContext& ctx, const PlanFrame& frame) const = 0;  // §11
};

class Planner {   // E15, E31, E14 подключают свои реализации тем же интерфейсом
public:
    virtual ~Planner() = default;
    [[nodiscard]] virtual PlannerId id() const = 0;
    [[nodiscard]] virtual std::span<const GoalKind> goals() const = 0;    // какие цели обслуживает
    [[nodiscard]] virtual StepResult step(PassContext& ctx, GoalKind goal, PlanFrame& frame) = 0; // возобновляемый
};
```

`StepResult` — `Done{candidate?}`, `NeedMoreBudget` (рамка сохраняется), `Nothing`. Планировщик обязан останавливаться только **между кандидатами** (проверка `wu.try_spend(цена кандидата)` перед оценкой) и хранить положение в `PlanFrame.cursor` (ключ), чтобы продолжение не зависело от числа тиков. `DynastyAgent` — единственная реализация `Agent` в M1; планировщики регистрируются в `PlannerRegistry` при `install_ai_systems` (E15/E31 добавляют свои без правок кода E17, кроме строки регистрации).

### 5.4 `CommandSink`, резервирования и гонки

1. Агенты обрабатываются **последовательно** в порядке §6.1; общий снапшот — состояние мира на начало тика (команды тика применятся на следующей границе).
2. Каждая команда перед эмиссией проходит **тот же** `validate`, что команда игрока (общий код домена), и проверку резервирований: `Person` (сватовство, помолвка, кандидат челобитной, приглашение в заговор), `Vacancy`, `Province` (стройка, управитель, налоговая политика), `Army` (приказ), `Plot` (вступление). Ресурс, уже зарезервированный агентом раньше в этом тике, — кандидат пропускается (`Skipped{Reserved}`), это не ошибка.
3. Отказ `validate` на эмиссии — **баг** (`emit_rejected += 1`, запись `Rejected`, `PAT_ASSERT` в debug); приёмка AI-A5 требует 0.
4. Команда, прошедшая эмиссию, но отклонённая при применении (игрок или система изменили мир между тиками), — «гонка»: на следующем тике `ai.schedule` находит её в `ctx.applied_commands` (актор — управляемый род, тег из множества команд ИИ) и выпускает `AgentCommandRejected` (194): запись журнала, `race_rejected += 1`, кулдаун `(цель, объект)` на `race_cooldown_days = 7`.
5. Команды ИИ получают актор = род агента; системные команды E17 (193…195, 197) — актор «система».

## 6. Время: системы, бюджет, внимание, тиры, случайность

### 6.1 Системы и место в тике

`install_ai_systems(sim, rules)` вызывается **последней** при сборке сценария: системы ИИ идут после всех систем доменов дня (E8, E9, E10, E11 `events.dispatch`, E12, E15, E16, E31 — их спецификации уже требуют «до систем ИИ E17»), чтобы агент видел состояние после сегодняшних ответов, свадеб, назначений и событий. Команды ИИ применяются на следующей границе тика вместе с командами игрока.

| # | Система | Частота | Что делает |
|---|---|---|---|
| 1 | `ai.schedule` | Daily | отклонённые команды ИИ из `applied_commands` → 194; события значимости (смерть/смена главы, фаза ≥ 2, раскрытие заговора, новая претензия, предложение/донос с участием игрока) → 195 `SetAgentTier`; истёкшие `tier_until` → 195 (возврат); смена главы → 192 `ConfigureAgent{archetype}` при `archetype_follows_head = yes`; строит порядок дня |
| 2 | `ai.run` | Daily | своя квота: `quota_wu + wu_carry`; агенты с `due ≤ today` или рамкой — в порядке `(рамка ↓, тир ↑, due ↑, dynasty ↑)`; проход §6.2; на каждого — одна команда 193 `AgentDeliberated` |

Месячной системы нет: AP начисляются «лениво» при проходе (§6.3). Выбор вариантов событий идёт внутри `events.dispatch` E11 через подменённый `EventChooser` (§9.7), а не в `ai.run`.

### 6.2 Бюджет WU, проход и рамки

**Проход агента:** `perceive` (своё + видимое, ≤ 2 цели) → `deliberate` (7 целей, гистерезис, обязательство) → `act` (для 1–2 целей: планировщики по `PlannerRegistry`, лучший кандидат, эмиссия) → `explain` (записи журнала) → команда 193.

**Стоимости** (`ai.pd: budget.costs`, `[предл.]`):

| Операция | WU |
|---|---:|
| Основа прохода (`perceive`, своё) | 50 |
| Оценка одной цели | 20 |
| Дешёвый фильтр сущностей (персоны, `living()`) | 1 на 8 строк |
| Просмотр вакансии / провинции / армии / заговора | 2 |
| Оценка кандидата брака (`score_match` + `accept_score`) | 30 |
| Оценка кандидата должности (`U`) | 20 |
| Оценка участия в заговоре (`invite_accept`, `claim_strength`) | 20 |
| Оценка стройки / налоговой политики / займа | 15 / 10 / 10 |
| `estimate_battle` | 25 |
| Эмиссия (`validate` + резервирование) | 10 |
| Запись журнала | 2 |

**Квота и перенос:** на тик доступно `Q = quota_wu + wu_carry`, где `quota_wu = 12 000` `[предл.]`, `wu_carry' = min(Q − used, quota_wu · carry_pm/1000)`, `carry_pm = 500`. Пик — ≤ 18 000 WU ≈ 1,8…3 мс при калибровке 0,1…0,17 мкс/WU (≤ 3 мс по GDD 07 §12; калибруется T05 и T19).

**Рамки:** перед оценкой кандидата планировщик вызывает `wu.try_spend(цена)`; при отказе — `NeedMoreBudget`: `ai.run` выпускает `AgentDeliberated{Partial}` с рамкой и останавливает обход агентов этого тика (следующие агенты ждут); на следующем тике агент с рамкой идёт первым, `perceive` и `deliberate` повторяются (их цена списывается снова), выбранные цели берутся **из рамки**, перебор продолжается после `cursor`; лучший кандидат рамки перепроверяется `validate` при эмиссии. Рамка старше 7 дней сбрасывается (новый проход, новый бросок).

**Пример (AI-A2, US-17.2).** Проход Честолюбца (§8.4) стоит: основа 50 + 7 целей 140 + `gain_office` (6 вакансий × 2 + 15 членов / 8 → 1 + 30 пар × 20 = 613) + эмиссия 20 + `prepare_plot` (2 заговора × 2 + 3 оценки × 20 + 10 = 74) + журнал 6 ≈ **903 WU**; со сватовством (`living()` 5 000 / 8 = 625 + 50 кандидатов × 30 = 1 500 + 10) ≈ **3 038 WU**. При квоте 12 000 и четырёх таких агентах в один день четвёртый получает 12 000 − 3 × 3 038 = 2 886 WU, прерывается на кандидате брака и завершает проход на следующий день первым; с переносом вчерашнего остатка (до 6 000) — укладывается целиком. При квоте 2 000 проход растягивается на 2 тика; в замороженном мире выбор тот же (F3).

### 6.3 Очки внимания (AP)

```
refill = clamp( ap_base(6) + court_size/4 + (diplomacy + stewardship главы)/8 , 6, 20 ) · ap_mult(difficulty)/1000
cap    = 2 · refill
ap_now = min(cap, ap + refill · (месяцев с ap_month))      — при проходе; команда 193 пишет ap и ap_month
```

`court_size` — члены рода + слуги (E10). Проход тратит не больше `max(3, ap_now/2)` AP (не «всё сразу»). Стоимость команд (`ai.pd: attention.costs`, `[предл.]`): `SendMarriageEnvoy` 3, `Betroth` 2, `SetHeir` 2, `SetEducation` 1, `PetitionForOffice` 3, `GiftToEmperor` 2, `HireServant`/`FireServant` 1, `AssignOffice` (внутренние должности рода) 1, `StartPlot` 5, `JoinPlot` 3, `ContributeToPlot` 2, `LeavePlot` 1, `Denounce` 3, `PressClaim`/`SupportClaim` 3, `SetTaxPolicy`/`SetRecruitPolicy` 2, `StartConstruction` 3, `TakeLoan` 2, `RepayLoan` 1, `AssignProvinceAdministrator` 1, `OrderMove`/`OrderSiege` 1, `AssignToFront` 2, `RaiseArmy` 3, `SetFaithStance` 6, `DonateToChurch` 2, команды E15 — данные E15; ответы на события и на предложения — 0.

**Пример.** Двор 12, дипломатия 8, хозяйство 10: `6 + 3 + 18/8 (= 2) = 11` AP в месяц, кап 22; дружелюбные — `11·800/1000 = 8`, беспощадные — `11·1200/1000 = 13`. Неделя 1: AP 11, лимит прохода 5 — `PetitionForOffice` 3 + `GiftToEmperor` 2 → 6; неделя 2: лимит 3 — `JoinPlot` 3 → 3; неделя 3: лимит 3 — `SetEducation` 1 → 2; неделя 4 — ничего; новый месяц: `min(22, 2 + 11) = 13`.

### 6.4 Тиры, значимость, LOD

```
S = 40·(претензия или кандидат заговора) + 30·(фаза ≥ 2 и позиция Plotter) + 20·(связь с игроком за 365 дней: брак, переговоры, донос, договор)
  + 5·ранг чести + 25·(смерть главы за 30 дней)                                                            — Breakdown 19400
tier = 1 при S ≥ 40 или в первой десятке по S; 2 при S ≥ 15 или в первых 30; иначе 3        (force_tier сценария перекрывает)
```

Периодичность тира 1/2/3 — 7/30/90 дней; начальный `due = start + (dynasty % период)`. Глубина: тир 1 — 2 цели за проход, все планировщики; тир 2 — 1 цель, лимит кандидатов ×½; тир 3 — 1 цель, только `secure_line` и `protect_self` (содержательный «фоновый дрейф» — M2). Повышение: событие из §6.1 → `SetAgentTier{tier = 1, until = today + 90, reason}` и `due = today + 1`; возврат — по `tier_until`.

**Пример (AI-A3, US-17.3; стресс-профиль).** Род ранга 2 без претензий: `S = 10` → тир 3, `due` через 70 дней. 1705-03-10 умирает глава; E8 сажает нового главу 14 лет. `ai.schedule` 1705-03-11 видит `Die` главы → `SetAgentTier{1, until 1705-06-09, HeadDied}`, `due = 1705-03-12`; проход: `secure_line` `need = 1000` (у нового главы нет наследника) → `SetHeir`/сватовство за ≤ 7 дней; 1705-06-09 тир возвращается к 3.

### 6.5 Случайность

- Поток `ai.agent`, индекс `DynastyId`: **один** `next_u64()` на новый проход (`pass_seed`, пишется в рамку). Продолжение рамки поток не тянет; число извлечений не зависит от ветки, числа кандидатов и разбиения по тикам.
- Шум: `n(ключ) = hash64(pass_seed, ключ) mod (2·noise_pm + 1) − noise_pm`, применяется как `x·(1000 + n)/1000`; ключ цели — `goal`, кандидата — `object ^ (tag << 48)`.
- `events.ai` — прежний один бросок на решение E11 (D12); E17 меняет только веса.
- Оценки без шума (кандидаты доменов, AP, тир) — без ГСЧ.

### 8.4 Формула, гистерезис, обязательства — с примером (AI-A7)

```
base_g    = need·opportunity/1000
u_g       = base_g · weight[archetype][g]/1000 · difficulty_mult(g)/1000 · (1000 + bias_pm)/1000   — 19000
net_g     = u_g − cost_g,  cost_g = AP·ap_price(10) + потеря_коп/money_price(1 000 коп)                 (вложения — стройка, заём — не потеря: их отдача уже в opportunity)
noisy_g   = net_g · (1000 + n(g))/1000
held      = текущая цель: noisy · hold_pm(1150)/1000, пока held_since + 14 дней > today — не сменяется
выбор     = до 2 целей с max noisy (тир 1), ничьи — по GoalKind; net ≤ min_utility(50) → Declined
```

**Пример.** Род без держаний; лучшая вакансия `U = 40`; свободный взрослый член 1, наследник взрослый, лучший жених `best_match = 70`; казна 18 000 руб при расходе 5 000 в месяц, лучшая стройка окупается за 30 мес.; милость 55; подозрение 10; позиция Opportunist, фаза 1, кандидат с `claim_strength ≥ 35` есть; max `unrest` 25, повстанцев нет. Тогда `base`: офис `800·400/1000 = 320`, линия `250·700/1000 = 175`, богатство `400·400/1000 = 160`, милость `150·1000/1000 = 150`, защита `150`, заговор `300·600/1000 = 180`, порядок `250`. Цена: офис 80 (3 + 2 AP = 50, подарок 300 руб = 30), линия 35 (3 AP + посредник 50 руб), богатство 30, милость 50, защита 50, заговор 30, порядок 50 (налоговое послабление).

| | офис | линия | богатство | милость | защита | заговор | порядок | Выбор |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| Честолюбец, `net` | 448 − 80 = **368** | 140 | 114 | 115 | 70 | 216 − 30 = **186** | 150 | `gain_office`, `prepare_plot` |
| Хозяйственник, `net` | 224 − 80 = 144 | 140 | 224 − 30 = **194** | 70 | 130 | 42 | 275 − 50 = **225** | `keep_order`, `grow_wealth` |

Шум (реалистичные, `n(gain_office) = −63`): `368·937/1000 = 344` — выбор не меняется. **Гистерезис:** если неделю назад Честолюбец держал `prepare_plot` (`186 → 186·1150/1000 = 213`), то `gain_office` 344 > 213 — смена; при `gain_office = 200` смены нет (US-17.7: «цель не мигает»).

**Обязательство:** выпуск команды с многошаговым продолжением (сватовство → помолвка, `StartPlot` → взносы, челобитная → решение) ставит `commit_goal/object`; цель удерживается, пока объект допустим и `net ≥ commit_utility · 500/1000`, но не дольше 365 дней; нарушение — запись `GoalChanged{CommitDropped}`.

**Кулдауны** (`[предл.]`, × `forgiveness`): отказ в браке — `(secure_line, кандидат)` 180 дней; проигранная челобитная — `(gain_office, вакансия)` до закрытия вакансии; отказ в заговоре — `(prepare_plot, род)` 120 дней; гонка — 7 дней.

### 8.5 Оценка кандидата (19100)

```
score = domain_norm(0…1000) · net_goal/1000 · risk_mult/1000 · player_mult/1000 − AP·ap_price − потеря/money_price ;  ± шум n(кандидат)
```

`domain_norm` — нормированная оценка домена (`10·U` для вакансии; `1000·match/match_norm` для брака; `invite_accept` сдвинутый к 0…1000; `p_att` ‰ для подавления; `12 000/окупаемость` для стройки). `player_mult = player_bias` для планов против рода игрока (донос, поддержка соперника) и для предложений игроку (брак, §9.3). Лучший — `max(score)`, ничья — по ключу; `score ≤ 0` — ничего не выпускать (`Declined`).

## 9. Планировщики и контракты с доменами

### 9.1 Общие правила

- Планировщик — тонкая обёртка: перечисляет кандидатов через `AiView`, оценивает **функцией домена**, применяет `score` §8.5, выпускает **обычную** команду домена. Формулы доменов в `src/sim/ai` не появляются (ревью по [code-duplication-audit.md](code-duplication-audit.md)).
- Функция, вызываемая «с чужой стороны» (ответ другого рода: `accept_score`, `invite_accept`), читает только видимые входы §5.3; домен документирует её входы; скрытые — через `AiView::public_projection` (полоса) (F10).
- Временный ИИ домена (`marriage.matchmaker`, `court.ai`, действия `crisis.ai_stance`, `army.ai` для родов, `religion.ai_stance`) получает одну строку `if (is_ai_managed(world, house)) continue;` — её добавляет задача планировщика E17 (или задача домена, если она сливается позже; кто последний — тот и добавляет).
- Пока соседняя задача не слита, планировщик работает на заглушке с той же сигнатурой (контракт ниже); тест планировщика пишется против реальной функции после слияния.

### 16.4 «Без скрытых бонусов» (#670 B, T19)

1. Поля `AiRules::difficulty` читаются только в `src/sim/ai` (grep-тест).
2. Два мира, отличающиеся только `SetAiOptions{difficulty}`: после команды различается лишь байт `AiMeta.difficulty`; хеши правил доменов и `AiView` одинаковы.
