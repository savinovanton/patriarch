# E2 — Бенчмарки и стресс-генератор

> Веха: **M0**. Размер: **M–L (~20 рабочих дней)**. Статус: **E2-T01–T07 выполнены; остальные задачи впереди**.
> Опирается на: ADR-0002 (бюджеты, риск-спайки), TZ NFR-PERF-1…7.
> Оценки: **S** ≤ 1 дн., **M** 2–3 дн., **L** ~1 нед., **XL** > 1 нед.

## 1. Цель

Получить **измеренные** ответы на главные вопросы производительности до того, как они будут зашиты в игровой код, и превратить бюджеты из ADR-0002 в **автоматический гейт** CI. Эпик отвечает на три вопроса:

1. Укладывается ли дневной/месячный тик на **400 провинциях + 5 000 персонажах** в бюджеты (8 мс / 120 мс)?
2. Насколько индекс триггеров быстрее «наивной» проверки на 500 событиях?
3. Какой способ передачи снапшотов UI дешевле (копия / persistent / двойной буфер с диффами)?

## 2. Объём

**Входит:** Google Benchmark, генератор синтетических миров («год 60», ×3), «макеты» будущих систем для замера, телеметрия подсистем, CI-гейт на регрессии, учёт памяти, итоговый отчёт с обновлением ADR-0002.
**Не входит:** реальные игровые системы, рендер (E3).

## 3. Бюджеты (из ADR-0002, уточняются по результатам)

| Метрика | Цель |
|---|---|
| Дневной тик (p95) | ≤ 8 мс |
| Недельный | ≤ 30 мс |
| Месячный (пик) | ≤ 120 мс |
| Годовой | ≤ 400 мс |
| Память к концу партии | ≤ 1.5 ГБ |
| Деградация «год 1 → год 60» | ≤ 2× |
| ИИ на тик (в WU) | среднее ≤ 1 мс, пик ≤ 3 мс |

Измерения — на **двух профилях**: (а) машина разработки (i5-12400F), (б) «слабый профиль» (4 ядра, ограничение через аффинити/частоту; при возможности — реальная слабая машина).

## 4. Пользовательские истории и критерии приёмки

**US-2.1.** *Как разработчик, я хочу знать стоимость тика на «позднем» мире.*
- *Дано:* мир из генератора (400 провинций, 5 000 персонажей, 100 родов, 300 армий, 100 схем, 400 договоров, нагрузка ×3). *Когда:* прогон 10 игровых лет в `simcli`. *Тогда:* отчёт содержит p50/p95/p99 по дневным, недельным, месячным, годовым тикам и по подсистемам.

**US-2.2.** *Как разработчик, я хочу, чтобы регрессии блокировались автоматически.*
- *Дано:* базовые результаты бенчмарков в репозитории. *Когда:* PR замедляет ключевой путь более чем на 10%. *Тогда:* CI-проверка падает с указанием бенчмарка и величины регрессии.

**US-2.3.** *Как разработчик, я хочу выбрать способ публикации снапшотов по данным.*
- *Дано:* три реализации (копия по диффам, persistent, двойной буфер). *Когда:* замер при 60 Гц чтения. *Тогда:* отчёт сравнивает время тика, задержку снапшота, память; принято решение, записанное в ADR.

## 6. Тесты и проверки

- Валидность генератора: инварианты мира (родство симметрично, ссылки существуют, лимиты соблюдены).
- Стабильность бенчмарков: относительное стандартное отклонение ≤ 5%; нестабильные помечаются и не участвуют в гейте.
- Корректность «макетов»: отсутствие побочных зависимостей от порядка; хеш состояния после прогона воспроизводим.
- Регрессионный гейт проверен «отравленным» PR (искусственное замедление в 20%).

## 7. Риски и вопросы

| Риск | Митигация |
|---|---|
| Результаты на 12400F обманчиво хороши | Слабый профиль (T08) и поиск реального слабого ПК; бюджеты с запасом 2× |
| «Макеты» не отражают реальные системы | Макеты используют ту же раскладку данных и размеры; пересмотр после M1 (повторный замер) |
| Шум на CI-раннерах | Сравнение медиан с повторами; мягкий порог на раннерах, строгий — на выделенной машине (локальный раннер, если понадобится) |
| Публичный репозиторий и раннеры GitHub: время/ресурсы ограничены | Публичные репозитории получают бесплатные минуты; бенчмарки гонять nightly, а не на каждый PR |

**Открытые вопросы:**
1. Есть ли под рукой «слабая» машина (4 ядра, 8 ГБ, встроенная графика) для реальных замеров? Если нет — принимаем эмуляцию ограничением ядер и частоты.
2. Нужен ли выделенный self-hosted раннер для бенчмарков (стабильное железо) или хватит nightly на GitHub-раннерах плюс локальные замеры?
