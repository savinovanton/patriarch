# E7 — Персонажи и династия

> Веха: **M1**. Размер: **L по дорожной карте, по факту ≈ 64 дня FTE при последовательной работе (≈ 35–40 календарных за счёт параллельных веток)** — оценка требует уточнения после T02. Статус: **разложен на задачи 2026-11-07** (задачи — в GitHub Issues, метка `epic:E7`, эпик — #40).
> Опирается на: GDD 01 (спека эпика: §2–5, §8, §10, §12–14), ТЗ FR-DYN-1…3, FR-DYN-6, FR-DYN-7, NFR-PERF-2/5, NFR-DET-1, NFR-TEST-1, FR-SAVE-1, ADR-0001 (команды, снапшоты), ADR-0002 (P1 лимиты и LOD, P2 тик по частотам, P4 SoA, P5 события), `docs/dev/code-style.md` §4 (правила детерминизма).
> Оценки: **S** ≤ 1 дн., **M** 2–3 дн., **L** ~1 нед.

## 1. Цель

Превратить заготовки E1 (`CharacterTable` из пяти колонок, три демо-системы) в **настоящую модель людей и рода**: персонаж уровня A с навыками, чертами, здоровьем, родством и образованием; архив умерших (уровень C) без активной симуляции; жизненный цикл по таблицам GDD 01 (старение, смертность, зачатие, беременность, роды, образование, совершеннолетие); честь и единство рода; глава рода и вымирание; летопись; а также первые окна (древо рода, окно персонажа, совет рода, летопись) поверх снапшота. Всё детерминировано, хранится в `World`, меняется только командами, укладывается в бюджет **5 000 живых персонажей** (NFR-PERF-5) и сохраняется/загружается вместе с миграцией схемы.

Эпик даёт **механизм и первую настройку баланса**; сами правила браков и законы наследования — E8, должности — E10, поведение членов рода — E17, события — E11/E22.

## 2. Объём

**Входит:**
- модель персонажа уровня A (поля GDD 01 §2.1: идентичность, родство, 5 навыков, здоровье/плодовитость/стресс/благочестие, черты, честолюбие и лояльности, образование), архив уровня C (FR-DYN-7), портрет по id из пула, имя и отчество;
- расширение рода: единство, закон наследования (поле + значение по умолчанию), ветви (хранение), честь с рангами, глава рода и **вымирание рода** как состояние, **летопись**;
- жизненный цикл по расписанию ADR-0002 P2: ежегодная смертность и старение, помесячные здоровье/стресс/зачатие, роды по таймеру, образование и совершеннолетие;
- черты и навыки из `.pd` (≈ 25 черт, 5 навыков), разложение навыков на слагаемые для тултипов (FR-UI-3);
- разреженные мнения (≤ 30 на персонажа) и их затухание — как хранилище и API;
- «запасное» правило преемника при смерти главы и правило вымирания (по GDD 01 §2.2 / §6, «порядок при отсутствии наследника»);
- таблицы смертности/плодовитости/возрастов как **данные** (`.pd`) с запасными значениями в коде;
- мост «снапшот → UI» и окна: древо рода, окно персонажа (полное), совет рода (состав, честь, единство), летопись;
- сценарий `dynasty.v1` для `simcli` с демографическим тестом на 100 лет, калибровка по GDD 01 §13.1, бюджеты производительности и стресс-профиль.

**Не входит (и кому отдаётся):**

| Что | Кому |
|---|---|

## 3. Решения и допущения эпика

Решения помечены **(предл.)** — это предложение агента; архитектурные подтверждаются в T01 (ADR). Вопросы владельцу — ❓ (не решать молча, см. последний раздел).

| # | Вопрос | Решение (статус) |
|---|---|---|
| 1 | Идентичность людей | `CharacterId` должен оставаться верным ссылкой на человека **всю партию** (на умерших ссылаются родство, летопись, должности, схемы E10/E14). **(предл.)** Идентификаторы персонажей не переиспользуются: умерший остаётся в таблице как «архивная» строка, разреженные данные (мнения, претензии, беременность) освобождаются. Точная раскладка решена в [ADR-0006](../adr/0006-character-storage.md) §D1–D3: одна таблица, id не переиспользуются в «режиме династии», умершие остаются строками (группа S сбрасывается), живые — отдельный список по возрастанию id (≈ 149 Б/id, ≈ 5.2 МБ на 5 000 + 20 000) ✅ |
| 2 | Совместимость с замороженным демо E1 | Демо-сценарий (`demo.v1`) не контент игры, его golden-значения менять нельзя, кроме единственной осознанной смены в T02. **(предл.)** Новые колонки хешируются **отдельными частями** (`ext[…]`: `character_ext`, `dynasty_ext`, …); пустая часть = 0 и **не входит в `total`** (ADR-0006 §D7) — поэтому пять старых частей **и `total`** демо остаются прежними; меняется только хеш байтов сейва (один раз, в T02). Старая команда `KillCharacter` остаётся как есть (демо), новая смерть — команда `Die` |
| 3 | Где живёт игровая логика E7 | Только в новых системах `dynasty.*`, которые ставит сценарий `dynasty.v1` (и позже сценарий M1 из E4-T10). Демо-системы не меняются |
| 4 | Расписание жизненных событий | **(предл.)** Смертность и старение — **в день рождения** персонажа, а не по `id % 365`: при штаффеле по id первый бросок ребёнка может прийти после его первого года, и корзина «0 лет» (220‰) будет систематически пропущена. Решено в ADR-0006 §D4: `ScheduledQueue` как производный (не сохраняемый) индекс над колонками, порядок в дне `(due, kind, id)`, бросок на предстоящий год с датой смерти внутри года; 29 февраля → 28 февраля ✅. Месячные расчёты (здоровье, зачатие) — `is_monthly_slot(id)`; роды и совершеннолетие — очередь по дате |
| 5 | Как системы меняют мир | Решения принимают системы `dynasty.*`, эффекты идут **внутренними командами** (`Die`, `Birth`, …) с валидацией на границе тика. Следствие: задержка «решение → эффект» один тик; системы должны переносить, что персонаж умер между решением и применением (проверка при `apply`) |
| 6 | Данные и состояние | Состояние — в `World` (SoA). Определения и баланс — в `.pd` (см. подраздел ниже). Скомпилированные таблицы (`DemographyRules`, `TraitCatalog`) — **неизменяемые параметры**, передаются системам при создании, не являются состоянием; их хеш входит в сейв вместе с хешем контента E4 (решение 6 эпика E4) |
| 7 | Слои | `sim` не зависит от `data`. Структуры правил (`DemographyRules`, `TraitDef`) объявлены в `sim` с запасными значениями из GDD; заполнение из `.pd` — в слое сборки (`src/game` или будущий `rules`), чтобы тесты `sim` работали без файлов |
| 8 | Случайность | Только `world.rng().stream(name)`; отдельный поток на назначение: `demography.mortality`, `demography.conception`, `demography.birth`, `demography.genetics`, `demography.health`, `demography.names`. **(предл.)** Правило: на одну обрабатываемую сущность — **фиксированное число извлечений** независимо от ветки (бросаем всегда, сравниваем потом), чтобы добавление условия не сдвигало последовательность для остальных |
| 9 | Арифметика | `Fixed32` для навыков (0…20), здоровья/плодовитости/стресса/благочестия (0…100), лояльностей (−100…100); вероятности — целые промилле (`chance_permille`); никаких `float`. Множители таблиц — в промилле/`Fixed` |
| 10 | Черты в записи | **(предл.)** 8 слотов `u16` (индекс черты в каталоге, 0 — пусто), отсортированы по возрастанию; не битовая маска (маска не масштабируется на моды и > 64 черт). Противоположности взаимоисключающие (проверка при выдаче) |
| 11 | Родство в хранилище | **(принято, ADR-0006 §D2)** Родители — колонки; дети — не `vector<vector<…>>` на человека, а интрузивные **производные** списки «первый ребёнок / следующий брат» (порядок `(birth_date, id)`, не сохраняются, строятся при загрузке); супруг — текущий (одна колонка) + число браков и короткий список бывших (до 3 браков, GDD §7.3) |
| 12 | Образование в M1 | Выбор направления (5 направлений = 5 навыков) + наставник по желанию, без учебных событий (GDD §5, §14); итог — образовательная черта и бонус навыков в 16 лет |
| 13 | Имена | **(предл.)** Отчества задаются **явными формами в данных** (`Пётр → Петрович / Петровна`), без морфологического алгоритма; фамилии — из рода с женской формой также в данных. Имена людей — вымышленные сочетания (решение #2), без совпадения с реальными историческими лицами рода |
| 14 | Мнения | Разреженное хранилище ≤ 30 записей на человека; при переполнении вытесняется слабейшее по модулю (ничья — по меньшему id); затухание помесячно по штаффелю |
| 15 | Крёстные | ❓ (вопрос 3): влияет только на резерв поля в схеме |
| 16 | Смысл «легитимности» (FR-DYN-6) | ❓ (вопрос 1): шкала рода или статус рождения |
| 17 | Допустимое вымирание родов и баланс | ❓ (вопрос 2): влияет на приёмку калибровки |

### 3.2 Контракты с соседними эпиками

- **E8:** `Marry`/`Widow` (только системный актор, без правил), `children_of`, `age`, плодовитость, колонка легитимности, поле `succession_law`, замена функции запасного преемника, ветви, `AdjustHonor`/`AdjustUnity`, API летописи.
- **E10 / E14 / E17 / E31:** хранят `CharacterId` в своих таблицах. Умерший остаётся валидным идентификатором с `is_alive == false`; `Die.apply` чистит ссылки E7 (глава, супруг, наставник, мнения, беременность, очередь). Остальные эпики реагируют на уже применённую команду `Die` из журнала команд тика (шины триггеров в E7 нет — E11 может строить её поверх журнала) и добавляют проверки в свой `check_invariants`.
- **E11:** все изменения людей — команды, поэтому триггеры «рождение/смерть/брак» выводятся из журнала применённых команд.
- **E30:** создание людей и рода — через те же команды/конструкторы (`CreateCharacter`, расширенные `Birth`/`Found`).

## 4. Пользовательские истории и критерии приёмки

**US-7.1.** *Как игрок, я хочу видеть, на что способен человек и почему.*
- *Дано:* персонаж с чертами «честолюбивый» и образованием «дипломатическое». *Когда:* навожу курсор на навык «Дипломатия». *Тогда:* тултип раскрывает значение в слагаемые (базовое, наследственное, образование, каждая черта), сумма слагаемых равна показанному числу; то же для здоровья и плодовитости.

**US-7.2.** *Как игрок, я хочу, чтобы род жил сам.* (DYN-A1)
- *Дано:* род с главой 45 лет, женой 30 лет и тремя детьми. *Когда:* прошло 5 лет без вмешательства (сценарий `dynasty.v1`, фиксированный seed). *Тогда:* в роду родилось 1–4 ребёнка (в большинстве прогонов по набору seed), возраст каждого вырос, `check_invariants()` пуст (родство симметрично, нет живых с датой смерти).

**US-7.3.** *Как игрок, я хочу помнить умерших.*
- *Дано:* персонаж умер. *Когда:* открываю древо рода. *Тогда:* он показан как умерший (даты жизни, причина смерти, родители, дети), не участвует в годовых/месячных расчётах, не числится в членах рода, его мнения и беременность убраны; память занята только компактной записью.

**US-7.4.** *Как игрок, я хочу, чтобы смерть главы не ломала игру.*
- *Дано:* глава рода умер, в роду есть совершеннолетние. *Когда:* применяется `Die`. *Тогда:* в тот же или следующий тик главой становится преемник по запасному правилу, в летописи две записи (смерть, смена главы); если живых нет — род помечен вымершим, запись в летописи, игровых исключений нет. (Законы наследования и споры — E8.)

**US-7.5.** *Как разработчик, я хочу правдоподобную демографию.*
- *Дано:* `dynasty.v1`, 100 лет, несколько seed. *Когда:* тест подсчитывает метрики. *Тогда:* выполняются допуски GDD 01 §13.1 (продолжительность жизни знати 38–48, 5–8 детей на замужнюю женщину, доля мальчиков 51–52%, число живых выходит на плато) и доля вымерших родов не выше порога, принятого владельцем (❓2).

**US-7.6.** *Как разработчик, я хочу, чтобы сейвы и реплеи не ломались.* (DYN-A7)
- *Дано:* два прогона одного seed и потока команд; сохранение в середине беременности. *Когда:* загрузка и продолжение. *Тогда:* хеши династий и всего мира совпадают с прогоном без перезагрузки; сейв старой схемы читается с миграцией.

**US-7.7.** *Как автор баланса, я хочу править таблицы без пересборки.*
- *Дано:* `data/balance/demography.pd`. *Когда:* меняю смертность корзины 45–59 и запускаю `contentlint` и `simcli --scenario dynasty`. *Тогда:* ошибки схемы показываются с `файл:строка`, новое значение влияет на результат, хеш контента в сейве изменился.

**US-7.8.** *Как игрок, я хочу выбирать образование наследника.*
- *Дано:* ребёнок 7 лет. *Когда:* отдаю команду `SetEducation(child, focus, tutor?)`. *Тогда:* валидация отклоняет умершего/взрослого/несуществующего наставника с причиной; в 16 лет ребёнок получает образовательную черту и бонус к навыку направления; результат зависит от навыка наставника.

**US-7.9.** *Как игрок, я хочу понимать честь и единство рода.*
- *Дано:* род с честью 3200. *Когда:* открываю совет рода и навожу курсор на честь. *Тогда:* видны ранг рода, пороги соседних рангов и список последних изменений с причинами и датами (разложение).

## 5. Технические задачи

Порядок «сначала риск»: сперва проект хранения и сохранений (самое дорогое место для ошибки — каскадом идёт в хеш, сейвы, реплеи, команды и все соседние эпики), потом данные и системы, затем калибровка и производительность, затем окна.

## 6. Тесты

**Детерминизм**
- Каждая система и команда: два прогона одного seed → одинаковые хеши; прогон с разбиением на два отрезка (сохранение/загрузка посередине) → тот же хеш, что без разбиения.
- `simcli --verify-determinism --scenario dynasty` в CTest (аналог `simcli_determinism`).
- Ревью-правила: нет `unordered_*` в итерациях, нет `float`, порядок обхода — по возрастанию id или явному ключу; потоки ГСЧ только по именам §3 (грепом/тестом в `tests/` проверяется отсутствие `rand`, `random_device`).
- Параметры правил попадают в хеш метаданных: изменение таблицы смертности меняет хеш правил, а не «тихо» состояние.

**Политика golden-значений** (AGENTS.md §5.4, `tests/golden_test.cpp`)
- `demo.v1`: шесть значений хеша (`total` и пять частей) **не меняются никогда**: расширенные части пусты (0) и не входят в `total` (ADR-0006 §D7). Единственное осознанное изменение — хеш байтов `save_state` в T02 (блок расширения); тест после этого хеширует нагрузку без слова схемы, и дальнейшие подъёмы схемы его не трогают. Любой другой PR, меняющий golden демо, — баг.
- Реплеи: команды E7 добавляются **новыми тегами из блока 6…31** (`type_of` — явная таблица), кодировка старых не меняется; `PRP1` не меняется (`total` покрывает расширенные части), `play_replay` сравнивает только записанные поля.
- `dynasty.v1`: собственные значения в `tests/golden_dynasty_test.cpp`, фикстура данных — копия в `tests/data/` (правки живого `data/` баланс не ломают golden). Первое закрепление в T18 помечено «предварительное», осознанное пересчитывание в T19; далее любое изменение формул или таблиц обновляет golden с объяснением в коммите.
- Изменения хеша от «незапланированного» (например, смена порядка итерации) — баг, а не повод править константу.

**Сохранения и миграции** (FR-SAVE-1)
- `World::kStateSchema` поднимается на единицу в каждом PR, меняющем раскладку (T02, T03, T04, **T12**, T14, T16, T17; номер — следующий свободный на момент слияния, таблица шагов в ADR-0006 §D6; затем E8+/E31/E10 по своим задачам); у каждой версии — шаг миграции «N−1 → N» и фикстура сейва (`tests/data/saves/`, генерируется отдельной утилитой, не `assets/`).
- Тест цепочки: сейв схемы 1 (из E1) → последовательно до текущей; результат проходит `check_invariants()`, имеет умолчания в новых колонках и тот же хеш старых частей.
- Сейв в середине беременности, с непустой очередью жизненных событий, с архивом и летописью; фаззинг порчи байтов и обрезаний (как в E1-T10) расширен на новые разделы; счётчики из файла не доверенные (проверка `plausible`).
- Контейнер `PSV1` и `kSaveFormatVersion` не меняются без необходимости: миграция схемы мира живёт в `World::load_state` (читает версии ≤ текущей типизированными шагами), а не в `migrate_to_current` — зафиксировано в ADR-0006 §D6.

**Реплеи**
- `Die`, `Birth`, `SetEducation`, `AdjustUnity` проходят `validate()`, пишутся в журнал, воспроизводятся `play_replay`; внутренние команды (смерть, роды) повторно порождаются системами и не пишутся как внешний ввод.

**Свойства (property)**: инварианты GDD 01 §13.3 — дата рождения не позже сегодня, нет циклов родства, ≤ 2 родителей, симметричный супруг, сумма членов родов = числу живых уровня A, шкалы в границах, нет живых ссылок на архивных там, где они недопустимы.

**Демографический прогон** (GDD 01 §13.1): 100 лет без игрока на ≥ 10 seed; допуски: продолжительность жизни знати при рождении 38–48; 5–8 детей на замужнюю женщину; доля мальчиков 51–52%; плато численности; доля вымерших родов — по ответу ❓2.

**Производительность (NFR-PERF-2/5, GDD 01 §12)** — бюджеты **[предл.]**, измеряются в T20 на `stressgen` (5 000 живых + ~20 000 архивных, профили `year60`, `year60x3`):

| Что | Бюджет |
|---|---|
| Ежегодная демографическая обработка 5 000 персонажей, пик «всё в один день» | ≤ 5 мс (GDD §12); при размазывании по дням — ≤ 0.1 мс/день |
| Помесячный обход фертильных пар (сотни) | ≤ 2 мс (GDD §12); со штаффелем на день ≤ 0.1 мс |
| Доля E7 в дневном тике p95 (бюджет всего тика 8 мс) | ≤ 0.5 мс |
| Память: 5 000 живых + 20 000 архивных | ≤ 10 МБ [предл.] (общий потолок партии 1.5 ГБ) |
| `compute_hash` по 25 000 строк | ≤ 2 мс |
| Размер несжатого сейва мира с людьми | ≤ 6 МБ; загрузка ≤ 200 мс (NFR-PERF-6: всё ≤ 15 с) |
| Деградация «год 1 → год 60» | ≤ 2× (NFR-PERF-3): проверка, что рост архива не замедляет тик |

Для регрессий бенчмарки E7 подключаются к CI-гейту E2-T07 (порог 10%), когда он появится.

**Контент**: `contentlint` на `data/traits`, `data/skills`, `data/balance`, `data/names` (после E4-T08); тест «все ключи текстов существуют» (E4-T06).

**UI**: тесты моста (формат имён, дерево, разложение сумм), скриншот-тесты окон (как в E3-T07/T08), замер кадра с деревом из 300 узлов.

## 7. Риски

| Риск | Митигация |
|---|---|
| Смена раскладки персонажей каскадом ломает хеш, сейвы, реплеи, `stressgen` и демо golden | T01 (ADR + план миграций) до кода; новые колонки в отдельных частях хеша — демо-доказательство неизменности; сейв/реплей фикстуры; изменения схемы строго последовательны |
| Идентификаторы: переиспользование слотов (LIFO в `EntityTable`) делает ссылки на умерших ошибочными | Не переиспользовать id людей (T01), проверка `is_alive` в каждой ссылке, инвариант «ссылка на архивного допустима только там, где задокументировано» |
| Штаффель по `id` систематически пропускает корзину «0 лет» | Смертность в день рождения (очередь/корзины по дню года), тест на «ребёнок получает бросок 0 лет» |
| Демография реалистична, но игра заканчивается вымиранием слишком часто | Калибровка T19, ответ владельца ❓2, параметры в данных; смягчение — множитель знати, а не правка кода |
| Экспоненциальный рост населения в сценарии без E8 | Поправка на «тесноту» в T12, плато как критерий T19, жёсткий потолок не вводим |
| Утечка «каждый день по всем» (проверки дней рождения) | Очередь/корзины вместо скана; правило ревью ADR-0002 P8; бенчмарки T20 |
| Размер T02 (L) и конфликты с параллельными задачами E4/E9 в `World` | Разрезать по частям хеша (персонажи/род); координация в issue; перед стартом `gh pr list`; T02 берётся одним агентом |
| Нехватка контента (черты, имена, таблицы) | Запасные значения в коде + минимальный набор ≈ 25 черт и пулы имён по ~30 имён на пол; расширение — E22 |
| UI-задачи упираются в состояние E6 | T21 не зависит от E6 (мост); T22–T24 стартуют после каркаса E6; при задержке остаются в `status:blocked` |
| Стоимость разложений (`breakdown`) для тултипов на горячем пути | Разложение строится лениво по запросу UI из снапшота (ADR-0002 P3), основное значение хранится/считается без него |
| Тесты на статистику нестабильны | Фиксированные seed, допуски заранее вычислены на выборке, а не на одном прогоне |
