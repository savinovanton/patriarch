## Рекомендуемый порядок («сначала риск»)

Самые дорогие ошибки стека видны в E3 (UI) и E2 (производительность). Поэтому не идти строго по номерам:

```
Неделя 1:  E0-T01…T05  (репозиторий, CMake, vcpkg, тесты)            ── основа
Недели 2–4: E3 сокращённый (T01, T02, T03, T04, T06, T07, T08, T10, T11)  ── выживает ли D3D11 + RmlUi?
           ∥ E1-T01…T04 (Fixed, PRNG, ID, календарь)                  ── параллельно, мелкие задачи
Недели 5–8: E1-T05…T11 (мир, команды, цикл, поток, снапшоты, реплей, сейвы)
Недели 9–11: E2 (бенчмарки, генератор, спайки A/B/C, CI-гейт)
Недели 12+: E3-T12 (связка с ядром), E0-T06 (CI полностью), обновление ADR
```

**Критические решения (гейты):**
1. **После E3 сокращённого (≈ неделя 4):** подходит ли RmlUi? Если нет — запасной план из ADR-0001.
2. **После E2-T03 (≈ неделя 10):** укладывается ли месячный тик в бюджет? Если нет — пересмотр лимитов (ТЗ NFR-PERF-5).
3. **После E2-T05:** выбор способа публикации снапшотов (ADR).

## Темп

| Занятость | Календарь M0 (≈ 75–90 дней FTE) |
|---|---|
| Полный день (FTE) | ~4–5 месяцев |
| Полдня (50%) | ~8–10 месяцев |
| 10–15 часов в неделю (~25%) | ~16–20 месяцев |

Это расходится с первоначальной оценкой в ADR/эпиках («спайки 2–3 недели»): та оценка относилась к **одному** спайку, а не ко всему M0. Реалистичная цель по ритму — **играбельный результат каждые 2–4 недели**: окно с картой (конец недели 4), симуляция в консоли (неделя 8), симуляция + карта вместе (неделя 12).

## Общие правила по задачам

- Каждая задача закрывается PR с тестами; для S-задач допустим прямой коммит в `main` после прохождения CI.
- Формат ID: `E{эпик}-T{номер}`; ссылка на ID в сообщении коммита.
- «Готово» = код + тест/бенчмарк + запись в документации (если меняется контракт).
- Новые решения оформляются ADR (`docs/adr/`).
