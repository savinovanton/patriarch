# E2-T05 — публикация снапшотов для UI

Изолированный спайк: одинаковое числовое UI-представление передаётся тремя способами.
Игровой `SimulationRunner` и формат `World` не меняются.

```powershell
cmake --build --preset win-msvc-release --target snapshot_spike
python tools/snapshot_spike/run_matrix.py --exe out/win-msvc/tools/snapshot_spike/Release/snapshot_spike.exe --output out/E2-T05-results.json
```

Один вариант (JSON в stdout, ошибки в stderr):

```powershell
.\out\win-msvc\tools\snapshot_spike\Release\snapshot_spike.exe --profile year60 --changed-permille 10 --rate 400 --seconds 2 --repetitions 3 --hold-frames 0
```

## Одинаковые данные и гарантии

- `year60`: 400 провинций + 100 родов, 500 строк по 8 `uint32`, 16 000 байт.
- `year60x3`: 1 200 провинций + 300 родов, 1 500 строк, 48 000 байт.
- Во всех вариантах UI читает восемь полей не более 400 провинций и 100 родов,
  равномерно распределённых по исходному массиву (включая последнюю страницу).
  Это checksum числовых полей, без форматирования строк, RmlUi, GPU и персонажного окна.
- Начальные значения берутся из мира `stressgen` (5 000 / 15 000 персонажей), часть
  полей — явно синтетические заполнители. Изменения синтетические, не игровые команды.
- Доля изменений — **строк** за публикацию. В каждой выбранной строке меняется ровно
  **одно** из восьми полей; даже 100% строк не означает изменение всех полей.
  Порядок строк перемешан, seed мира 7, PRNG `snapshot.fixture` / `snapshot.changes`.
- Любой выданный `Frame` неизменяем и может пережить transport. Версии монотонны,
  UI имеет latest-state семантику и может пропускать промежуточные версии.

Три прототипа:

1. `full`: новая полная копия UI-представления и atomic `shared_ptr` публикация.
2. `diff`: копирование только изменённых ячеек в неизменяемые пакеты
   `(row, field, value)`. Очередь максимум 64 пакета; при переполнении заменяется полной
   контрольной копией текущего состояния. UI забирает цепочку под коротким mutex и
   применяет вне mutex. Его cache копируется, если старый `Frame` ещё удержан читателем.
3. `pages`: два банка страниц по 128 строк (4 КиБ данных). В заднем банке обновляются
   все устаревшие страницы, а не только изменения последнего тика: банк может отставать
   на несколько версий. Публикуется immutable directory. Если старый читатель держит
   страницу, применяется COW; иначе память страницы используется повторно.

`pages` не обещает фиксированный расход ровно двух буферов при произвольном удержании
читателями. Все три схемы могут расходовать больше памяти из-за старых `Frame`.
Atomic `shared_ptr` не объявляется lock-free. Diff-копирование checkpoint выполняется
под mutex при переполнении; это ограниченный fallback с измеряемой стоимостью.

## Два режима измерения

**Micro:** один поток, общий вход для всех схем, 64 публикации прогрева, затем 1 024
измеренных публикации × 3 повтора. Порядок схем чередуется. Изменения и контрольный
checksum строятся вне таймера. Отдельно измеряются publish и acquire/apply; сверка
выполняется после таймеров. В конце сравниваются все поля, включая не попавшие в viewport.
Потребитель забирает каждую версию. Счётчики памяти/копирования включают прогрев.

**Paced:** отдельные producer/UI-потоки, целевые 40 или 400 публикаций/с и 60 чтений/с,
2 секунды × 3 повтора. На повторах порядок схем вращается. Потоки закреплены за первым
и третьим разрешённым логическим CPU (если доступны только два — за первым и вторым);
это не утверждение об их физической топологии. Используется локальный high-resolution
waitable timer Windows, без изменения системного timer resolution и без busy-wait.
JSON сообщает фактически достигнутые частоты, overruns и доступность high-res таймеров.
Изменения/ожидаемый checksum вне publish-таймера, но входят в ограничение реальной частоты.

`acquire_us` включает получение ссылки и, для diff, применение накопленной цепочки;
`read_us` — чтение/контрольный checksum UI-полей. `age_at_acquire_us` — время от готовности
входной версии до завершения её получения UI, включая ожидание кадра; это не latency
каждой публикации: UI может пропускать версии. Повторные кадры включены в возраст,
нулевая начальная версия исключена. Нет обещания общей доставки или очереди событий.

Матрица: два размера × 1/10/100% строк × 40/400 публикаций/с; ещё два варианта на
400 публикаций/с удерживают два старых кадра (`year60`/1%, `year60x3`/100%). Всего 14
вариантов, фиксированный перемешанный порядок seed 20261107, без повторных прогонов
ради удобных результатов. SHA-256 измеренных C++-исходников записываются в JSON.

Квантили — nearest-rank. RSD считается по средним publish трёх повторов;
`stable=true` только при ≥3 повторах и RSD ≤5%. Нестабильные строки сохраняются и не
используются для точного ранжирования. В paced короткие выборки и scheduler влияют
на хвосты; порогов времени в тестах/CI нет.

## Память и существующий API

`owned_bytes_peak` считает одновременно живые объекты Data/Packet/Page/Directory и
их vector capacity с помощью общих atomic-счётчиков (их стоимость входит во время).
Это логическое владение транспорта, **не** RSS процесса: исключены allocator headers,
control blocks, служебные capacity очередей/банков, исходный мир и массивы замеров.
`producer_payload_bytes` / `consumer_payload_bytes` считают копируемые данные, а не
cache-line или DRAM-трафик; метаданные и инициализация в эти счётчики не входят.

Отдельный `world_copy_reference_us` измеряет нынешнюю `World::snapshot()` + atomic store
той же полной копии мира (16 прогрева + 176 измерений); хеш проверяется после таймера.
Он не участвует в сравнении трёх одинаковых UI-payload: содержит также персонажей,
индексы и PRNG. `serialized_world_bytes` — размер сериализации, не оценка heap памяти.

Целевые проверки: `ctest --preset win-msvc-debug -L snapshot_spike`. Они проверяют
переполнение diff-очереди, устаревший задний банк, точные поля, старые кадры после
уничтожения транспорта, конкурентное чтение и структуру реального CLI-отчёта.
